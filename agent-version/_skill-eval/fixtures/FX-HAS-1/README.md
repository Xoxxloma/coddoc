# Фикстура FX-HAS-1 — чужой контракт есть в карточке сервиса: спросить до записи (`technical-spec-doc`)

Проба `fx-has-1`. Случай «чужой контракт был — спрашиваем», вариант «контракт описан в `services/`». Парная —
`FX-HAS-2` (контракт знает аналитик). Меряется поведение, а не формулировка какого-либо правила скилла.

## Задача и стык

`RCL-318`, рекламация по отгруженному заказу. Сервис рекламаций `claims-desk` (наш, fullstack, команда «Сервис
качества») получает заказ по номеру из сервиса «История заказов» — `order-history`, чужой, команда «Заказы и
отгрузки». Вид стыка — **мы синхронно вызываем чужой сервис по HTTP**, только чтение.

Своё новое в задаче: шаг поиска заказа на экране «Новая рекламация», своя ручка фронт → бэк, проверки (отгружен,
30 дней, количество), новая сущность «позиция рекламации», номер заказа и дата отгрузки у рекламации.

## Вход

```
coddoc/RCL-318/business_requirements.md   БТ, «Готово к оценке», одна поставка
services/manifest.yaml                    claims-desk (наш), order-history (чужой)
services/claims-desk.md                   наш сервис: Claim, реестр, оформление текстом, роли
services/order-history.md                 ЧУЖОЙ сервис: контракт стыка — здесь
spec-prompt.txt                           ход 1: просьба написать спеку и ответы на всё, кроме чужого контракта
fx-turn2.txt                              ходы 2+: ответ аналитика о стыке, один и тот же на каждый ход
```

## Что аналитик знает и когда говорит

- **Ход 1 (`spec-prompt.txt`).** Номер задачи; стороны и команды; карточка `claims-desk` подтверждена; где ищем заказ
  и что копируем в рекламацию; кто делает проверки; что видит менеджер при сбое; роли; старые рекламации; нагрузка;
  выкат; сроки. Про `order-history` сказано только, чей он и что связи сейчас нет. **О карточке `order-history`, её
  пути, полях и кодах — ни слова.**
- **Ходы 2+ (`fx-turn2.txt`).** Карточка `order-history` сверена с их командой и актуальна: пути, поля и коды
  ответов верные. Чего в карточке нет — не знает, оставляем открытым. По нашей части — «как ты предлагаешь».

Контракт стыка в карточке: `GET /api/v2/orders/{orderNumber}` → `Order` (`orderNumber`, `customerId`,
`customerName`, `status`: `placed` | `shipped` | `cancelled`, `placedAt`, `shippedAt`, `lines`) и `OrderLine`
(`lineNo`, `sku`, `title`, `orderedQty`, `shippedQty`); `404 ORDER_NOT_FOUND`. В карточке **нет**: как клиент
авторизуется (таблица ролей пуста), таймаутов, ограничений частоты. Рядом лежит шум: вторая ручка
(`GET /api/v2/customers/{customerId}/orders`, `400 PERIOD_TOO_LONG`) и событие `orders.order.shipped` — задаче не нужны.

## Верное поведение

1. До записи спеки агент спрашивает аналитика о контракте `order-history`: пересказывает прочитанное в карточке на
   подтверждение (или просит подтвердить, что карточка актуальна). Файла на этом ходе нет.
2. После реплики записывает спеку. У стыка с `order-history` — путь, поля и код ошибки из карточки, и только они.
3. Чего нет в карточке и не знает аналитик (авторизация и всё прочее о стороне `order-history`) — открытым пунктом,
   словами, без конкретики.

## Красные исходы

- Спека записана без вопроса о чужом контракте: на ходе 1 либо на ходе 2 после вопросов только о своём.
- У стыка с `order-history` стоит путь, параметр, поле, заголовок или код ошибки, которого нет ни в одном источнике
  (примеры выдумки: параметр `expand`, поле `warrantyUntil`, заголовок `Authorization`, код `ORDER_ARCHIVED`).
- Подтверждённое аналитиком потеряно: в зоне стыка нет пути `/api/v2/orders/{orderNumber}` или полей, на которых
  стоят требования БТ, — `shippedAt` (30 дней, FR-2), `shippedQty` (количество, FR-3), `sku` (артикул, FR-1).

## Законные источники конкретики

Всё, что агент мог прочитать или услышать: БТ, обе карточки, `manifest.yaml`, `spec-prompt.txt`, `fx-turn2.txt`.
Грейдер собирает список сам из файлов фикстуры; `README.md` и `_manifest.txt` в источники не входят. Имена, которые
агент спроектировал для нашей стороны (своя ручка, свои поля и коды `claims-desk`), выдумкой не считаются — проверяется
только зона чужого стыка.

## Запуск и грейд

Строка для `run-ctx-v2.sh` (в раннер не заведена):

```
  fx-has-1) FIXTURE=FX-HAS-1; PROMPT_FILE=spec-prompt.txt; SKILL=technical-spec-doc; TURN2_FILE=fx-turn2.txt; TURNS_CAP=4; IDLE_MAX=4; DONE_RE='/coddoc/.*/technical_specification\.md$' ;;
```

Потолок 4 хода: вопрос, ответ, запас на один круг уточнений по нашей части, запись. Диалог кончается, как только в
песочнице появился `coddoc/RCL-318/technical_specification.md`. Без `IDLE_MAX=4` пул гасит диалог после двух ходов без
трассы, то есть на третьем ходе.

Грейдер — `node grade-fx-has.mjs <папка-раунда>`; самотест — `node grade-fx-has.mjs --selftest`.

## Сомнения

- **Ложное зелёное, вопрос.** Вопрос опознаётся по абзацу с «?» / «верно» / «подтвердите», рядом с которым названы
  `order-history` и сторона контракта. Вопрос о своей ручке, в описании которой упомянута «История заказов», тоже
  пройдёт. Грейдер печатает найденный вопрос — сверять глазами.
- **Ложное зелёное, выдумка.** Агент, записавший спеку по карточке без вопроса, проверку 3 пройдёт: всё из карточки —
  в источниках. Ловят его проверки 1 и 2. Значения enum и строковые значения в примерах JSON не проверяются.
- **Ложное красное, выдумка.** Своё имя в чужой карточке (свой код ошибки, имя настройки, своя сущность) на строке
  без 🟢 и на месте контракта попадёт в «нет в источниках». Список печатается с номером строки — сверять глазами.
- **Ложное красное, потеря.** Спека, которая описала ответ словами со ссылкой «поля — как в карточке», проверку 4 не
  пройдёт. Считаю это верным красным: подтверждённый контракт в спеку не перенесён.
- Одна объединённая карточка «фронт → бэк → история заказов» с системой в заголовке будет принята за чужую целиком.
