## 1. Введение и контекст
### 1.0. Тип изменения
Доработка существующего: добавление проверки легитимности клиента в сервисе, который раздаёт конфигурацию приложениям, и управление ключами приложений в портале управления конфигурацией.
### 1.1. Описание проблемы
Сервис, который отдаёт приложениям конфигурацию, сейчас может выдать её любому, кто узнал адрес сервиса и appId приложения — отличить легитимного клиента от поддельного нечем.

### 1.4. Как сейчас
Сервис конфигурации не проверяет личность вызывающего ни на одном запросе: конфигурация любого appId/кластера/namespace отдаётся по одному запросу, кем бы он ни был отправлен. В части случаев для смягчения перед сервисом ставят nginx с basic-авторизацией — это обходной путь, и для клиентских библиотек (SDK) он неудобен.

## 2. Бизнес-требования (цели и ценность)
### 2.1. Бизнес-цель
Я как администратор приложения должен иметь возможность включить проверку клиента по ключу для приватных namespace своего приложения, чтобы конфигурацию с чувствительными настройками не мог забрать поддельный клиент.
### 2.2. Ценность для бизнеса
Отсутствие встроенной проверки клиентов может быть блокером при выборе этого решения для компаний с требованиями безопасности. В одном конфигурационном центре живут разные приложения и команды — проверка не даёт им видеть чужие чувствительные настройки. Особенно важно там, где тестовые стенды открыты в интернет, а связывать сети при гибридном облаке дорого.
### 2.3. Бизнес-риски и меры по снижению
| Риск | Вероятность / влияние | Меры по снижению |
|------|-----------------------|------------------|
| Без встроенной проверки клиент, узнавший appId и адрес сервиса, может забрать чувствительную конфигурацию чужого приложения/команды | — | — |
| Часть тестовых стендов открыта в интернет, а при гибридном облаке связывать сети дорого — без встроенной проверки это увеличивает поверхность атаки | — | — |

## 3. Объём проекта
### 3.1. Входит в проект
- Проверка легитимности клиента при доступе к приватным namespace приложения.
- Создание и включение ключа приложения в портале управления конфигурацией, отдельно на каждое окружение.
- Передача секрета клиентом тем же способом, что сейчас appId (детали — в §4.3).
- Обратная совместимость: при отсутствии включённого ключа у приложения конфигурация отдаётся как раньше, старые клиенты продолжают работать без изменений.
- Отказ (`401 Unauthorized`) при неверном или отсутствующем секрете, если у приложения включён ключ.
- Отклонение запроса с меткой времени старше одной минуты.
### 3.2. Не входит в проект
- Проверка доступа к публичным namespace — они остаются открытыми, как сейчас.
- Отдельный ключ на каждый namespace внутри приложения — ключ действует на уровне приложения, на каждое окружение свой.
- Защита от повторной отправки запроса (replay) в пределах минутного окна и одноразовые запросы — сознательно не делаются.
### 3.3. Архитектурные изменения и интеграции
Затронуты сервис, который раздаёт конфигурацию приложениям (добавляется проверка клиента по ключу), и портал управления конфигурацией (управление ключами приложения по окружениям).

## 4. Функциональные требования
### 4.1. Описание функционала / бизнес-процесса
Администратор приложения в портале управления конфигурацией создаёт и включает ключ приложения отдельно на каждое окружение (**FR-1**). Пока у приложения нет ни одного включённого ключа, сервис конфигурации отдаёт конфигурацию приватных namespace без проверки — как раньше, старые клиенты продолжают работать без изменений (**FR-2**). Как только у приложения появляется хотя бы один включённый ключ, запросы к приватным namespace этого приложения проверяются по ключу; запросы к публичным namespace проверке не подлежат (**FR-3**). Если при включённом ключе клиент присылает неверный или отсутствующий секрет, сервис отвечает `401 Unauthorized`, конфигурация не отдаётся (**FR-4**). Запрос с меткой времени старше одной минуты сервис отклоняет как недействительный; в пределах минуты повтор того же запроса не блокируется — защиты от повторной отправки и одноразовых запросов не делаем (**FR-5**).
### 4.2. Критерии приёмки
- **[FR-1]** Дано: администратор приложения открывает управление ключами приложения в портале на конкретном окружении. Когда: создаёт и включает ключ. Тогда: ключ становится активным для проверки запросов этого приложения на этом окружении.
- **[FR-2]** Дано: у приложения нет ни одного включённого ключа. Когда: клиент запрашивает конфигурацию приватного namespace. Тогда: конфигурация отдаётся без проверки, как раньше.
- **[FR-3]** Дано: у приложения есть включённый ключ. Когда: клиент запрашивает конфигурацию публичного namespace. Тогда: проверка ключа не применяется, конфигурация отдаётся как обычно для публичного namespace.
- **[FR-4]** Дано: у приложения включён ключ. Когда: клиент присылает неверный или отсутствующий секрет при запросе конфигурации приватного namespace. Тогда: сервис отвечает `401 Unauthorized`, конфигурация не отдаётся.
- **[FR-5]** Дано: запрос подписан меткой времени старше одной минуты. Когда: сервис проверяет запрос. Тогда: запрос отклоняется как недействительный; ближайшее значение по ту сторону границы — метка времени в пределах минуты — проходит, и повтор такого запроса в этом окне не блокируется.

### 4.3. Бизнес-данные
Доработка:

| № | Объект | Что это | Что меняется |
|---|--------|---------|--------------|
| 1 | Конфигурация приложения | набор настроек, который получает приложение-клиент | без изменений в структуре; доступ к приватным namespace может требовать проверки ключа |
| 2 | Ключ приложения | секрет, подтверждающий, что обратилось легитимное приложение; создаётся и включается администратором приложения в портале, отдельно на каждое окружение | новый объект. Разработчик прописывает секрет в приложении; клиент считывает его в порядке приоритета: системное свойство JVM `apollo.accesskey.secret` (ключ запуска `-Dapollo.accesskey.secret`) → переменная окружения `APOLLO_ACCESSKEY_SECRET` → свойство `apollo.accesskey.secret` в файле `/META-INF/app.properties` — тот же порядок, что сейчас у appId |

### 4.5. Разбиение на части
Не применимо: все FR — звенья одного механизма проверки клиента. Создание и включение ключа без проверки на стороне сервиса конфигурации не защищает ничего; проверка без способа завести ключ невозможна. Ни один кусок не приносит бизнесу пользы (защита приватных namespace), пока не выпущены остальные.
