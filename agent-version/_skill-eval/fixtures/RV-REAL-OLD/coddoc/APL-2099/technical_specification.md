## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В портале управления конфигурацией администратор приложения сможет завести и включить ключ приложения отдельно на каждое окружение. Как только у приложения появится хотя бы один включённый ключ, сервис конфигурации начнёт требовать от клиента подписанный секретом запрос при обращении к приватным namespace этого приложения и будет отвечать `401 Unauthorized`, если подпись неверна, отсутствует или метка времени старше минуты. Публичные namespace и приложения без включённых ключей продолжают работать без проверки, как сейчас.
**Тип:** доработка — так названа в шапке БТ (§1.0).
**Стороны:** Fullstack — новый UI и API управления ключами в apollo-portal, новое хранение в apollo-adminservice, новая проверка при выдаче конфигурации в apollo-configservice.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| apollo-configservice | изменение (добавляется проверка ключа перед выдачей конфигурации) | команда Apollo (тот же продукт, в рамках которого ставится задача) | 🟢 |
| apollo-adminservice | изменение (хранение и CRUD ключа приложения по окружению) | команда Apollo | 🟢 |
| apollo-portal | изменение (новый экран и API управления ключами) | команда Apollo | 🟢 |
### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель БТ §2.1 — дать администратору приложения включаемую проверку клиента по ключу для приватных namespace, чтобы конфигурацию с чувствительными настройками не мог забрать поддельный клиент.

## 2. Взаимодействия (ядро)

### INT-1. Создание ключа приложения — 🟢
- **Вид:** новое
- **Граница/направление:** apollo-portal (UI) → apollo-portal (API), далее транслируется в apollo-adminservice выбранного окружения — 🔵 подтверждено аналитиком (по карточке services/apollo-portal.md: другие операции над приложением/namespace уже транслируются порталом во все активные окружения тем же способом)
- **Триггер:** администратор приложения нажимает «Создать ключ» для приложения на конкретном окружении
- **Контракт (запрос):** `POST /apps/{appId}/envs/{env}/accesskeys`; поля тела: `comment` (string, необязательно — метка для различения нескольких ключей одного приложения и окружения)
- **Контракт (ответ):** `id` (long), `appId` (string), `secret` (string — возвращается только в ответе на это создание, дальше не раскрывается), `enabled` (boolean, всегда `false` сразу после создания), `comment` (string|null), `dataChangeCreatedTime` (timestamp)
- **Пример запроса:**
  ```json
  { "comment": "SDK биллинга" }
  ```
- **Пример ответа (успех):**
  ```json
  { "id": 101, "appId": "billing-service", "secret": "7f2c1a9e4b3d...", "enabled": false, "comment": "SDK биллинга", "dataChangeCreatedTime": "2026-11-08T12:00:00Z" }
  ```
- **Ошибки:** см. «Каталог ошибок»
- **Состояния UI по ответу (если есть фронт):** значение → секрет показан один раз с предупреждением, что повторно он не отобразится; ошибка → сообщение с retry
- **Авторизация:** Master (владелец приложения) или обладатель права AssignRole на этот appId; проверяется в apollo-portal
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1

### INT-2. Включение/выключение ключа — 🟢
- **Вид:** новое
- **Граница/направление:** apollo-portal (UI) → apollo-portal (API) → apollo-adminservice окружения
- **Триггер:** администратор переключает статус конкретного ключа
- **Контракт (запрос):** `PUT /apps/{appId}/envs/{env}/accesskeys/{keyId}`; поля тела: `enabled` (boolean, обязательно)
- **Контракт (ответ):** `id` (long), `enabled` (boolean) — секрет в ответе не возвращается
- **Пример запроса:**
  ```json
  { "enabled": true }
  ```
- **Пример ответа (успех):**
  ```json
  { "id": 101, "enabled": true }
  ```
- **Ошибки:** см. «Каталог ошибок»
- **Состояния UI по ответу (если есть фронт):** значение → строка ключа обновляет статус; ошибка → сообщение с retry
- **Авторизация:** Master или AssignRole на appId
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1

### INT-3. Удаление ключа — 🟢
- **Вид:** новое
- **Граница/направление:** apollo-portal (UI) → apollo-portal (API) → apollo-adminservice окружения
- **Триггер:** администратор удаляет ключ из списка
- **Контракт (запрос):** `DELETE /apps/{appId}/envs/{env}/accesskeys/{keyId}`; тело отсутствует
- **Контракт (ответ):** не сущность (void), код 204
- **Пример запроса:** тело отсутствует
- **Пример ответа (успех):** тело отсутствует, код 204
- **Ошибки:** см. «Каталог ошибок»
- **Состояния UI по ответу (если есть фронт):** значение → ключ пропадает из списка; ошибка → сообщение с retry
- **Авторизация:** Master или AssignRole на appId
- **Происхождение:** 🟢 новое
- **Трассировка:** операционная потребность управления ключами, уточнённая аналитиком устно в этой сессии — в FR БТ отдельным пунктом не названа (FR-1 покрывает только создание и включение)

### INT-4. Проверка ключа приложения при выдаче конфигурации — 🟢 изменение существующего
- **Вид:** изменение существующего
- **Граница/направление:** Приложение-клиент (SDK) → apollo-configservice
- **Триггер:** клиент запрашивает конфигурацию приватного namespace
- **Существующий стык:** 🔵 подтверждено аналитиком (по карточке services/apollo-configservice.md) — `GET /configs/{appId}/{clusterName}/{namespace}`, `GET /configfiles/{appId}/{clusterName}/{namespace}`, `GET /configfiles/json/{appId}/{clusterName}/{namespace}`. Проверка не применяется к `GET /notifications` и `GET /notifications/v2` — они не отдают значений конфигурации.
- **Изменение:**

  | Поле | Где | Было | Стало |
  |------|-----|------|-------|
  | `Timestamp` | заголовок запроса | не существовало | добавлено: unix-время в миллисекундах на момент отправки запроса |
  | `Authorization` | заголовок запроса | не существовало | добавлено: `base64(HMAC-SHA1(секрет_ключа, значение заголовка Timestamp))` |
  | код ответа `401` | ответ | не возникал (личность вызывающего не проверялась) | добавлено: возвращается, если у appId есть включённый ключ на этом окружении, запрошенный namespace приватный, и подпись неверна/отсутствует либо `Timestamp` старше 60 секунд |

- **Контракт (запрос):** заголовки `Timestamp` и `Authorization` обязательны, только если у appId есть хотя бы один включённый ключ на этом окружении и запрошенный namespace не публичный; путь и остальные параметры — без изменений
- **Контракт (ответ):** без изменений при успехе; при отказе — код `401`, тело как в существующем стиле ошибок сервиса (текст, не JSON)
- **Пример запроса:** заголовки `Timestamp: 1731000000000`, `Authorization: Zm9vYmFyYmF6...==`; путь — как раньше
- **Пример ответа (успех) — фрагмент:** тело конфигурации не меняется относительно текущего поведения
- **Ошибки:** см. «Каталог ошибок»
- **Состояния UI по ответу (если есть фронт):** ~~не применимо: клиент — SDK, не пользовательский интерфейс~~
- **Авторизация:** при включённом у appId ключе на этом окружении и приватном namespace — обязательна валидная подпись; без включённых ключей (FR-2) или для публичного namespace (FR-3) — проверка не применяется
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-2, FR-3, FR-4, FR-5

### Каталог ошибок (сводно) — последний подраздел §2, после всех INT-карточек
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 401 | текст, называющий appId и namespace (без секрета) — секрет неверен, отсутствует или `Timestamp` старше 60 секунд | INT-4, у appId включён ключ на этом окружении, namespace приватный | не применимо — ответ получает SDK, не человек |
| 403 | текст — нет прав на управление ключами этого приложения | INT-1/2/3, вызывающий не Master и не AssignRole на appId | `error_forbidden` в портале |
| 404 | текст — приложение, окружение или ключ не найдены | INT-1/2/3, неверный appId/env/keyId | `error_source` в портале |

## 3. Backend — ответственность
### 3.1. По сервисам
**apollo-adminservice** (на каждое активное окружение) — 🟢: хранит новую сущность «Ключ приложения», реализует CRUD по ней (создание, включение/выключение, удаление) по вызову от apollo-portal; собственной проверки прав не делает — 🔵 подтверждено аналитиком (по карточке services/apollo-adminservice.md, роль «без входа»: контракт целиком без деления по ролям, проверка прав — в apollo-portal).

**apollo-portal** — 🟢: отдаёт экран управления ключами, реализует API `INT-1/INT-2/INT-3`, проверяет права вызывающего (Master/AssignRole) перед обращением к apollo-adminservice нужного окружения; сама транслирует запрос в это окружение — 🔵 подтверждено аналитиком (по карточке services/apollo-portal.md: та же схема, что у остальных операций над приложением — например, изменение данных приложения рассылается во все активные окружения).

**apollo-configservice** — 🟢: реализует `INT-4` — при запросе `/configs`, `/configfiles`, `/configfiles/json` для приватного namespace проверяет, есть ли у appId включённые ключи на этом окружении; если есть — пересчитывает HMAC-подпись по каждому включённому ключу и сравнивает с заголовком `Authorization`, проверяет `Timestamp`; список ключей держит в локальном кэше, обновляемом периодическим опросом БД (см. §5.1) — не обращается к apollo-adminservice по сети, 🔵 подтверждено аналитиком (со слов: проверка — фильтр в сервисе конфигураций; карточка apollo-configservice.md также не называет исходящих сетевых зависимостей — «Зависит от: —»).

### 3.2. Данные и хранение
- [🟢] `AccessKey` (концептуально — новая таблица в ApolloConfigDB каждого окружения, 🔵 подтверждено аналитиком со слов) — поля: `id` (long), `appId` (string), `secret` (string, генерируется сервером при создании, клиенту отдаётся только в ответе на создание), `enabled` (boolean, по умолчанию `false`), `comment` (string|null), `dataChangeCreatedTime` (timestamp), `dataChangeLastModifiedTime` (timestamp). Индекс по `appId` — основной паттерн чтения («все ключи приложения на этом окружении»), и при создании, и при проверке в configservice.

Миграция: новая таблица, существующие таблицы (App, Namespace, Release и т.д.) не меняются — подтверждено аналитиком явно («в App ничего не добавляем»). Старых строк в новой таблице нет, пересчитывать нечего.

Новых сущностей, кроме `AccessKey`, нет.

### 3.3. Авторизация/доступ на бэке
- apollo-portal: эндпоинты `INT-1/INT-2/INT-3` — доступ Master или обладателя права AssignRole на этот appId (🔵 подтверждено аналитиком, по карточке services/apollo-portal.md: роли `Master`/`AssignRole`); негативный случай — `403`.
- apollo-adminservice: не проверяет права вызывающего самостоятельно — доверяет apollo-portal (🔵 по карточке services/apollo-adminservice.md).
- apollo-configservice (`INT-4`): негативные случаи — неверный/просроченный/отсутствующий секрет при включённом ключе → `401` (FR-4); публичные namespace проверке не подлежат (FR-3); при отсутствии включённых ключей у appId проверка не применяется (FR-2).

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
apollo-portal, экран приложения: новый раздел «Ключи приложения» на уровне выбранного окружения — список ключей (метка/комментарий, дата создания, статус включён/выключен) и действия «Создать», «Включить/выключить», «Удалить». Вызывает `INT-1`, `INT-2`, `INT-3`.
### 4.2. Пользовательские сценарии
Основной поток: администратор создаёт ключ → копирует показанный один раз секрет → передаёт его в конфигурацию клиентского приложения → включает ключ, когда клиент готов его использовать (FR-1).
Ветвление: администратор выключает ключ, не удаляя его (например, при инциденте) — ключ сохраняется и может быть включён обратно.
Исключение: администратор закрывает экран, не скопировав секрет, — секрет не восстановим (решение §2, INT-1); единственный выход — создать новый ключ и удалить/выключить этот.
### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | запрос списка ключей или выполнение действия в процессе | спиннер |
| `value` | список ключей получен, в приложении на этом окружении есть хотя бы один ключ | таблица ключей |
| `empty` | у приложения на этом окружении ещё нет ни одного ключа | «Ключей нет» + кнопка «Создать» |
| `secret_revealed` | сразу после успешного создания, до ухода с экрана | показан секрет с предупреждением «больше не будет показан» |
| `error_source` | ошибка связи с apollo-adminservice окружения или 404 | сообщение об ошибке + retry |
| `error_forbidden` | 403 | «нет доступа» |
### 4.3.1. Loading и таймауты (обязательно, если есть FE)
Вызовы `INT-1/INT-2/INT-3` — обычные синхронные запросы apollo-portal к apollo-adminservice выбранного окружения, той же природы, что и остальные операции портала с этим окружением (🔵 по карточке services/apollo-portal.md — проксирование по каждому активному окружению); отдельный новый профиль таймаутов не вводится. Polling не требуется — операции выполняются по действию пользователя, не в фоне.
### 4.4. Доступ по ролям в UI
Раздел «Ключи приложения» доступен для просмотра и действий только Master или обладателю AssignRole на это приложение на выбранном окружении (🔵, см. §3.3); остальным пользователям портала раздел недоступен.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
`INT-1/INT-2/INT-3` — синхронные HTTP-вызовы portal → adminservice, как остальные операции портала с окружениями.
`INT-4` — проверка подписи синхронная, в процессе обработки запроса к apollo-configservice, без обращения по сети: ключи читаются из локального кэша, который обновляется периодическим опросом БД раз в 1 секунду пачками до 500 изменившихся записей — 🟢 собственный дизайн, по аналогии с существующими кэшами конфиг-сервиса (`scanNewAppNamespaces`, та же БД, тот же приём). Ожидаемая нагрузка не меняется по характеру: проверка добавляет сравнение подписи в памяти к уже существующему пути выдачи конфигурации, нового сетевого узкого места не создаёт.
### 5.2. Надёжность/деградация
Между включением/выключением ключа в apollo-adminservice и обновлением кэша в apollo-configservice есть окно до ~1 секунды (интервал опроса) — в этом окне запрос с ещё не подхваченным изменением может получить `401` или, наоборот, пройти по уже выключенному ключу; эффект самоустраняется в пределах следующего опроса.
Если БД окружения временно недоступна во время проверки подписи — apollo-configservice продолжает использовать последний успешно загруженный кэш ключей, как и для остальных своих кэшей; отдельного поведения не вводится.
Операция проверки — только чтение, ничего не пишет в apollo-configservice; вопрос «что остаётся записанным при сбое вызова другого сервиса» неприменим — вызова другого сервиса по сети при проверке нет.
### 5.3. Безопасность/доступ (сводно)
| Граница | Кто вправе |
|---|---|
| Создание/включение/выключение/удаление ключа (apollo-portal) | Master или AssignRole на appId |
| Получение конфигурации приватного namespace при включённом ключе (apollo-configservice) | клиент с валидной HMAC-подписью секретом одного из включённых ключей |
| Получение конфигурации публичного namespace или при отсутствии включённых ключей | без изменений — как сейчас |

## 6. Релиз и интеграция
### 6.1. Порядок выката
1. Миграция схемы (новая таблица `AccessKey`) во все активные окружения.
2. apollo-configservice — читает новую таблицу, но она пуста, поведение не меняется.
3. apollo-adminservice + apollo-portal — появляется UI/API управления ключами.

Такой порядок подтверждён аналитиком: к моменту, когда можно завести ключ, проверка в apollo-configservice уже активна — нет окна «ключ есть, но не проверяется».
### 6.2. Обратная совместимость
Приложения без включённых ключей продолжают получать конфигурацию без проверки — старые клиенты не затронуты (FR-2, подтверждено БТ).

### 6.4. План отката (обязательно, если задача деплоится — иначе «не применимо: причина»)
- **Откат только BE** (apollo-configservice на старой версии, apollo-adminservice/apollo-portal уже новые): новая версия сервисов управления ключами не влияет на старую версию apollo-configservice — она не знает о таблице `AccessKey` и продолжает отдавать конфигурацию без проверки всем, как раньше. Допустимо, безопасность временно слабее, но работоспособность не страдает.
- **Откат только FE/управления** (apollo-adminservice/apollo-portal на старой версии, apollo-configservice уже новый): уже созданные ключи продолжают проверяться (данные в БД остаются), но управлять ими (создавать/включать/выключать/удалять) через портал временно нельзя. Допустимо как временная мера.
- **Откат DDL** (удаление таблицы `AccessKey`): выполняется только после отката/отключения новых apollo-configservice/apollo-adminservice/apollo-portal — иначе новый apollo-configservice ожидает таблицу, которой больше нет. Все созданные ключи теряются безвозвратно — ожидаемо, так как функциональность отключается целиком.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1, INT-2 | Дано: администратор открывает управление ключами приложения на окружении. Когда: создаёт ключ и включает его. Тогда: ключ становится активным для проверки запросов этого приложения на этом окружении. |
| FR-2 | INT-4 | Дано: у приложения нет ни одного включённого ключа. Когда: клиент запрашивает конфигурацию приватного namespace. Тогда: конфигурация отдаётся без проверки, как раньше. |
| FR-3 | INT-4 | Дано: у приложения есть включённый ключ. Когда: клиент запрашивает конфигурацию публичного namespace. Тогда: проверка не применяется, конфигурация отдаётся как обычно. |
| FR-4 | INT-4 | Дано: у приложения включён ключ. Когда: клиент присылает неверный или отсутствующий секрет. Тогда: `401 Unauthorized`, конфигурация не отдаётся. |
| FR-5 | INT-4 | Дано: запрос подписан меткой времени старше одной минуты. Когда: сервис проверяет запрос. Тогда: запрос отклоняется; запрос с меткой в пределах минуты проходит, повтор в этом окне не блокируется. |
| — (уточнено в интервью, в FR БТ отдельно не названо) | INT-3 | Дано: администратор хочет вывести ключ из обращения навсегда. Когда: удаляет ключ. Тогда: ключ пропадает из списка управления и перестаёт проходить проверку после обновления кэша конфиг-сервиса. |

## 8. Допущения и открытые вопросы
- **🔵 Подтверждено аналитиком:**
  1. Хранилище ключей — отдельная таблица в ApolloConfigDB окружения, без изменений в таблице App (со слов аналитика).
  2. Роль «администратор приложения» = `Master` или обладатель права `AssignRole` на приложение (по карточке services/apollo-portal.md, подтверждено аналитиком).
  3. Проверка выполняется фильтром в apollo-configservice перед выдачей конфигурации (со слов аналитика).
  4. apollo-adminservice не ведёт собственной авторизации, проверка прав — в apollo-portal (по карточке services/apollo-adminservice.md).
  5. Пути и параметры получения конфигурации (`/configs`, `/configfiles`, `/configfiles/json`) не меняются (со слов аналитика).
- **🟡 К валидации:** нет.
- **❓ Открытые решения:** нет.
- **⚠️ Требует уточнения:** нет.
- **Технические риски:**
  1. Окно до ~1 секунды между изменением статуса ключа и обновлением кэша configservice (задержка опроса) → принятая мера: короткий интервал опроса (1 с), как у остальных кэшей конфиг-сервиса.
  2. Секрет виден в портале только один раз при создании, восстановить потерянный секрет нельзя → принятая мера: при потере администратор создаёт новый ключ и выключает/удаляет скомпрометированный.
