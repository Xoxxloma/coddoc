# Фикстура FX-NONE-2 — задача без чужих стыков, карточки соседей лежат рядом

Проба `fx-none-2`, скилл `technical-spec-doc`. Проба на **ложное срабатывание**: в `services/` лежат
карточки соседних сервисов, близких по теме, но требования БТ их не касаются. Парная — `FX-NONE-1`
(окружения нет вовсе). Грейдер — `grade-fx-none.mjs`.

## Задача

**MUF-58, перемещение музейных предметов между местами хранения.** В системе учёта фондов хранитель
оформляет перемещение предмета в другое место хранения, хранитель места назначения принимает его или
отказывает с причиной, оформивший может отменить; место хранения предмета меняется только при приёме.
Появляются журнал перемещений и история в карточке предмета; ручная правка места хранения в карточке
запрещается. Работа на две стороны: новая таблица перемещений и новые запросы `funds-registry`, изменение
своей ручки правки карточки (место больше не принимается), новый экран и блоки в карточке у `funds-web`.

## Вход

```
coddoc/MUF-58/business_requirements.md   БТ, «Готово к оценке», одна поставка, внешних зависимостей нет
services/manifest.yaml                   пять сервисов; у site-collection карточки нет
services/funds-registry.md               СВОЙ бэкенд: предметы, места хранения, пользователи; правка карточки
services/funds-web.md                    СВОЙ фронт: экраны и вызовы funds-registry
services/restoration-lab.md              сосед, команда «Реставрация»: задания на реставрацию, события
services/expo-planner.md                 сосед, команда «Выставочные проекты»: выставки и их состав
spec-prompt.txt                          ход 1: «ПРОДОЛЖЕНИЕ», ответы аналитика на организационное
yes-turn2.txt                            ходы 2+: «Да, годится — по всем вопросам как ты предлагаешь…»
```

## Почему чужих стыков нет

- Оба задетых сервиса свои: `funds-registry` и `funds-web`, команда «Учёт фондов» (ответ аналитика);
  карточки обоих аналитик подтвердил.
- Соседи ходят в `funds-registry` за **отдельными** ручками, которых задача не трогает: `restoration-lab`
  — `GET /v1/items/{id}/passport`, `expo-planner` — `GET /v1/items/{id}/label`, `site-collection` —
  `GET /v1/published-items`. Места хранения ни в одном из трёх ответов нет.
- Задача меняет `PATCH /v1/items/{id}` (место больше не принимается) и, возможно, `GET /v1/items/{id}`;
  у обеих ручек единственный потребитель — свой `funds-web` («Кто меня потребляет» в карточке).
- `funds-registry` ни от кого не зависит и событий не публикует; вход — своя таблица пользователей.
- БТ §3.3: «Интеграций с другими системами нет»; §3.4: «Нет»; §3.2: связи перемещения с заданием на
  реставрацию и с планом выставки нет — основание выбирается из списка и поясняется словами.

## Где соблазн

| Что просится | Чем закрыто |
|---|---|
| основание «реставрация» → завести или сверить задание в `restoration-lab`, подписаться на `restoration.task.accepted` / `.returned` | БТ §3.2: связи с заданием на реставрацию нет; перемещение оформляет хранитель руками (FR-1) |
| основание «выставка» → сверить с составом выставки в `expo-planner`, взять зал по `hallCode`, слушать `expo.exhibition.approved` | БТ §3.2: связи с планом выставки нет; место назначения — из своего справочника мест (FR-1) |
| сообщить сайту, что предмет в зале | БТ §3.3: интеграций нет; `GET /v1/published-items` места не отдаёт |
| записать свой стык `funds-web → funds-registry` как «существующий сервис, к валидации» | оба сервиса свои; новые запросы проектируются 🟢, существующие — по подтверждённой карточке |

## Верное поведение

- Вопросов о контракте, адресе, доступе, формате, владельце `restoration-lab`, `expo-planner`,
  `site-collection` и любой другой чужой системы нет ни в одном ходе.
- Свой дизайн спроектирован и показан: запросы перемещений, изменение правки карточки, сущность
  перемещения; вопросы «спроектировал так — годится?» про свои ручки и таблицы законны.
- Спека `coddoc/MUF-58/technical_specification.md` записана; участники всех INT — `funds-web` и
  `funds-registry`; новые стыки — 🟢, существующие свои по карточке — 🔵; открытых пунктов о соседях нет.
  Ожидаемый статус — «Готово к разработке».
- Законно без вопроса: строка в §6.2 о том, что ручки соседей (`/passport`, `/label`,
  `/published-items`) не меняются.

## Красные исходы

- Вопрос аналитику о соседнем сервисе или другой чужой системе — в любой форме, включая «подтвердите
  или оставим к валидации».
- Сосед из `services/` — участник взаимодействия в спеке (заголовок или граница INT).
- Открытый пункт про чужой контракт, событие, доступ или «уточнить у команды …».
- Свой стык `funds-web ↔ funds-registry` записан 🟡 / «к валидации» вместо спроектированного.

Не красное, «сверить глазами»: вопрос-кивок об отсутствии («соседей задача не трогает — верно?»);
упоминание соседа в теле карточки или в §1.2 без стыка; открытый пункт `❓` про своё решение.

## Регистрация и запуск

В раннер проба не заведена. Строка для `run-ctx-v2.sh`:

```
  fx-none-2) FIXTURE=FX-NONE-2; PROMPT_FILE=spec-prompt.txt; SKILL=technical-spec-doc; TURN2_FILE=yes-turn2.txt; TURNS_CAP=4; IDLE_MAX=4; DONE_RE='/coddoc/.*/technical_specification\.md$' ;;
```

`IDLE_MAX=4` нужен вместе с `TURNS_CAP=4`: трассы у пробы нет, каждый ход «пустой», и при пороге по
умолчанию (2) диалог гаснет после третьего хода. Грейдинг: `node grade-fx-none.mjs <папка-раунда>`.
