## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В разделе «Склад» веб-интерфейса сервисного центра появляется новая вкладка «На исходе»: кладовщик видит список запчастей с остатком меньше минимального или нулевым — остаток, минимальный остаток, дата последнего пересчёта. Список строится вызовом унаследованной ручки `GET /v1/parts/stock?level=low&level=out` узла-фундамента #0; новых ручек в этой части нет.
**Тип:** доработка
**Стороны:** FE-only — новой работы на бэкенде в этой части нет; `repair-api` отдаёт список через уже реализованную в узле #0 ручку INT-0.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `repair-web` | новая вкладка «На исходе», потребитель INT-0 | команда «Сервис» | 🟢 (новая вкладка) |
| `repair-api` | отдаёт INT-0 (без изменений в этой части) | команда «Сервис» | 🔵 depends-on #0 |

### 1.3. Связь с бизнес-требованиями
Кладовщик (FR-3) узнаёт, каких запчастей мало или нет, раньше, чем за ними придут, — на тех же данных склада, что и остаток в заказе-наряде (PRT-601), через один и тот же унаследованный контракт INT-0. Приоритет и сроки — как в БТ (High, до 2026-12-01).

## 2. Взаимодействия (ядро)

### INT-0. Остатки запчастей (унаследован из узла-фундамента #0) — 🔵 depends-on #0
- **Вид:** потребление существующего
- **Граница/направление:** FE → BE (`repair-web` → `repair-api`)
- **Триггер:** кладовщик открывает вкладку «На исходе» в разделе «Склад», либо нажимает «Обновить»
- **Контракт (запрос):** `GET /v1/parts/stock`; эта часть всегда передаёт `level=low&level=out` (без `partId` — показываются все запчасти с этими уровнями). Параметры и их семантика — как в #0: `partId` string, повторяемый, необязательный; `level` enum `low | out`, повторяемый, необязательный; без параметров — все запчасти склада; неизвестный `partId` в ответ не попадает, ошибки нет.
- **Контракт (ответ):** `items[]`, порядок — по `partName`. Элемент: `partId` string; `partName` string; `shelfQty` int, ≥ 0 — остаток на складе, `0` — валидный ноль; `minQty` int или `null` — минимальный остаток, `null` — минимум не задан; `stockLevel` enum `ok | low | out` (на этом экране в ответе только `low` и `out` — отфильтровано запросом); `recountedAt` строка (дата-время ISO 8601, UTC) или `null` — `null`: остаток ни разу не пересчитывали.
- **Пример запроса:** `GET /v1/parts/stock?level=low&level=out`, тело отсутствует
- **Пример ответа (успех):**
  ```json
  {
    "items": [
      { "partId": "P-1042", "partName": "Ремень привода 6PK", "shelfQty": 1, "minQty": 3, "stockLevel": "low", "recountedAt": "2026-10-20T09:00:00Z" },
      { "partId": "P-2210", "partName": "Термостат ТС-40", "shelfQty": 0, "minQty": 3, "stockLevel": "out", "recountedAt": null }
    ]
  }
  ```
- **Ошибки:** см. «Каталог ошибок» ниже.
- **Состояния UI по ответу:** см. §4.3.
- **Авторизация:** `MASTER` и `STOREKEEPER` допущены на бэке, как в #0; на этом экране фактически вызывает только `STOREKEEPER` — видимость вкладки ограничена на фронте (§4.4).
- **Происхождение:** 🔵 depends-on #0
- **Трассировка:** FR-3

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 `UNKNOWN_LEVEL` | «Неизвестный уровень остатка» | не возникает на этом экране — `level` фиксирован фронтом (`low`, `out`) | — |
| 403 | — | роль не `MASTER` и не `STOREKEEPER`; на этом экране фактически не возникает — вкладка видна только `STOREKEEPER` (§4.4) | `error_forbidden` (не используется в типовом сценарии) |
| 503 `STOCK_UNAVAILABLE` | «Остатки склада недоступны» | база склада не ответила | `error_source` — «Остатки недоступны» |
| — (таймаут клиента) | — | фронт не получил ответ за 5 с | `error_source` — «Остатки недоступны» (см. §4.3.1) |

### 3.2. Данные и хранение

### 3.3. Авторизация/доступ на бэке

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
В разделе «Склад» добавляется новая вкладка «На исходе» (🟢 размещение — последней среди вкладок раздела; при несовпадении с макетом поправить на фронте). Вкладка вызывает INT-0 (🔵 depends-on #0) с фиксированными параметрами `level=low&level=out`.
### 4.2. Пользовательские сценарии
Кладовщик открывает вкладку «На исходе» → список запчастей с `stockLevel ∈ {low, out}`, упорядоченный по `partName` (как отдаёт INT-0). По каждой запчасти: остаток (`shelfQty`), минимальный остаток (`minQty`, прочерк «—» при `null`), дата последнего пересчёта (`recountedAt`, пометка «остаток не пересчитан» при `null`). Кладовщик может нажать «Обновить» для повторного запроса без кэша. [FR-3]
### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | открытие вкладки / клик «Обновить» | спиннер |
| `value` | `items.length > 0` | таблица строк (остаток / минимум / дата пересчёта) |
| `empty` | `items.length === 0` | «Всё в наличии» |
| `error_source` | `503 STOCK_UNAVAILABLE` от `repair-api` либо таймаут запроса (5 с) | «Остатки недоступны» + кнопка «Обновить» |

Внутри `value`: `shelfQty = 0` отображается как «0» (валидный ноль, не «—»); у строки с `recountedAt = null` — отдельная пометка «остаток не пересчитан» рядом с датой (признак строки, а не состояние всего списка).
### 4.3.1. Loading и таймауты (обязательно, если есть FE)
Кэша нет — отдельного warm-path не возникает: каждый запрос (открытие вкладки или клик «Обновить») равнозначен первому. Таймаут — 5 секунд, один и тот же для обоих случаев; по таймауту — состояние `error_source`. Polling нет — обновление только по действию кладовщика (открытие вкладки / клик «Обновить»); кладовщик открывает вкладку несколько раз в день.
### 4.4. Доступ по ролям в UI
Вкладка «На исходе» видна только роли `STOREKEEPER`; роль `MASTER` вкладку не видит (бэк технически пускает к INT-0 обе роли — §3.3, но на этом экране вызывает только `STOREKEEPER`).

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Синхронно, без кэша. Таймаут запроса — 5 секунд (🟢 решение этого экрана; отдельно от серверного SLA INT-0 «ответ до 1 с» в #0). Нагрузка: кладовщик открывает вкладку несколько раз в день; нагрузка на сам INT-0 — как в #0.
### 5.2. Надёжность/деградация
При `503` от `repair-api` либо таймауте запроса (5 с) фронт показывает «Остатки недоступны» (§4.3); ручка только читает — при сбое ничего не записывается (как в #0 §5.2). Повтор — вручную, кнопкой «Обновить».
### 5.3. Безопасность/доступ (сводно)
| Граница | Кто вправе |
|---------|------------|
| INT-0 (бэк) | `MASTER`, `STOREKEEPER` — 🔵 depends-on #0 |
| Вкладка «На исходе» (фронт) | только `STOREKEEPER` |
