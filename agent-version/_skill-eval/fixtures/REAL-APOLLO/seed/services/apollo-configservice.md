# apollo-configservice — backend

> Генерируется. Правки руками затираются.
> Заметки человека — в `services/manifest.yaml`, поле `notes`.
> Форма — `reference/card.template.md` скилла `service-map`. Соседние карточки формой не являются.

## Назначение

Сервис держит настройки приложений в одном месте и раздаёт их уже бегущим инстансам без пересборки и перезапуска: по первому запросу отдаёт актуальную версию конфигурации, а при её изменении обновляет клиентов почти без задержки. Он поддерживает выдачу конфигурации по приложению, кластеру и namespace с учётом публичных (общих для нескольких приложений) namespace и серых релизов — версии конфигурации, нацеленной на часть клиентов по IP; долгий опрос за уведомлением об изменении без постоянного повторного запроса; раздачу той же конфигурации в виде файла `.properties` или JSON; и обнаружение работающих инстансов остальных компонентов Apollo через встроенный сервис-реестр. Главные объекты — релизы конфигурации с их namespace и правилами серой раздачи, а также инстансы приложений, которые эту конфигурацию запрашивают и чьё фактическое применение релиза фиксируется отдельно.

## Что умеет для пользователя
| Возможность | Для кого |
|---|---|
| Получить актуальную конфигурацию по идентификатору приложения, кластеру и namespace — с учётом публичных namespace и серых релизов для конкретного клиента | Приложение-клиент Apollo |
| Получить ту же конфигурацию в виде файла `.properties` или JSON | Приложение-клиент Apollo |
| Узнать об изменении конфигурации без постоянного опроса — один долгий запрос вместо поллинга | Приложение-клиент Apollo |
| Подписаться на изменение сразу нескольких namespace одним запросом — старый способ ограничен одним namespace и оставлен только для совместимости со старыми клиентами | Приложение-клиент Apollo |
| Найти работающие инстансы meta-, config- и admin-сервисов Apollo при старте | Приложение-клиент Apollo / инфраструктура |
| Получать обновления списка namespace (новые, переименованные, удалённые) без перезапуска сервиса | Эксплуатация (косвенно — все клиенты конфигурации) |
| Не терять изменение релиза, даже если push-уведомление о нём не дошло | Приложение-клиент Apollo (через долгий опрос) |
| Зафиксировать, какую версию конфигурации фактически применил конкретный инстанс приложения | Эксплуатация |

## Публичный контракт

### `GET /actuator/health`
Проверка живости сервиса.
- проверяет доступность БД: запрашивает первую страницу (размер 1) из списка приложений

### `GET /configfiles/json/{appId}/{clusterName}/{namespace}`
Та же конфигурация, что и `/configs`, но в виде готового JSON-файла.
сущности: → не сущность, тело — те же пары ключ-значение конфигурации, сериализованные в JSON
- кэшируется под отдельным от `.properties`-варианта ключом (ключ кэша включает формат вывода)
- конфигурация не найдена — пустое тело, код 404

### `GET /configfiles/{appId}/{clusterName}/{namespace}`
Та же конфигурация, что и `/configs`, но в виде файла `.properties`.
сущности: → не сущность, тело — пары ключ-значение конфигурации в формате `.properties`
- при наличии серого правила для клиента локальный кэш не используется вовсе — конфигурация каждый раз загружается заново
- локальный кэш живёт 30 минут, суммарный вес кэша (по длине текста) ограничен 50 МБ
- если серое правило появилось уже в момент загрузки без кэша, результат в кэш не кладётся — защита от «протекания» чужой грей-версии в общий кэш
- кэш точечно инвалидируется по приходу изменения, затрагивающего те же отслеживаемые ключи
- конфигурация не найдена — пустое тело, код 404

### `GET /configs/{appId}/{clusterName}/{namespace}`
Текущая конфигурация приложения в указанном кластере и namespace.
сущности: → не сущность, ответ — appId, кластер, namespace, releaseKey и пары ключ-значение конфигурации
- суффикс `.properties` у имени namespace срезается, а регистр имени нормализуется
- служебный плейсхолдер appId отключает поиск собственного релиза приложения — отдаётся только публичный namespace, если он есть
- публичный namespace подмешивается только тогда, когда запрошенный namespace не принадлежит этому appId; служебный namespace `application` считается принадлежащим любому appId
- поиск релиза идёт по указанному кластеру → по датацентру (если он задан и отличается от кластера) → по кластеру `default`; на каждом шаге сначала проверяется, не настроено ли для клиента серое правило, и только потом берётся последний активный релиз
- при объединении собственный релиз приложения перекрывает значения из публичного namespace
- ни одного релиза не найдено — ответ 404 с текстом, называющим appId, кластер и исходный namespace
- releaseKey, присланный клиентом, совпал с посчитанным на сервере — ответ 304 без тела
- при известном IP клиента каждый отданный релиз асинхронно попадает в аудит инстансов

### `GET /notifications`
Долгий опрос за изменением одного namespace — устаревший способ, оставлен для старых клиентов Apollo.
сущности: → не сущность, ответ — namespace и его новый notificationId
- принимает ровно один namespace за вызов, по умолчанию `application`
- ответ держится не дольше 30 секунд, после чего код 304
- если на момент запроса уже есть более новое изменение по отслеживаемым ключам, ответ приходит немедленно, не дожидаясь долгого опроса

### `GET /notifications/v2`
Долгий опрос за изменением сразу нескольких namespace одним запросом.
сущности: → не сущность, ответ — список записей «namespace и его новый notificationId»
- принимает список namespace одним JSON-параметром; пустой список или неразбираемый JSON — ответ 400
- при несовпадении регистра имени одного и того же namespace в двух записях запроса побеждает запись с меньшим notificationId, а клиенту имя namespace возвращается в том написании, в котором он его прислал
- таймаут долгого опроса настраивается (по умолчанию 60 секунд, допустимый диапазон 1–90 секунд)
- если на одно изменение отвечает больше подписчиков, чем задано порогом (по умолчанию 100), рассылка уходит в отдельный поток с паузой между пачками — чтобы не разослать всем одновременно

### `GET /services/admin`
Список работающих инстансов admin-сервиса Apollo.
сущности: → не сущность, ответ — список записей «имя сервиса, id инстанса, адрес»
- данные берутся из реестра Eureka, отдельного фильтра по appId или IP нет

### `GET /services/config`
Список работающих инстансов самого config-сервиса Apollo.
сущности: → не сущность, ответ — список записей «имя сервиса, id инстанса, адрес»
- принимает параметры appId и ip, но они ни на что не влияют — возвращаются все зарегистрированные инстансы без фильтрации

### `GET /services/meta`
Список работающих инстансов meta-сервиса Apollo.
сущности: → не сущность, ответ — список записей «имя сервиса, id инстанса, адрес»
- данные берутся из реестра Eureka, отдельного фильтра нет

## Фоновые задачи

### `doAudit`
Фиксирует, какую версию конфигурации (releaseKey) фактически получил конкретный инстанс приложения.
- работает непрерывно фоновым потоком, вычитывая внутреннюю очередь аудита (ёмкость 10 000 записей); пустая очередь — пауза в 1 секунду перед следующей попыткой
- очередь переполнена — новая запись аудита молча теряется, вызывающий код это не проверяет и не повторяет попытку
- повторная запись в БД пропускается, если releaseKey для этого инстанса и namespace не изменился и предыдущая запись была не более 10 минут назад
- кэш «инстанс по appId+кластеру+ip+датацентру» живёт 1 час, кэш «последний releaseKey по инстансу и namespace» — 1 сутки; по истечении оба перечитываются из БД заново
- попытка параллельно создать один и тот же инстанс не считается ошибкой — конфликт БД проглатывается, используется уже существующая запись

### `scanNewAppNamespaces`
Подгружает только что созданные namespace приложений, не дожидаясь перезапуска сервиса.
- расписание — опрос БД с настраиваемым интервалом (по умолчанию 1 секунда)
- берёт пачками по 500, упорядоченными по id, и продолжает пока очередная пачка полная
- публичные namespace дополнительно попадают в отдельный кэш «имя → namespace», из которого берётся подмешивание публичной конфигурации в `/configs`

### `scanNewReleaseMessages`
Держит в памяти кэш последних изменений релизов, которым пользуются `/notifications` и ценообразование конфигурации.
- работает как цикл самоопроса с настраиваемым интервалом (по умолчанию 1 секунда) и останавливается сам, как только приходит хотя бы одно push-уведомление об изменении релиза — дальше кэш обновляется только по push
- загружает сообщения пачками по 500, упорядоченными по id
- разрыв больше единицы между последним известным id и id пришедшего уведомления запускает полную перезагрузку с последнего известного id, а не точечное добавление одной записи

### `updateAndDeleteCache`
Перестраивает кэш namespace приложений, подчищая переименованные и удалённые записи.
- расписание — опрос БД с настраиваемым интервалом (по умолчанию 60 секунд)
- перечитывает уже закэшированные id пачками по 500 и обновляет запись только если время последнего изменения в БД новее, чем в кэше
- id, не найденный при перечитывании, считается удалённым и вычищается из обоих кэшей — и по ключу appId+namespace, и по публичному имени
