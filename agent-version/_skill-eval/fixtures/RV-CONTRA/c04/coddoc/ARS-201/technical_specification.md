## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В шапке административной панели «Арсенал» (экран `/admin`) появляется счётчик числа активных пользователей системы. Счётчик обновляется раз в минуту без перезагрузки страницы, показывает «0» как обычное значение и «—», если источник данных недоступен. Виден только администраторам — оператор панель активности не видит вовсе.
**Тип:** доработка
**Стороны:** Fullstack — [существующий FE-экран `/admin` (`arsenal-web`) получает новый элемент шапки; BE-сторона — бэкенд, отдающий число активных пользователей, не подтверждён аналитиком]

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `arsenal-web` | FE: новый элемент шапки, вызывающий счётчик | Арсенал-Core (из БТ §1.3, эксперт для консультаций) | 🟢 изменение существующего (UI) |
| Бэкенд-источник числа активных пользователей | BE: отдаёт счётчик | не подтверждён | 🟡 к валидации |

### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель БТ: дать администратору видимость текущей нагрузки для планирования безопасных окон регламентных работ (FR-1, FR-5, FR-6, FR-7).

## 2. Взаимодействия (ядро)

### INT-1. Счётчик активных пользователей в шапке — 🟡
- **Вид:** потребление существующего (предположительно — БТ §3.3: «данные активности собираются бэком системы «Арсенал» самостоятельно, новых интеграций не требуется»; какой именно сервис и эндпоинт — не подтверждено)
- **Граница/направление:** FE (`arsenal-web`, шапка `/admin`) → BE Арсенала (сервис не подтверждён)
- **Триггер:** открытие `/admin`; далее периодический опрос раз в 60 секунд
- **Контракт (запрос):** 🟡 к валидации — метод, путь и параметры запроса не подтверждены аналитиком, словами не описываются, чтобы не создать мнимый факт
- **Контракт (ответ):** 🟢 требование к контракту (накладывается этой спекой, независимо от того, кто его реализует): ответ должен содержать число активных пользователей (целое, 0 — валидное значение) и однозначный признак «источник недоступен», отличимый от 0. 🟡 Как это устроено у конкретного существующего источника (имена полей, null-семантика) — не подтверждено, к валидации при интеграции.
- **Пример запроса:** 🟡 к валидации — пример не приводится, пока источник не подтверждён (конкретика у 🟡 не допускается)
- **Пример ответа (успех):** 🟡 к валидации — пример не приводится по той же причине
- **Ошибки:** сетевая ошибка/таймаут/5xx → состояние `error_source` на фронте (см. §4.3); коды и тела конкретного источника — 🟡 к валидации

- **Авторизация:** 🔵 подтверждено аналитиком (со слов) — видит только роль Administrator, Operator не видит панель/счётчик вовсе. 🟡 Проверяется ли это также на бэке-источнике (а не только скрытием на фронте) — к валидации.

## 3. Backend — ответственность
### 3.1. По сервисам
Бэкенд-источник (сервис не подтверждён, 🟡) обязан отдавать: число активных пользователей (int, 0 — валидный) и однозначный признак недоступности, отличимый от 0 (🟢 требование этой спеки). Есть ли у источника уже такая возможность и в каком виде — 🟡 к валидации; объём доработки (если нужна) определится после подтверждения источника аналитиком.
### 3.2. Данные и хранение
Новых сущностей нет. По БТ §3.3 данные активности уже собираются бэком Арсенала самостоятельно, новых интеграций не требуется — новых таблиц и миграций в рамках этой задачи не ожидается. Если после подтверждения источника (открытый пункт 1) окажется, что он не даёт нужного признака недоступности — это может потребовать доработки существующей сущности; на данный момент не предрешаем.
### 3.3. Авторизация/доступ на бэке
🔵 подтверждено аналитиком (со слов): видеть счётчик/панель активности может только роль Administrator, Operator — нет. 🟡 Где это физически enforced на бэке-источнике (помимо скрытия элемента на фронте) — не подтверждено, к валидации.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Экран `/admin` (административная панель, существующий), шапка — добавляется элемент-счётчик активных пользователей. Вызывает INT-1.
### 4.2. Пользовательские сценарии
Администратор открывает `/admin` → в шапке отображается число активных пользователей (FR-1). Число обновляется раз в 60 секунд без перезагрузки страницы (FR-1). Если источник недоступен — «—» вместо нуля или устаревшего значения (FR-5). Если активных пользователей нет — отображается «0» как обычное значение (FR-6). Пользователь с ролью Operator не видит панель активности вовсе (FR-7).
### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос после открытия `/admin` | скелетон/спиннер в шапке |
| `value` | ответ получен, источник доступен, count > 0 | число |
| `zero` | ответ получен, источник доступен, count = 0 | «0» |
| ~~`empty`~~ | ~~Не применимо: для этого счётчика нет отдельного «пустого» значения помимо 0 — оно покрыто состоянием `zero`.~~ | ~~—~~ |
| `error_source` | таймаут / 5xx / сетевая ошибка / источник сигналит недоступность | «—» (не ноль, не устаревшее значение) |
| `error_forbidden` | роль Operator | элемент/панель не отображается вовсе (не сообщение об ошибке — скрытие целиком, по FR-7) |

### 4.3.1. Loading и таймауты (обязательно, если есть FE)
- **Таймаут cold-path** (первый запрос после открытия `/admin`) — 8 с (по `context/conventions.md`).
- **Таймаут warm-path** (каждый из периодических опросов) — 3 с (по `context/conventions.md`).
- **Polling:** интервал 60 секунд (подтверждено аналитиком — «чаще не требуется»), без джиттера — нагрузка низкая (десятки администраторов, не тысячи, подтверждено аналитиком).
- При таймауте / 5xx / сетевой ошибке — состояние `error_source` (см. §4.3).
### 4.4. Доступ по ролям в UI
Administrator — видит счётчик. Operator — панель активности (счётчик) не видит вовсе. Подтверждено аналитиком (со слов); согласуется с уже существующей ролевой моделью `arsenal-web` (роли `admin`/`operator`).

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Polling раз в 60 секунд, без кэша — прямой запрос к источнику на каждый тик (🟢). Таймауты: 8 с / 3 с (по конвенции). Ожидаемая нагрузка: десятки администраторов одновременно (подтверждено аналитиком) — не требует отдельных мер по масштабированию.
### 5.2. Надёжность/деградация
При недоступности источника FE показывает «—» и не блокирует остальную работу панели (FR-5). Что остаётся записанным у источника при сбое его собственного сбора данных — 🟡 к валидации, устройство источника не подтверждено.
### 5.3. Безопасность/доступ (сводно)
| Роль | Видит счётчик | Проверка |
|------|---------------|----------|
| Administrator | да | 🔵 подтверждено аналитиком (со слов) — скрытие на фронте |
| Operator | нет (панель активности не отображается) | 🔵 подтверждено аналитиком (со слов) — скрытие на фронте; 🟡 проверка на бэке — к валидации |

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано: `/admin` открыта и загрузилась. Когда: администратор смотрит в шапку. Тогда: отображается текущее число активных пользователей. |
| FR-1 | INT-1 | Дано: число активных пользователей изменилось на источнике. Когда: администратор находится на `/admin` не более 60 секунд. Тогда: счётчик в шапке обновился без перезагрузки страницы. |
