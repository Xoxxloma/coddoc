## 1. Обзор изменения

### 1.1. Что делаем и тип изменения
**Суть:** Сервис раздачи конфигурации (`apollo-configservice`) начинает проверять подпись и метку времени в заголовках запроса к приватным namespace (`/configs`, `/configfiles`, `/configfiles/json`): валидный запрос проходит как раньше, невалидный получает `401`. Портал управления конфигурацией (`apollo-portal`) получает раздел «Ключи приложения» на окружение: администратор приложения заводит, включает, выключает и удаляет ключ через сервис администрирования своего окружения (`apollo-adminservice`). Пока у приложения нет ни одного включённого ключа, поведение не меняется.
**Тип:** доработка
**Стороны:** Fullstack — BE (`apollo-configservice`, `apollo-adminservice`) + FE (раздел в `apollo-portal`)

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| apollo-configservice | проверяет подпись/метку времени перед выдачей конфигурации приватного namespace | не указан в карточке | 🟢 изменение существующего |
| apollo-adminservice | хранит и отдаёт ключи приложения (новая таблица, своя БД на окружение) | не указан в карточке | 🟢 новое |
| apollo-portal | UI создания/включения/выключения/удаления ключа; проксирует в adminservice выбранного окружения | не указан в карточке | 🟢 новое; проксирование — 🔵 подтверждено аналитиком (со слов; согласуется с `services/apollo-portal.md` — «все операции с приложениями... проксируются... по каждому активному окружению») |

### 1.3. Связь с бизнес-требованиями
Реализует цель снижения риска безопасности раздачи конфигурации (БТ §2.2) без дорогого сетевого разделения стендов, часть которых открыта в интернет.

## 2. Взаимодействия (ядро)

### INT-1. Создание ключа приложения — 🟢
- **Вид:** новое
- **Граница/направление:** FE (apollo-portal) → BE (apollo-adminservice выбранного окружения)
- **Триггер:** администратор приложения создаёт ключ на экране «Ключи приложения», выбрав окружение
- **Контракт (запрос):** `POST /apps/{appId}/envs/{env}/access-keys`; поля запроса: `secretKey` (string, обязательно — значение вводит администратор вручную, системой не генерируется)
- **Контракт (ответ):** `id` (long), `appId` (string), `secretKey` (string), `isEnabled` (bool, `false` при создании), `createdBy` (string), `createdTime` (iso8601)
- **Пример запроса:**
  ```json
  { "secretKey": "a1b2c3d4e5f6" }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "id": 101,
    "appId": "orderservice",
    "secretKey": "a1b2c3d4e5f6",
    "isEnabled": false,
    "createdBy": "ivanov",
    "createdTime": "2026-11-01T10:00:00Z"
  }
  ```
- **Ошибки:** см. «Каталог ошибок»
- **Состояния UI по ответу (если есть фронт):** значение → новая строка в списке; ошибка → сообщение формы, значение не очищается
- **Авторизация:** вправе — держатель роли `Master` или права `AssignRole` этого `appId` в портале; иначе — отказ в доступе (§3.3/§4.4)
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

### INT-2. Включение/выключение ключа — 🟢
- **Вид:** новое
- **Граница/направление:** FE (apollo-portal) → BE (apollo-adminservice выбранного окружения)
- **Триггер:** администратор переключает статус ключа в списке

- **Контракт (ответ):** обновлённая запись ключа (поля — как в INT-1)
- **Пример запроса:**

- **Пример ответа (успех):**

    "appId": "orderservice",

    "isEnabled": true,
    "createdBy": "ivanov",

    "lastModifiedBy": "ivanov",

- **Авторизация:** как в INT-1
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

### INT-3. Удаление ключа — 🟢

- **Граница/направление:** FE (apollo-portal) → BE (apollo-adminservice выбранного окружения)
- **Триггер:** администратор удаляет ключ из списка
- **Контракт (запрос):** `DELETE /apps/{appId}/envs/{env}/access-keys/{keyId}`; тело отсутствует
- **Контракт (ответ):** без тела

### INT-4. Список ключей приложения — 🟢
- **Вид:** новое
- **Граница/направление:** FE (apollo-portal) → BE (apollo-adminservice выбранного окружения)
- **Триггер:** открытие экрана «Ключи приложения» на выбранном окружении
- **Контракт (запрос):** `GET /apps/{appId}/envs/{env}/access-keys`; тело отсутствует
- **Контракт (ответ):** список записей — поля как в INT-1 (без `secretKey` в маскированном виде: значение показывается полным, так как его ввёл сам администратор и оно не является системно-генерируемым одноразовым секретом)
- **Пример запроса:** тело отсутствует
- **Пример ответа (успех):**
  ```json
  [
    {
      "id": 101,
      "appId": "orderservice",
      "secretKey": "a1b2c3d4e5f6",
      "isEnabled": true,
      "createdBy": "ivanov",
      "createdTime": "2026-11-01T10:00:00Z"
    }
  ]
  ```
- **Ошибки:** см. «Каталог ошибок»
- **Состояния UI по ответу:** `loaded_empty` → список пуст, показать «ключей нет» + кнопку «Создать»; `loaded` → таблица строк
- **Авторизация:** как в INT-1
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

### INT-5. Проверка ключа при выдаче конфигурации — 🟢 изменение существующего
- **Вид:** изменение существующего
- **Граница/направление:** Приложение-клиент → BE (apollo-configservice)
- **Триггер:** клиент запрашивает конфигурацию приватного namespace
- **Существующий стык:** 🔵 подтверждено аналитиком (по карточке `services/apollo-configservice.md`) — пути `GET /configs/{appId}/{clusterName}/{namespace}`, `GET /configfiles/{appId}/{clusterName}/{namespace}`, `GET /configfiles/json/{appId}/{clusterName}/{namespace}`; сейчас отдают конфигурацию без проверки личности клиента (роль «без входа» видит всё по одному запросу)
- **Изменение:**

  | Поле | Где | Было | Стало |
  |------|-----|------|-------|
  | `Authorization` | заголовок запроса | отсутствовал | новый; обязателен, если у `appId` есть хотя бы один включённый ключ; значение `Apollo <подпись>` |
  | `Timestamp` | заголовок запроса | отсутствовал | новый; обязателен при тех же условиях; epoch-мс |
  | код `401` | ответ | не было (личность не проверялась) | новый — нет/неверна подпись либо `|serverNow − Timestamp| > 60000` мс, при наличии у `appId` ≥1 включённого ключа |

  Подпись: `base64(HMAC-SHA1(secretKey, String(Timestamp)))`. Сервер пробует подписи со всеми текущими включёнными ключами `appId` — совпадение любого достаточно (несколько одновременно включённых ключей — ротация без простоя, по БТ §4.1).
  Если запрошен служебный плейсхолдер `appId` (отдаёт только публичный namespace, см. карточку) — проверка не выполняется: ключ привязан к конкретному `appId`, публичные namespace проверке не подлежат (БТ §4.1).
  Если у `appId` нет ни одного включённого ключа — проверка не выполняется, поведение как раньше (БТ §2.3).

- **Пример запроса:** заголовки `Authorization: Apollo 7mFV2qk4o=`, `Timestamp: 1730455200000`; тело отсутствует (GET)
- **Пример ответа (успех):** без изменений (фрагмент: прочие поля — без изменений, как в карточке: `appId`, кластер, `namespace`, `releaseKey`, пары ключ-значение конфигурации)
- **Пример ответа (отказ):** `401`, пустое тело (как у существующих отказов `/configs*` в этой же карточке — `404` тоже без тела)
- **Ошибки:** `401`, пустое тело — нет/неверна подпись, отсутствует заголовок, либо метка времени вне окна 60 секунд; причина не различается в ответе
- **Состояния UI по ответу (если есть фронт):** не применимо — потребитель этого взаимодействия SDK/приложение-клиент, не экран портала
- **Авторизация:** проверка выполняется до начала формирования ответа конфигурации; негативный случай — `401` без выдачи конфигурации
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-1, FR-2

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 401 | пустое тело | `/configs*`: нет/неверна подпись, отсутствует заголовок, либо метка времени старше 60с — при наличии у appId включённого ключа | не применимо (не FE, см. INT-5) |
| 403 | — (как для прочих административных операций портала) | INT-1..4: у пользователя портала нет права `Master`/`AssignRole` на этот appId | `error_forbidden` |
| 404 | — (как для прочих операций над ключом) | INT-2/INT-3: `keyId` не найден у этого `appId`/окружения | сообщение «ключ не найден» |

## 3. Backend — ответственность

### 3.1. По сервисам
`apollo-configservice`: перед формированием ответа `/configs`, `/configfiles`, `/configfiles/json` проверяет, есть ли у `appId` включённый ключ; если есть — проверяет подпись и метку времени, читая новую таблицу ключей из своей БД окружения без сетевого вызова — 🔵 подтверждено аналитиком со слов («ключи лежат в отдельной таблице в ApolloConfigDB»; согласуется с картой карточки — хранилище через JPA общего модуля). `/notifications`, `/notifications/v2`, `/services/admin|config|meta` не меняются — 🟢 решение по объёму (эти ручки не отдают значений конфигурации, см. §8).
`apollo-adminservice`: хранит и отдаёт CRUD ключей — новая таблица, инстанс окружения, выбранного в портале.
`apollo-portal`: проксирует INT-1..4 в `apollo-adminservice` выбранного окружения — 🔵 подтверждено аналитиком (со слов + по карточке).

### 3.2. Данные и хранение
- 🟢 `ApolloAccessKey` (новая таблица, БД окружения — ApolloConfigDB; у каждого окружения своя БД, поэтому отдельного поля «окружение» у записи нет — окружение определяется физической БД, в которой лежит строка) — поля: `id` (long), `appId` (string), `secretKey` (string), `isEnabled` (bool), `createdBy` (string), `createdTime` (timestamp), `lastModifiedBy` (string), `lastModifiedTime` (timestamp). На одно приложение — несколько строк, у каждой свой `isEnabled` (БТ §4.1, подтверждено аналитиком).

Миграция: да, новая таблица; индекс по `appId` (запросы «включённые ключи appId» и «список ключей appId»). Существующие таблицы (в т.ч. `App`) не меняются — подтверждено аналитиком («в App ничего не добавляем»). Старых строк в новой таблице нет — пересчёт не требуется.

### 3.3. Авторизация/доступ на бэке
`apollo-adminservice` личность пользователя портала не проверяет — проверка выполняется на стороне `apollo-portal` до проксирования, как и для прочих административных операций — 🔵 по карточке (аналогичный паттерн для namespace/ролей). `apollo-configservice` проверяет не пользователя, а подпись секрета — аутентификации личности здесь нет и не требуется по БТ.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Новый раздел «Ключи приложения» на странице приложения в `apollo-portal`, по аналогии с существующими разделами ролей/namespace — список ключей выбранного окружения, действия «Создать», «Включить/выключить», «Удалить». Вызывает INT-1..4.

### 4.2. Пользовательские сценарии
Основной: администратор выбирает окружение → видит список ключей (INT-4) → создаёт ключ, вводя значение (INT-1) → включает его (INT-2). Ветвления: выключает ключ без удаления (временно отключить, не теряя запись); удаляет ключ (INT-3). Отсылка: FR-3.

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loaded_empty` | список ключей окружения пуст | «ключей нет» + кнопка «Создать» |
| `loaded` | ≥1 ключ | таблица строк с переключателем `isEnabled` |
| `error_forbidden` | 403 при попытке управлять | «нет доступа» |
| `error_source` | 5xx / сеть при любом из INT-1..4 | сообщение об ошибке + retry |

### 4.4. Доступ по ролям в UI
Управлять ключами (INT-1..4) может держатель роли `Master` (владелец приложения) либо права `AssignRole` этого `appId` — 🟢 назначено по аналогии с управлением namespace/ролями в `apollo-portal` (аналитик не стал уточнять конкретную роль и предложил решить по карточке). Пользователям без этих прав раздел скрыт — по аналогии с тем, как в карточке портала скрываются элементы при отсутствии доступа.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
Проверка ключа в `apollo-configservice` — синхронная часть обработки запроса `/configs*`. Без TTL-кэша на состояние ключа, либо с кэшом, инвалидируемым синхронно при изменении (как уже сделано для изменения конфигурации в этой же карточке) — чтобы включение/выключение/удаление действовало со следующего запроса клиента, как того требует критерий приёмки FR-3. Ожидаемая нагрузка — на уровне текущей нагрузки `/configs*`, плюс чтение одной-двух строк БД на запрос.

### 5.2. Надёжность/деградация
Чтение таблицы ключей — из той же БД окружения, к которой `/configs*` уже обращается за релизом; отдельной новой точки отказа не добавляется.

### 5.3. Безопасность/доступ (сводно)
| Кто | Что может |
|-----|-----------|
| Приложение-клиент с валидным включённым ключом | получает конфигурацию приватного namespace — как и раньше |
| Приложение-клиент без ключа / с неверным ключом, при наличии включённого ключа у appId | `401`, конфигурация не отдаётся |
| Держатель `Master`/`AssignRole` в портале | создаёт/включает/выключает/удаляет ключи своего приложения |
| Прочие пользователи портала | раздел «Ключи приложения» скрыт |

## 6. Релиз и интеграция

### 6.1. Порядок выката
1. `apollo-adminservice` (хранение, новая таблица) — подтверждено аналитиком.
2. `apollo-portal` (UI создания/включения/выключения/удаления).
3. `apollo-configservice` (включение проверки) — последним: до его выката ключи можно завести и включить, но они не используются, это безвредно; после — поведение меняется только для приложений, у которых уже есть включённый ключ.

### 6.2. Обратная совместимость
Приложения без включённого ключа — поведение `/configs*` не меняется (БТ §2.3, риск-мера принята в БТ).

### 6.4. План отката
- **Откат только BE (apollo-configservice):** на старой версии проверка не выполняется — поведение как до задачи, не опасно; ключи, уже заведённые через портал, просто не используются до повторного выката.
- **Откат только FE/adminservice (apollo-portal, apollo-adminservice):** если `apollo-configservice` с проверкой уже выкачен, а хранение ключей откатывается — у уже созданных и включённых ключей данные теряются вместе с таблицей (см. план отката DDL) — чтобы не потерять доступ клиентов, откат adminservice раньше отката configservice не делать.
- **Откат DDL:** новая изолированная таблица `ApolloAccessKey`, других сущностей не меняет; down-миграция — удаление таблицы, данные о ключах (но не о конфигурации) теряются безвозвратно.

### 6.5. Преднастройка до релиза

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-5 | Дано валидный включённый ключ приложения и метка времени не старше минуты, когда клиент запрашивает конфигурацию приватного namespace, тогда конфигурация отдаётся как раньше |
| FR-2 | INT-5 | Дано неверный/невключённый ключ или метка времени старше минуты, когда клиент запрашивает конфигурацию приватного namespace, тогда ответ `401` без конфигурации |
| FR-3 | INT-1, INT-2, INT-3, INT-4 | Дано администратор на выбранном окружении, когда создаёт/включает/выключает/удаляет ключ, тогда список и проверка на `apollo-configservice` отражают это со следующего обращения клиента |
