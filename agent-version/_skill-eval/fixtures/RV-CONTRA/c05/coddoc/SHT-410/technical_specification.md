## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В карточке рейса появится отметка, есть ли место для велосипеда. Список рейсов станет показывать сначала рейсы от офиса сотрудника. Запись на рейс начнёт проходить только при активном пропуске — для этого shuttle-api будет обращаться к службе пропусков (badge-service) и к справочнику сотрудников (org-directory).
**Тип:** доработка
**Стороны:** Fullstack — меняются shuttle-api (BE) и shuttle-web (FE); добавляются вызовы в два чужих сервиса.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| shuttle-api | изменение: badge-check при записи, bikeRack в карточке рейса, вызов в org-directory, employeeOfficeCode в списке рейсов | команда «Шаттл» | 🟢 изменение существующего |
| shuttle-web | изменение: отметка велосипеда, сортировка по офису, новые состояния ошибки записи | команда «Шаттл» | 🟢 изменение существующего |
| badge-service | потребитель — новый вызов | команда «Безопасность зданий» | 🟡 к валидации |
| org-directory | потребитель — новый вызов | команда «Кадровые системы» | 🟡 к валидации |
### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель БТ: сотрудник не теряет место из-за заблокированного пропуска (FR-1), заранее знает про велосипед (FR-2) и видит свои рейсы первыми (FR-3).

## 3. Backend — ответственность
### 3.1. По сервисам
- **shuttle-api**: реализует проверку пропуска перед записью (INT-1, INT-2 — новые коды ошибок, 🟢); добавляет `bikeRack` в карточку рейса (INT-3, 🟢); запрашивает офис сотрудника в org-directory и добавляет `employeeOfficeCode` в ответ списка (INT-4, INT-5, 🟢/🟡).
- **shuttle-web**: показывает отметку велосипеда (INT-3), сортирует список по `employeeOfficeCode` (INT-5), показывает новые состояния ошибки записи (INT-2).
- **badge-service, org-directory**: работ на их стороне задача не предполагает — только потребляются. Не применимо: эти сервисы задача не меняет.
### 3.2. Данные и хранение
- 🟢 `Trip.bikeRack: boolean, NOT NULL, default false` — новое поле у существующей сущности `Trip` (владелец — shuttle-api). Миграция: добавить колонку с default `false`; у уже лежащих рейсов `false` (подтверждено аналитиком явно). Точный DDL финализирует shuttle-api.
- Заполнение `bikeRack`: транспортная служба один раз отмечает его скриптом при выкате, дальше — через поддержку; экран для этого не нужен (подтверждено аналитиком).
- `employeeOfficeCode` не хранится в shuttle-api — вычисляется на каждый запрос списка обращением в org-directory (без кэша, 🟢 дизайн).
- Новых сущностей, кроме `Trip.bikeRack`, нет.
### 3.3. Авторизация/доступ на бэке
- Доступ к данным рейсов и записи — без изменений, роль `EMPLOYEE` (как в БТ).
- 🟡 К валидации: как shuttle-api авторизуется при вызовах в badge-service и org-directory — не определено; аналитик подтвердил, что доступ заводится заявкой до релиза (см. §6.5).

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
- Карточка рейса (`/trips/:tripId`) — отметка «можно с велосипедом» по `bikeRack` (INT-3).
- Список рейсов (`/trips`) — сортировка по `employeeOfficeCode`/`officeCode` (INT-5).
- Запись на рейс — новые состояния ошибки (INT-2).
### 4.2. Пользовательские сценарии
- Основной: сотрудник открывает список → видит сначала рейсы своего офиса → открывает карточку → видит, есть ли место для велосипеда → нажимает «Записаться» → пропуск активен → запись проходит (FR-1, FR-2, FR-3).
- Ветвление: пропуск заблокирован/истёк → запись не проходит, сотрудник видит причину (FR-1).
- Ветвление: badge-service недоступен → сотрудник видит «не удалось проверить пропуск, попробуйте позже», может повторить (FR-1, бизнес-риск §2.3 БТ).
- Ветвление: org-directory недоступен → список рейсов открывается в общем порядке, без сообщения об ошибке (FR-3).
### 4.3. Состояния
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `value` (список) | список получен, `employeeOfficeCode` известен | рейсы своего офиса — первыми |
| `value_unsorted` (список) | список получен, `employeeOfficeCode === null` | рейсы в общем порядке, как сейчас |
| `error_badge_blocked` (запись) | ответ `403 badge_blocked` | «пропуск заблокирован» |
| `error_badge_expired` (запись) | ответ `403 badge_expired` | «пропуск истёк» |
| `error_badge_unavailable` (запись) | ответ `503 badge_check_unavailable` | «не удалось проверить пропуск, попробуйте позже» + повтор |

`bikeRack` — обычное булево поле карточки рейса, не отдельное состояние (`zero`/`empty` к boolean не применимы).
### 4.3.1. Loading и таймауты
Polling не используется — задача не вводит обновление в реальном времени. 🟢 Таймаут вызова shuttle-api → badge-service и shuttle-api → org-directory — 3 секунды (наш дизайн интеграции); истечение таймаута трактуется как недоступность (см. «Каталог ошибок» и §5.2). Отдельных cold/warm значений не вводим — вызовы одноразовые, не повторяющиеся в рамках одного открытия экрана.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- Проверка пропуска — синхронно, на каждую запись, без кэша (подтверждено аналитиком явно).
- Получение офиса сотрудника — синхронно, на каждое открытие списка рейсов, без кэша (🟢 дизайн — других указаний нет).
- Нагрузка: ~1500 сотрудников, до 300 записей в день, пик 7:00–9:00 (подтверждено аналитиком).
### 5.2. Надёжность/деградация
- Запись пишет у нас (бронирование места) и вызывает badge-service: если вызов не удался — запись **не создаётся**, место не занимается и не теряется (подтверждено аналитиком).
- Список рейсов вызывает org-directory: если вызов не удался — список всё равно отдаётся, в общем порядке, без ошибки (подтверждено аналитиком).
### 5.3. Безопасность/доступ (сводно)
| Кто | Что может |
|---|---|
| `EMPLOYEE` | видит рейсы, видит `bikeRack`, видит свой офис первым в списке, записывается на рейс при активном пропуске |
| сервисный аккаунт shuttle-api → badge-service | 🟡 к валидации, заводится заявкой до релиза |
| сервисный аккаунт shuttle-api → org-directory | 🟡 к валидации, заводится заявкой до релиза |

## 6. Релиз и интеграция
### 6.1. Порядок выката
shuttle-api (BE) — раньше shuttle-web (FE); фиче-флага нет (подтверждено аналитиком). Клиент один — веб, мобильного нет.
### 6.2. Обратная совместимость
Все изменения ответов — аддитивные (`bikeRack`, `employeeOfficeCode`, новые коды ошибок записи), существующие поля и успешный путь записи не меняются.

### 6.4. План отката
- **Откат только BE** (FE новый, BE старый): ответы не содержат `bikeRack`/`employeeOfficeCode` → FE трактует отсутствующее `bikeRack` как `false`, отсутствующий `employeeOfficeCode` как `null` (общий порядок); запись проходит без проверки пропуска — как «сейчас», допустимо на время откатa.
- **Откат только FE** (BE новый, FE старый): старый FE не показывает `bikeRack`/сортировку — не критично; при ошибке проверки пропуска старый FE покажет общую ошибку запроса (не специальное сообщение) — функциональность записи не ломается.
- **Откат DDL** (`bikeRack`): down-миграция убирает колонку; данные не критичны (признак восстанавливается скриптом/поддержкой повторно).
