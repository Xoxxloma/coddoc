## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В карточке инцидента появляется журнал уведомлений СЦБ о его закрытии. При переводе инцидента в статус «закрыт» сервис пультовой службы сам отправляет уведомление во внешнюю систему СЦБ (с автоматическими повторами при неуспехе) и ведёт журнал попыток; диспетчер пультовой службы открывает карточку и видит состояние передачи, время последней попытки и исход — без звонка смежникам.
**Тип:** доработка
**Стороны:** Fullstack — новый исходящий вызов BE→СЦБ, новая сущность и эндпоинт на BE, новый блок UI на FE.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Сервис пультовой службы | расширяется: сущность журнала, исходящая интеграция с СЦБ, новый эндпоинт для фронта карточки инцидента | пультовая служба (наша команда) | 🔵 подтверждено аналитиком (со слов) |
| Шлюз СЦБ (внешняя система смежной службы) | принимает исходящее уведомление о закрытии инцидента | смежная служба / их интегратор | 🟡 к валидации |
### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель БТ: диспетчер уверен, что закрытие инцидента ушло в СЦБ, и видит подтверждение передачи, не звоня смежникам и не разбирая спорные случаи по записям разговоров (FR-1–FR-4).

### INT-2. Журнал уведомлений СЦБ по инциденту — 🟢
- **Вид:** новое
- **Граница/направление:** FE (карточка инцидента) → BE (сервис пультовой службы)
- **Триггер:** диспетчер открывает/обновляет карточку закрытого инцидента
- **Контракт (запрос):** `GET /v1/incidents/{incidentId}/scb-notifications`; параметры пути: `incidentId` (string, обязательный, идентификатор существующего инцидента)
- **Контракт (ответ):** `incidentId` (string); `currentState` (enum: `pending` — ожидает успешной доставки или повтора, `sent` — доставлено, `failed` — повторы исчерпаны без успеха); `notifications` (массив записей попыток, может быть пустым, если инцидент ещё не закрывался): каждая запись — `id` (string), `attemptAt` (iso8601, UTC, момент попытки), `outcome` (enum: `sent` | `failed`), `errorReason` (enum: `timeout` | `network_error` | `rejected_by_scb` | `unknown`, `null` когда `outcome=sent`)
- **Пример запроса:**
  ```
  GET /v1/incidents/INC-10294/scb-notifications
  ```
  тело отсутствует
- **Пример ответа (успех):**
  ```json
  {
    "incidentId": "INC-10294",
    "currentState": "failed",
    "notifications": [
      { "id": "ntf-1", "attemptAt": "2026-11-01T09:12:00Z", "outcome": "failed", "errorReason": "timeout" },
      { "id": "ntf-2", "attemptAt": "2026-11-01T09:17:00Z", "outcome": "failed", "errorReason": "timeout" }
    ]
  }
  ```
- **Ошибки:** см. «Каталог ошибок» ниже.
- **Состояния UI по ответу:** `value` — `notifications` непустой → список с временем и исходом; `empty` — `notifications: []` (инцидент ещё не закрывался) → «—»; `error_source` — 5xx/таймаут/сеть; `error_forbidden` — 403.
- **Авторизация:** роль «диспетчер пультовой службы» (FR-4); любая другая роль — 403, тело не раскрывает, что скрыто (конвенция `context/conventions.md` §2).
- **Происхождение:** 🟢 новое.
- **Трассировка:** FR-2, FR-4.

## 3. Backend — ответственность
### 3.1. По сервисам
Сервис пультовой службы:
- при переводе инцидента в «закрыт» синхронно выполняет первую попытку отправки в СЦБ (таймаут 8 с — конвенция `context/conventions.md`), результат (успех/неуспех) пишет записью журнала (🟢);
- при неуспехе первой попытки ставит фоновый повтор (🔵 подтверждено аналитиком — со слов: «повторную отправку делаем фоном на нашей стороне»): до 4 дополнительных попыток с интервалами 1 мин / 5 мин / 15 мин / 60 мин от предыдущей, таймаут каждой попытки — 3 с (конвенция); после 5-й неуспешной попытки запись журнала фиксируется с исходом `failed`, `currentState` инцидента становится `failed`, дальнейшие автоматические повторы не выполняются (🟢);
- на каждой попытке, включая повторы, передаёт один и тот же стабильный идентификатор события (производный от `incidentId`), чтобы повтор не создавал второго уведомления у смежников (FR-3) — 🟢 с нашей стороны; подтверждение, что СЦБ действительно дедуплицирует по этому идентификатору, — часть открытого пункта №1 (🟡);
- отдаёт журнал по INT-2 с проверкой роли.
### 3.2. Данные и хранение
- 🔵 (подтверждено аналитиком, со слов) `Инцидент` — существующая сущность сервиса пультовой службы; поля не меняются, добавляется связь 1→N с записями журнала.
- 🟢 `Запись журнала уведомлений СЦБ` — новая сущность: `id`, `incidentId` (ссылка на инцидент), `attemptAt` (iso8601, UTC), `outcome` (enum `sent`|`failed`), `errorReason` (enum `timeout`|`network_error`|`rejected_by_scb`|`unknown`, `null` при `outcome=sent`), `attemptNumber` (int, порядковый номер попытки по инциденту).

Миграции: да — новая таблица/структура в сервисе пультовой службы (точный DDL — на стороне владеющего сервиса, он же наш); старых строк нет, пересчёт не требуется.
Индекс: по `incidentId` (типовой запрос журнала по инциденту).
Хранение/срок жизни: вместе с инцидентом, отдельного срока не вводим (🔵 подтверждено аналитиком, со слов).
### 3.3. Авторизация/доступ на бэке
Эндпоинт журнала (INT-2) проверяет роль вызывающего: «диспетчер пультовой службы» — разрешено; любая другая роль (включая «руководитель смены» из §1.2/§5.3 БТ) — отказ 403 (🔵 подтверждено аналитиком, со слов: «роль, которой доступен журнал, — диспетчер пультовой службы; отказ остальным — по общим правилам»). Это сужает круг явно перечисленных в БТ §1.2/§5.3 потребителей журнала до одной роли — аналитик подтвердил это явно в этом интервью, расхождение с §1.2/§5.3 БТ называем здесь.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
В карточке инцидента — новый блок «Журнал уведомлений СЦБ»; вызывает INT-2 при открытии/обновлении карточки.
### 4.2. Пользовательские сценарии
Диспетчер открывает закрытый инцидент → видит блок журнала с текущим состоянием передачи и списком попыток (время, исход). При неуспехе и последующих фоновых повторах при следующем открытии карточки видит обновлённый журнал (FR-2, FR-3).
### 4.3. Состояния
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос журнала | спиннер/скелетон |
| `value` | 2xx, `notifications` непустой | список записей: время + исход |
| `empty` | 2xx, `notifications: []` | «—» |
| `error_source` | 5xx / таймаут / сеть | сообщение об ошибке + retry |
| `error_forbidden` | 403 | «нет доступа» |

Отдельно отображается `currentState` бейджем: `pending` → «отправляется», `sent` → «доставлено», `failed` → «не доставлено».
### 4.3.1. Loading и таймауты
Запрос журнала — холодный путь (первое открытие карточки) — таймаут 8 с; повторное открытие/обновление — тёплый путь — 3 с (конвенция `context/conventions.md`). Поллинг не применяется: журнал не требует автообновления без действия пользователя — диспетчер обновляет карточку сам.
### 4.4. Доступ по ролям в UI
Блок журнала виден только роли «диспетчер пультовой службы»; для прочих ролей (в том числе «руководитель смены») блок не отображается / запрос к INT-2 вернёт 403 — см. §3.3.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Первая попытка отправки в СЦБ — синхронно при закрытии инцидента (таймаут 8 с); повторы — фон (до 4 шт., интервалы 1/5/15/60 мин, таймаут 3 с каждая) — 🔵 «фон» подтверждено аналитиком, конкретные числа повторов — 🟢-дизайн. Кэш не требуется (журнал читается по запросу, объём мал). Нагрузка: закрытий по смене — десятки, не тысячи (🔵 подтверждено аналитиком, со слов) — особых мер масштабирования не требуется.
### 5.2. Надёжность/деградация
Недоступность/ошибка/таймаут шлюза СЦБ не блокирует и не откатывает закрытие инцидента: закрытие — локальное действие сервиса пультовой службы, отправка в СЦБ — побочный эффект с повтором. При сбое в журнале фиксируется запись `failed` с причиной; после исчерпания повторов `currentState=failed` — диспетчер видит это и может прибегнуть к прежнему процессу (звонок) как и раньше в редких случаях окончательного отказа.
### 5.3. Безопасность/доступ (сводно)
| Роль | Журнал (INT-2) |
|---|---|
| Диспетчер пультовой службы | разрешено |
| Руководитель смены | 403 |
| Любая другая роль | 403 |

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано инцидент в статусе «открыт», когда диспетчер закрывает его, тогда в журнале появляется запись о попытке отправки в СЦБ |
| FR-2 | INT-2 | Дано закрытый инцидент с ≥1 попыткой отправки, когда диспетчер открывает карточку, тогда видит записи журнала с временем и исходом |
| FR-3 | INT-1 (повтор) | Дано первая попытка завершилась неуспехом, когда срабатывает фоновый повтор, тогда в журнале появляется вторая запись, а в СЦБ уходит уведомление с тем же идентификатором события |
| FR-4 | INT-2 | Дано пользователь с ролью, отличной от «диспетчер пультовой службы», когда он запрашивает журнал, тогда получает 403 |
