## 1. Введение и контекст

### 1.0. Тип изменения
Доработка существующего: сервис раздачи конфигурации получает проверку легитимности клиента, портал управления конфигурацией получает управление ключами приложения.

### 1.1. Описание проблемы
Клиенту для получения конфигурации сейчас достаточно адреса сервиса и appId — отличить настоящего клиента от поддельного нечем.

### 1.2. Конечные потребители
Приложения-клиенты, которые легитимно обращаются за своей конфигурацией.

### 2.2. Ценность для бизнеса
Снижение риска безопасности. Для компаний с требованиями безопасности отсутствие проверки клиента может быть блокером при выборе конфигурационного центра. В одном центре живут разные приложения и команды, которые не должны видеть чужие чувствительные настройки. Часть тестовых стендов открыта в интернет ради удобства, а при гибридном облаке связывать сети дорого — проверка клиента закрывает этот риск без дорогого сетевого разделения.

### 2.3. Бизнес-риски и меры по снижению
| Риск | Вероятность / влияние | Меры по снижению |
|------|-----------------------|------------------|
| Действующие клиенты без ключа после обновления перестанут получать конфигурацию | — | Проверка включается автоматически только когда у приложения есть хотя бы один включённый ключ; если ключа нет, запрос проходит как раньше |

Других рисков пользователь не назвал.

## 3. Объём проекта

### 3.1. Входит в проект
- Проверка легитимности клиента при обращении за конфигурацией приватного namespace приложения.
- Управление ключами приложения (создание, включение, выключение) в портале, по окружениям.

### 3.2. Не входит в проект
- Публичные namespace — проверки не касаются.
- Отдельный ключ на уровень namespace — достаточно уровня приложения.
- Защита от повторного использования валидного запроса в пределах окна действия метки времени (одноразовые запросы) — осознанно не делается, признано слишком трудоёмким.

### 3.3. Архитектурные изменения и интеграции
Затрагиваются сервис раздачи конфигурации (проверка ключа перед выдачей) и портал управления конфигурацией (создание и включение/выключение ключей администратором приложения). Новых внешних интеграций пользователь не назвал.

## 4. Функциональные требования

### 4.1. Описание функционала / бизнес-процесса
Разработчик приложения прописывает секрет (ключ) у себя в приложении. Администратор приложения заводит и включает ключ в портале, на окружение; ключей может быть несколько одновременно включённых — это позволяет сменить ключ без простоя. Автоматического срока действия у ключа нет, включают и выключают его вручную.

При обращении клиента за конфигурацией приватного namespace сервис проверяет переданный ключ: если ключ верный и включён, а метка времени запроса не старше минуты — конфигурация отдаётся, как и раньше; если ключ неверный, не включён, или метка времени запроса устарела — конфигурация не отдаётся. Публичные namespace проверке не подвергаются.

⚠️ Применимость проверки к выгрузке конфигурации файлом, к долгому опросу за уведомлением об изменении namespace и к обнаружению работающих инстансов Apollo — не обсуждалась, уточнить.

- **FR-1.** Легитимный клиент с валидным включённым ключом получает конфигурацию приватного namespace, как и раньше.
- **FR-2.** Нелегальный клиент (неверный/невключённый ключ или устаревшая метка времени запроса) не получает конфигурацию приватного namespace.
- **FR-3.** Администратор приложения создаёт, включает и выключает ключи приложения в портале, по окружениям; несколько ключей могут быть включены одновременно.

### 4.2. Критерии приёмки
- **FR-1** Дано клиент передал верный включённый ключ приложения, и метка времени запроса не старше минуты, когда клиент запрашивает конфигурацию приватного namespace, тогда сервис отдаёт конфигурацию, как и раньше.
- **FR-2** Дано клиент передал неверный или невключённый ключ, когда клиент запрашивает конфигурацию приватного namespace, тогда сервис отвечает 401 Unauthorized и конфигурацию не отдаёт. Дано клиент повторяет ранее верный запрос с меткой времени старше минуты, когда он обращается за конфигурацией, тогда сервис отказывает в выдаче.
- **FR-3** Дано у приложения есть ключ, заведённый в портале, когда администратор приложения включает или выключает этот ключ на нужном окружении, тогда состояние ключа меняется и начинает (или перестаёт) учитываться проверкой при следующем обращении клиента.

### 4.3. Бизнес-данные
Доработка:

| № | Объект | Что это | Что меняется |
|---|--------|---------|--------------|
| 1 | Ключ (секрет) приложения | Значение, которым клиент подтверждает свою легитимность при запросе конфигурации; выдаётся на окружение, может быть несколько одновременно включённых, включается и выключается администратором вручную, автоматического срока действия нет | Новый объект |
| 2 | Конфигурация приложения | Настройки приложения по приватным namespace, которые запрашивает клиент | Состав данных не меняется — меняется то, что доступ к приватным namespace теперь проверяется |

### 4.5. Разбиение на части
Не применимо: управление ключами в портале и проверка ключа при выдаче конфигурации — звенья одного потока. Ключи без проверки на стороне сервиса раздачи конфигурации ничего не защищают; проверка без возможности завести и включить ключ в портале не может быть включена. Ни одна часть не даёт бизнесу защиты сама по себе, пока не выпущена вторая.

|------|----------------------------|
| Разработчик приложения | Прописывает секрет (ключ) в своём приложении, чтобы оно могло подтвердить легитимность при запросе конфигурации |
