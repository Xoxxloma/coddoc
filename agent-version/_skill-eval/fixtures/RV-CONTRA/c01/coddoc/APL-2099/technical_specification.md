## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** Сервис раздачи конфигурации Apollo (`apollo-configservice`) начинает проверять подпись и метку времени клиента перед отдачей конфигурации приватного namespace. Ключ приложения — новый объект, хранится в собственной базе `apollo-configservice` (`ApolloConfigDB`) по окружениям. Администратор приложения заводит, включает, выключает и удаляет ключи через портал (`apollo-portal`), который для этого напрямую зовёт новые ручки `apollo-configservice` выбранного окружения. Пока у приложения нет ни одного включённого ключа, раздача конфигурации не меняется.
**Тип:** доработка — так назван документ сверху (БТ §1.0: «Доработка существующего»)
**Стороны:** Fullstack — новый серверный контракт на `apollo-configservice` (проверка + CRUD ключей) и новое использование этого контракта в UI `apollo-portal`

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| apollo-configservice | новая логика проверки подписи + новое хранилище ключей + новые CRUD-ручки | ❓ TBD (отложено аналитиком) | 🟢 |
| apollo-portal | потребитель нового CRUD API (экран управления ключами) | ❓ TBD (отложено аналитиком) | 🟢 |
| apollo-adminservice | не затронут — ключи не входят в модель `App` этого сервиса | ❓ TBD (отложено аналитиком) | 🔵 подтверждено аналитиком (со слов; валидировать при интеграции) |

### 1.3. Связь с бизнес-требованиями
Закрывает риск из БТ §2.2: конфигурационный центр сейчас отдаёт чувствительные настройки любому, кто знает appId, без проверки личности клиента — это блокер для компаний с требованиями безопасности и для стендов, открытых в интернет.

## 2. Взаимодействия (ядро)

### INT-1. Проверка подписи клиента при выдаче конфигурации — 🟢
- **Вид:** изменение существующего
- **Граница/направление:** Приложение-клиент → `apollo-configservice`
- **Триггер:** запрос конфигурации приватного namespace
- **Существующий стык:** 🔵 подтверждено аналитиком (по карточке `services/apollo-configservice.md`; валидировать при интеграции) — три ручки: `GET /configs/{appId}/{clusterName}/{namespace}`, `GET /configfiles/{appId}/{clusterName}/{namespace}`, `GET /configfiles/json/{appId}/{clusterName}/{namespace}`; сейчас роль «без входа» — личность вызывающего не проверяется ни одной из них
- **Изменение:**
  | поле | где | было | стало |
  |---|---|---|---|
  | заголовок `Authorization` | запрос (все три ручки, только для приватного namespace) | отсутствовал | `Apollo <appId>:<подпись>`, обязателен |
  | заголовок `Timestamp` | запрос (все три ручки, только для приватного namespace) | отсутствовал | unix-время в мс, обязателен |
  | код `401` | ответ (все три ручки) | не возвращался | возвращается при неверной/отсутствующей подписи или просроченной метке времени |
- **Контракт (запрос):** заголовки `Authorization: Apollo <appId>:<подпись>`, `Timestamp: <unix-время, мс>`; подпись = `HMAC-SHA256(Timestamp + путь запроса, значение ключа)`, результат в Base64. Пути и параметры ручек не меняются. Проверка применяется только когда у `appId` есть хотя бы один включённый ключ (БТ §2.3) — иначе запрос обслуживается как раньше, без заголовков.
- **Контракт (ответ):** тело успешного ответа не меняется (контракт ручки как был). При отказе — код `401`, тело отсутствует (как у текущих `404` этого сервиса).
- **Пример запроса:**
  ```
  GET /configs/app123/default/application
  Authorization: Apollo app123:7wC1n2k9b3f7d4f0a6c5e8b1a2d3f4e5c6b7a8d9e0f1a2b3c4d5e6f7a8b9c0d1e
  Timestamp: 1730457600000
  ```
- **Пример ответа (ошибка, фрагмент — остальное как в текущем контракте ручки):**
  ```
  HTTP/1.1 401 Unauthorized
  (тело отсутствует)
  ```
- **Ошибки:** `401` — ключ не найден среди включённых ключей `appId`, подпись не совпала, либо `now_ms − Timestamp > 60000`. См. «Каталог ошибок».
- **Состояния UI по ответу:** ~~Не применимо: граница без пользовательского интерфейса — клиент — SDK/приложение, не экран.~~
- **Авторизация:** любой клиент с верной подписью по действующему включённому ключу приложения; публичные namespace проверке не подвергаются (БТ §3.1).
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-1, FR-2

### INT-2. Управление ключами приложения — 🟢
- **Вид:** новое
- **Граница/направление:** `apollo-portal` (UI) → `apollo-configservice` (новые ручки)
- **Триггер:** администратор приложения в портале выбирает окружение и создаёт / включает / выключает / удаляет ключ
- **Контракт (запрос):**
  - `POST /apps/{appId}/keys` — тело отсутствует; создаёт ключ в выключенном состоянии
  - `POST /apps/{appId}/keys/{keyId}/enable` — тело отсутствует
  - `POST /apps/{appId}/keys/{keyId}/disable` — тело отсутствует
  - `DELETE /apps/{appId}/keys/{keyId}` — тело отсутствует
  - `GET /apps/{appId}/keys` — тело отсутствует
- **Контракт (ответ):** `id` (long), `appId` (string), `value` (string, секрет; возвращается только в ответе на `POST .../keys`, в остальных ответах отсутствует), `enabled` (bool), `createdAt` (iso8601), `createdBy` (string)
- **Пример запроса:** тело отсутствует (см. выше)
- **Пример ответа (успех, `POST /apps/app123/keys`):**
  ```json
  {
    "id": 17,
    "appId": "app123",
    "value": "7wC1n2k9b3f7d4f0a6c5e8b1a2d3f4e5c6b7a8d9e0f1a2b3c4d5e6f7a8b9c0d1e",
    "enabled": false,
    "createdAt": "2026-11-01T12:00:00Z",
    "createdBy": "ivan.petrov"
  }
  ```
- **Пример ответа (успех, `GET /apps/app123/keys` — без `value`):**
  ```json
  [
    { "id": 17, "appId": "app123", "enabled": false, "createdAt": "2026-11-01T12:00:00Z", "createdBy": "ivan.petrov" },
    { "id": 12, "appId": "app123", "enabled": true, "createdAt": "2026-10-20T09:30:00Z", "createdBy": "ivan.petrov" }
  ]
  ```
- **Ошибки:** `403` — нет права `AssignRole`/`Master` на приложение; `404` — `appId`/`keyId` не найден. См. «Каталог ошибок».
- **Состояния UI по ответу:** значение → список ключей с их `enabled`; загрузка → спиннер; пусто → «ключей пока нет»; ошибка → `error_source`/`error_forbidden` (см. §4.3).
- **Авторизация:** право `AssignRole` или `Master` на приложение — 🔵 подтверждено аналитиком (со слов; валидировать при интеграции); проверяется в портале до вызова `apollo-configservice`, тот же паттерн, что сейчас у вызовов портала в `apollo-adminservice` (карточка `services/apollo-adminservice.md`: «проверка прав выполняется до вызова, в apollo-portal»).
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

## 3. Backend — ответственность
### 3.1. По сервисам
`apollo-configservice` — реализует INT-1 (фильтр проверки подписи перед выдачей трёх перечисленных ручек) и INT-2 (CRUD ключей, новое хранилище) — оба 🟢.
`apollo-portal` — только вызывающая сторона INT-2 (новый исходящий вызов из UI); собственный контракт портала не меняется.
`apollo-adminservice` — не затронут — 🔵 подтверждено аналитиком (со слов; валидировать при интеграции).

### 3.2. Данные и хранение
- 🟢 `ApplicationKey` (новая таблица в `ApolloConfigDB`, база `apollo-configservice`, своя на каждое окружение) — `id` (long), `appId` (string), `value` (string — секрет в открытом виде, нужен сервису для вычисления HMAC при проверке), `enabled` (bool), `createdAt` (timestamp), `createdBy` (string). Индекс по `appId` — под фильтр включённых ключей на каждый запрос конфигурации. Миграция: новая таблица, старых строк нет, пересчитывать нечего.
- 🔵 `App` (`apollo-adminservice`) — не меняется, ключ туда не добавляется (со слов аналитика; валидировать при интеграции).

Новых изменений в уже существующих таблицах нет.

### 3.3. Авторизация/доступ на бэке
INT-1: симметричный секрет (ключ), не ролевая модель — заявка `Authorization`/`Timestamp` проверяется на каждый запрос.
INT-2: право `AssignRole` или `Master` на приложение, проверка — в `apollo-portal` до вызова `apollo-configservice` (см. INT-2, «Авторизация»).

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Экран приложения в портале получает новый блок «Ключи приложения»: список по выбранному окружению, создание, включение/выключение, удаление. Вызывает INT-2.

### 4.2. Пользовательские сценарии
Основной: администратор выбирает окружение приложения → «Создать ключ» → видит сгенерированное значение один раз, копирует в конфиг клиентского приложения → «Включить». Побочные: выключить действующий ключ (например, перед сменой), завести второй ключ для бесшовной смены, удалить неиспользуемый ключ.

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---|---|---|
| `loading` | запрос списка ключей в процессе | спиннер |
| `value` | 2xx, список непустой | список ключей с `enabled` |
| `empty` | 2xx, список пуст | «ключей пока нет» |
| `error_source` | 5xx/таймаут/сеть, или 404 | сообщение об ошибке + retry |
| `error_forbidden` | 403 | «нет доступа» |

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
INT-1 — проверка синхронная, в рамках того же запроса. Ключи кэшируются в памяти `apollo-configservice` и перечитываются из `ApolloConfigDB` фоновой задачей раз в секунду (по аналогии с существующими задачами `scanNewAppNamespaces`/`updateAndDeleteCache`), без отдельного push-уведомления — изменение ключа видно клиенту в пределах секунды.

### 5.2. Надёжность/деградация
Пока не прошло ни одного успешного обновления кэша (холодный старт) либо очередное обновление не удалось — сервис использует последний успешно загруженный кэш. Если успешного обновления не было вовсе — приложение в это окно воспринимается как не имеющее ключей, то есть конфигурация отдаётся без проверки, как раньше (тот же защитный эффект, что описан в БТ §2.3 для приложений без ключа).

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Как проверяется |
|---|---|---|
| INT-1 (клиент → configservice) | клиент с верной подписью по включённому ключу приложения | симметричный HMAC + свежесть `Timestamp` |
| INT-2 (портал → configservice) | пользователь с `AssignRole`/`Master` на приложение | в портале, до вызова |

## 6. Релиз и интеграция
### 6.1. Порядок выката
1. `apollo-configservice` — новая таблица, CRUD-ручки и логика проверки. На момент выката ни у одного приложения включённых ключей нет — эффект нулевой, старые клиенты не замечают изменения.
2. `apollo-portal` — UI, вызывающий новые ручки `apollo-configservice`. Деплоится вторым, так как зависит от уже существующего на той стороне контракта.
3. Администраторы приложений заводят и включают ключи по готовности, постепенно, по одному приложению.

### 6.2. Обратная совместимость
Старый клиент без заголовков `Authorization`/`Timestamp` продолжает получать конфигурацию без изменений, пока у его приложения нет ни одного включённого ключа (БТ §2.3). После того как администратор включит ключ, старый клиент без подписи начнёт получать `401` — это ожидаемое следствие осознанного действия администратора, не баг совместимости.

### 6.4. План отката
- **Откат только `apollo-configservice`:** если ключи ещё не заводились — без эффекта. Если у части приложений уже есть включённые ключи — откат к версии без проверки временно снимает защиту с этих приложений (все клиенты будут обслужены без проверки подписи) — риск, см. §8.
- **Откат только `apollo-portal`:** CRUD-ручки на `apollo-configservice` остаются, UI управления ключами временно недоступен; уже заведённые и включённые ключи продолжают проверяться без изменений — безопасно.
- **Откат DDL (down-миграция):** удаление таблицы `ApplicationKey` стирает все заведённые ключи; после откатa все приложения воспринимаются как не имеющие ключей — защита снимается полностью до повторного заведения ключей — риск потери данных, см. §8.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано клиент передал верный включённый ключ (валидная подпись) и `Timestamp` не старше 60000 мс, когда запрашивает конфигурацию приватного namespace, тогда конфигурация отдаётся, как и раньше |
| FR-2 | INT-1, каталог ошибок | Дано ключ неверный/невключённый, когда клиент запрашивает конфигурацию приватного namespace, тогда ответ `401 Unauthorized`, конфигурация не отдаётся. | FR-3 | INT-2 | Дано у приложения есть ключ в `apollo-configservice`, когда администратор с правом `AssignRole`/`Master` включает, выключает или удаляет его на выбранном окружении, тогда состояние меняется и учитывается при следующем обращении клиента (в пределах ~1 секунды из-за кэша) |
