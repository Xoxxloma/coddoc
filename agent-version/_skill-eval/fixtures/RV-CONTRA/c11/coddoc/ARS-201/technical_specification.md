## 1. Обзор изменения

### 1.1. Что делаем и тип изменения

**Суть:** В шапке административной панели «Арсенал» появится ненавязчивый счётчик текущего числа активных пользователей. Фронт загрузит значение при открытии панели и будет запрашивать обновление раз в минуту; при нулевом значении покажет 0, при недоступности источника — прочерк.

**Тип:** доработка.

**Стороны:** Fullstack — новый API чтения для счётчика и новый элемент на существующем фронте административной панели.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| arsenal-web | Показывает счётчик в шапке и опрашивает API | Команда «Арсенал-Core» | 🔵 подтверждено аналитиком: существующий фронт и владелец команды |
| Новый backend API счётчика | Реализует новый INT-1 | Команда «Арсенал-Core» | 🟢 новый контракт; 🔵 подтверждено аналитиком: команда-владелец |
| auth (кандидат по выжимке; не подтверждён аналитиком) | Возможный источник числа активности | Сервис-владелец и команда не подтверждены | 🟡 к валидации |

### 1.3. Связь с бизнес-требованиями

Счётчик нужен администраторам отдела эксплуатации для оценки текущей нагрузки и выбора безопасных окон регламентных работ; этот слайс реализует FR-1, FR-6 и части FR-5/FR-7 для счётчика, а график и выгрузка остаются вне его объёма. Приоритет — Medium, срок — до конца текущего квартала.

## 2. Взаимодействия (ядро)

### INT-1. Загрузка текущего числа активных пользователей — 🟢

- **Граница/направление:** фронт админ-панели → backend API «Арсенала».
- **Триггер:** загрузка административной панели и затем один раз в 60 секунд, пока панель открыта.
- **Контракт (запрос):** GET /v1/active-users; тело отсутствует; дополнительные параметры не передаются.
- **Контракт (ответ):**
  - activeUserCount: integer | null — неотрицательное целое число; 0 — валидное отсутствие активных пользователей; null — backend не смог получить актуальное значение из источника.
  - Ответ содержит только текущее число, без истории и списка пользователей.
  - Backend не возвращает предыдущее значение, если источник недоступен.
- **Пример запроса:** тело отсутствует.
- **Пример ответа (успех):**
  ~~~json
  {
    "activeUserCount": 12
  }
  ~~~
- **Пример ответа (ноль):**
  ~~~json
  {
    "activeUserCount": 0
  }
  ~~~
- **Пример ответа (источник недоступен):**
  ~~~json
  {
    "activeUserCount": null
  }
  ~~~
- **Ошибки:** 401 — нет аутентифицированной сессии; 403 — роль не даёт права читать счётчик; 404 — API отсутствует, например при откате backend; 5xx — ошибка API. См. «Каталог ошибок».
- **Состояния UI по ответу:** положительное целое → value; 0 → zero; null → empty (прочерк, без старого значения); таймаут, сеть, 404 или 5xx → error_source (прочерк, без старого значения); 401 → error_session и счётчик скрыт; 403 → error_forbidden и счётчик скрыт.
- **Авторизация:** backend проверяет роль «Администратор» на каждом запросе; для остальных ролей отвечает 403 без раскрытия скрытых данных.
- **Происхождение:** 🟢 новый контракт.
- **Трассировка:** FR-1, FR-5, FR-6, FR-7.

### Каталог ошибок (сводно) — последний подраздел §2, после всех INT-карточек

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 401 | {"error":"unauthenticated"} | Нет аутентифицированной сессии | error_session; счётчик скрыт |
| 403 | {"error":"forbidden"} | Роль не даёт права на счётчик | error_forbidden; счётчик скрыт |
| 404 | {"error":"not_found"} | Backend API не развернуто или откачено | error_source; показать прочерк, повторить на следующем цикле опроса |
| 5xx | {"error":"internal_error"} | Ошибка backend API | error_source; показать прочерк, повторить на следующем цикле опроса |
| 200, activeUserCount: null | — | Источник текущего значения недоступен | empty; показать прочерк, не показывать устаревшее значение |
| Таймаут или сетевая ошибка | — | API не ответил | error_source; показать прочерк, повторить на следующем цикле опроса |

## 3. Backend — ответственность

### 3.1. По сервисам

- Новый backend API счётчика команды «Арсенал-Core» реализует INT-1 и проверяет роль «Администратор» перед выдачей числа — 🟢; команда-владелец подтверждена аналитиком 🔵.
- Источник и сервис-владелец текущего числа активности не подтверждены; выбор и способ чтения — 🟡 к валидации (см. открытый вопрос 1).

### 3.2. Данные и хранение

- Новых сущностей, таблиц и полей нет; счётчик вычисляется при запросе и не сохраняется.
- Исторические данные, список пользователей и миграция не нужны.
- Существующая сущность и правило определения активного пользователя относятся к неподтверждённому источнику — 🟡 к валидации (открытый вопрос 1).
- Точный способ чтения текущих данных определяет сервис-владелец после подтверждения источника.

### 3.3. Авторизация/доступ на бэке

- INT-1 доступен только роли «Администратор» — 🟢.
- Для других ролей API возвращает 403 с общим телом {"error":"forbidden"}; число активности в ответе не раскрывается.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

- В шапке административной панели «Арсенал» появляется визуально ненавязчивый счётчик текущих активных пользователей.
- Фронт вызывает INT-1 при загрузке панели и затем каждые 60 секунд.
- При недоступности источника показывает прочерк; старое число не оставляет на экране.

### 4.2. Пользовательские сценарии

- Администратор открывает панель — фронт загружает значение и показывает число в шапке (FR-1).
- Число изменилось — фронт получает новое значение на следующем цикле опроса без перезагрузки страницы (FR-1).
- Активных пользователей нет — фронт показывает 0 (FR-6).
- Источник недоступен или запрос завершился ошибкой — фронт показывает прочерк, а не ноль или старое значение (FR-5).
- Оператор открывает панель — счётчик и панель активности не отображаются (FR-7).

### 4.3. Состояния (именованные — обязательно, если есть FE)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| loading | Первый запрос после открытия панели | В области счётчика — прочерк |
| value | Успешный ответ с числом больше 0 | Текущее число |
| zero | Успешный ответ с activeUserCount: 0 | 0 |
| empty | Успешный ответ с activeUserCount: null — источник недоступен | Прочерк; предыдущий результат очищен |
| error_source | Таймаут, сеть, 404 или 5xx | Прочерк; предыдущий результат очищен |
| error_session | Ответ 401 | Счётчик скрыт |
| error_forbidden | Ответ 403 | Счётчик скрыт |

### 4.3.1. Loading и таймауты (обязательно, если есть FE)

- **Таймаут cold-path:** 8 секунд по конвенции проекта.
- **Таймаут warm-path:** 3 секунды по конвенции проекта.
- **Polling:** 60 секунд, без jitter; частота подтверждена аналитиком, аудитория — десятки администраторов.
- При таймауте, 404, 5xx или сетевой ошибке фронт очищает предыдущее значение, показывает прочерк и повторяет запрос по следующему циклу опроса.

### 4.4. Доступ по ролям в UI

- «Администратор»: видит счётчик.
- «Оператор»: не видит панель активности и счётчик.
- Скрытие элемента во фронте дополняет, но не заменяет проверку роли backend API.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- Загрузка синхронная по HTTP; повторный запрос запускается раз в 60 секунд.
- Кэш значения не используется: после ошибки нельзя показывать устаревшее число.
- При десятках администраторов ожидается нагрузка порядка десятков запросов в минуту.
- Таймауты клиента: 8 секунд для первого запроса и 3 секунды для последующих.

### 5.2. Надёжность/деградация

- Если источник недоступен, backend возвращает activeUserCount: null; валидный ноль возвращается как 0. Фронт переводит null в empty, а сетевые и серверные ошибки — в error_source.
- Если API недоступно по сети, отвечает 404 или 5xx, фронт показывает прочерк и не использует предыдущий результат.
- Следующий запрос выполняется по обычному минутному циклу.

### 5.3. Безопасность/доступ (сводно)

| Роль | UI | Backend API |
|------|----|-------------|
| Администратор | Видит счётчик | Может читать счётчик |
| Оператор | Не видит панель активности и счётчик | Получает 403; данные не раскрываются |

## 6. Релиз и интеграция

- INT-1 — добавочный API; существующие вызовы и потребители не меняются.
