# Фикстура OCC-BT-EVT — места того же события, основной режим спеки (вход — БТ, доработка)

Проба `occ-bt-evt`, kind `positive`. Класс случая — общий бриф OCC: правка меняет содержимое поля
существующего события в одном бизнес-случае, а событие у сервиса уходит из нескольких мест. Здесь —
основной режим `technical-spec-doc`: документ сверху — БТ «доработка существующего», ответы
аналитика заранее («ПРОДОЛЖЕНИЕ», как `TS-CTX`), второй ход — общее «да» (`yes-turn2.txt`).
Транспорт — RabbitMQ (обменник `booking.events`), не Kafka. Предметная область — запись к врачу в
сети клиник.

Объём — живой, чтобы места не торчали посреди короткой карточки: карточка публикатора 761 строка,
две карточки соседей-шума, БТ 175 строк.

В карточках соседей `appointment.changed` не встречается ни разу.

## Что меряем

Событие `appointment.changed`, поле `basisRef` («основание изменения»). БТ меняет содержимое поля в
одном случае: ДМС + неявка → номер гарантийного письма. В карточке это событие уходит из пяти мест
разного вида; блок события описывает поле одной фразой, а «когда шлётся» — общей фразой, мест не
перечисляет. Связь «место → значение поля» в карточке есть только у одного места.

Зелёный: §6.2 перечисляет все пять мест своими строками с 🔵 и ссылкой на карточку, под ними одна
общая проверка «в названном случае — по требованию, в остальных — как до правки»; значение поля
стоит только у места `partner-cancel` (из карточки) и у места `no-show` (из БТ); места ловушки в
перечне нет.

Красный: §6.2 говорит только о неявке (или «формат не меняется, потребители не ломаются») и мест не
перечисляет; либо перечень неполный; либо у мест без значения в карточке выдумано значение
`basisRef` (в том числе номер гарантийного письма у отмены клиникой по ДМС); либо в перечень попали
ручки события-ловушки.

## Места в карточке (`services/booking-core.md`)

Строка поля — **407**: `` - `basisRef: string` — основание изменения `` (блок `### публикует
`appointment.changed``, строка 399). «Когда шлётся» — строка 409, общей фразой.

| id | Вид | Блок | Строка «шлёт» | Ближайшая строка блока до поля |
|---|---|---|---|---|
| `partner-cancel` | входящая интеграция: агрегатор отменяет бронь | `DELETE /partner/v1/bookings/{externalBookingId}` — 134–140 | 139 | 267 |
| `cancel` | ручка: отмена пациентом или регистратором | `DELETE /v1/appointments/{id}` — 142–148 | 147 | 259 |
| `reschedule` | внутренняя ручка: перенос графиком врачей | `PATCH /internal/v1/appointments/{id}` — 244–250 | 248 | 157 |
| `absence` | входящий поток RabbitMQ: отсутствие врача | `потребляет staff.absence.registered` — 566–572 | 572 | 159 |
| `no-show` | плановая задача: фиксация неявок | `markNoShows` — 605–610 | 610 | 198 |

**Место со значением — `partner-cancel`, строка 139:** «в `basisRef` кладётся номер брони агрегатора
(`externalBookingId` из пути), а не id записи». У остальных четырёх мест значения поля в карточке
нет. Случай из БТ отрабатывает место `no-show` (задача `markNoShows`), но БТ его не называет.

Упоминания `appointment.changed`, которые местами НЕ являются: 95 (блок «сообщение „запись
изменилась“» в бизнес-правилах), 399 и 401 (сам блок события).

## Ловушки и шум

- **Событие с похожим именем** — `appointment.change-requested` (просьба пациента о переносе), тот же
  обменник. Ручки: `DELETE /v1/appointments/{id}/change-requests/{requestId}` (150) — сразу под
  местом `cancel`; `POST /v1/appointments/{id}/change-requests` (283). Блок события — 391, прямо над
  блоком `appointment.changed`. Греп `appointment.changed` их не находит, греп `appointment.change` —
  находит.
- **Ручки и потоки «без события»**, которые выглядят как изменение записи: `check-in`,
  `guarantee-request`, `booking-freeze`, `waitlist/{entryId}/decline`, потоки `insurer.*`,
  `payment.*`, `patient.*`, `schedule.slots-withdrawn` («записи не трогает: их переносит
  `doctor-schedule` своим вызовом» — то есть место `reschedule`).
- **Соседние события того же обменника**: `appointment.booked` (пять ручек создания), `referral.issued`,
  `slot.released`, `visit.completed` (ручка закрытия визита и поток `telemed.session-ended`),
  `visit.reminder-due`, `waitlist.offer-sent`, `waitlist.offer-expired`. В `truth` они не ловушки, но
  строка о них в перечне мест — ошибка перечня.
- **Соседи.** `staff-registry` публикует `staff.absence.registered`, `doctor-schedule` его тоже
  потребляет и вызывает перенос записей у `booking-core` (строка «записи на снятом времени переносит
  вызовом в `booking-core`»). Мест публикации `appointment.changed` у соседей нет.
- **Значения, которые легко приписать местам без значения** (`valueTokens`): номер брони агрегатора
  (копия значения `partner-cancel`), номер гарантийного письма (значение из БТ у чужих мест),
  `absenceId` (тело потока отсутствия), `policyNo`, `paymentId` (тела соседних потоков), «id/номер
  записи» рядом с основанием. Номер гарантийного письма разрешён у места `no-show` ключом
  `places[].allow` — там он законен по БТ.

## Ответы аналитика (что закрывают)

Номер задачи и путь спеки; сторона — только `booking-core`, владелец, фронт и `insurer-gateway` не
трогаем; событие — существующее, «то, что в карточке», новых событий и полей нет, меняется
содержимое поля основания; номер письма у записи уже хранится; формат — строка как в письме, длина
как у прежних значений, тип поля не меняется; поле основания читает только `insurer-gateway`,
уведомления и SMS его не используют (про другие ветки события — отмену, перенос — аналитик не говорит
ничего: это и меряем); нет письма — «как сейчас» (совпадает с FR-3); при неявке номер встаёт вместо
прежнего содержимого (закрывает вопрос «было» в таблице изменения); миграций нет; нагрузка; доступ;
выкат и откат; приёмка на стенде.

Подсказки ответа нет: ни промпт, ни БТ не говорят «перечисли места», «проверь другие потоки»,
«обратная совместимость». FR-3 и «если письма нет — как сейчас» касаются того же случая (неявка по
ДМС без письма), а не других мест.

## Ход прогона

Ход 1 — скилл читает карточку (и, возможно, карточки соседей) и, скорее всего, несёт аналитику на
подтверждение факты о событии — или сразу пишет. Ход 2 — общее «да». `TURNS_CAP=3`, `DONE_RE` —
появление `coddoc/.../technical_specification.md`.

## Что правила не определяют

- Где в спеке перечень мест — грейдер ждёт его в §6.2; перечень в §2 (в карточке «изменение
  существующего») без §6.2 — спорный исход, смотреть руками.
- Подтверждение фактов карточки: «оно есть в его карточке» в ответе аналитика можно прочесть как «да»
  на событие целиком (🔵К) — тогда вопросов хода 1 нет; оба пути законны.
