# Фикстура FX-NONE-1 — задача без чужих стыков, окружения нет

Проба `fx-none-1`, скилл `technical-spec-doc`. Проба на **ложное срабатывание**: чужих систем в задаче
нет, значит спрашивать о чужих контрактах не о чём. Парная — `FX-NONE-2` (карточки соседей лежат, задача
их не касается). Грейдер — `grade-fx-none.mjs`.

## Задача

**SMN-142, журнал передачи смены на участке.** В своём веб-приложении цеха «Смена» появляется раздел
«Передача смены»: мастер сдаёт смену записью по участку (три текстовых поля), другой мастер принимает
её с отметкой «кто и когда», все видят журнал с отбором и выделением непринятых дольше 12 часов,
начальник цеха ведёт справочник участков. Работа на две стороны: три экрана, новые запросы серверной
части, две новые таблицы (запись о передаче смены, участок), одна запись на участок, дату и смену.

## Вход

```
coddoc/SMN-142/business_requirements.md   БТ, «Готово к оценке», одна поставка, внешних зависимостей нет
spec-prompt.txt                           ход 1: «ПРОДОЛЖЕНИЕ», ответы аналитика на организационное
yes-turn2.txt                             ходы 2+: «Да, годится — по всем вопросам как ты предлагаешь…»
```

Папок `services/` и `context/` нет — это штатный исход для скилла, а не пробел фикстуры.

## Почему чужих стыков нет

- Приложение «Смена» целиком своё: экраны, серверная часть, база — команда «Цифровой цех» (ответ аналитика).
- Все данные раздела новые и свои: записи и справочник участков. Из уже существующего раздел берёт только
  вошедшего пользователя с ролью — вход и роли работают, задача их не меняет, серверная часть знает
  пользователя по сессии (ответ аналитика).
- БТ §3.3: «Интеграций с другими системами нет»; §3.4: «Нет».
- Каждое место, где просится интеграция, закрыто в БТ §3.2 без названия какой-либо системы: оборудование
  мастер называет словами; уведомлений нет; вложений нет; выгрузки нет; принимающего ни с чем не сверяем.

## Где соблазн

| Что просится | Чем закрыто |
|---|---|
| список оборудования из учёта оборудования или ремонтов | БТ §3.2: оборудование — словами |
| уведомление принимающему мастеру или начальнику о непринятой смене | БТ §3.2: уведомлений нет; FR-4 — выделение в журнале |
| кто мастер следующей смены — из графика смен или кадров | БТ §3.2 и FR-3: принять может любой другой мастер |
| участки — из оргструктуры | FR-5: свой справочник, ведёт начальник цеха |
| вход — через единый вход | ответ аналитика: вход и роли работают, не меняем |

## Верное поведение

- Вопросов о контракте, адресе, доступе, формате, владельце какой-либо чужой системы нет ни в одном ходе.
- Свой дизайн спроектирован и показан: запросы экран → серверная часть и две сущности; вопросы
  «спроектировал так — годится?» про свои ручки и таблицы законны.
- Спека `coddoc/SMN-142/technical_specification.md` записана; все карточки INT — 🟢, граница экран ↔ своя
  серверная часть; открытых пунктов о чужих системах нет. Ожидаемый статус — «Готово к разработке».

## Красные исходы

- Вопрос аналитику о чужой системе: откуда брать оборудование, как устроен единый вход, чем слать
  уведомления, у кого взять график смен — в любой форме, включая «подтвердите или оставим к валидации».
- В спеке взаимодействие с системой, которой задача не требует (участник INT — не «Смена»).
- Открытый пункт про чужой контракт или «уточнить у команды …».
- Свой стык экран ↔ серверная часть записан 🟡 / «к валидации» вместо спроектированного 🟢.

Не красное, «сверить глазами»: вопрос-кивок об отсутствии («интеграций нет — верно?»); открытый пункт
`❓` про своё решение без слов о контракте.

## Регистрация и запуск

В раннер проба не заведена. Строка для `run-ctx-v2.sh`:

```
  fx-none-1) FIXTURE=FX-NONE-1; PROMPT_FILE=spec-prompt.txt; SKILL=technical-spec-doc; TURN2_FILE=yes-turn2.txt; TURNS_CAP=4; IDLE_MAX=4; DONE_RE='/coddoc/.*/technical_specification\.md$' ;;
```

`IDLE_MAX=4` нужен вместе с `TURNS_CAP=4`: трассы у пробы нет, каждый ход «пустой», и при пороге по
умолчанию (2) диалог гаснет после третьего хода. Грейдинг: `node grade-fx-none.mjs <папка-раунда>`.
