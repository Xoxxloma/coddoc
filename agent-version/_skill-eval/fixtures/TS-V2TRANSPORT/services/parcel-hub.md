# parcel-hub — backend

> Генерируется. Правки руками затираются.
> Заметки человека — в `services/manifest.yaml`, поле `notes`.
> Форма — `reference/card.template.md` скилла `service-map`. Соседние карточки формой не являются.

## Назначение

Сервис ведёт путь посылки от первого скана на сортировке до вручения или списания как утерянной и показывает, какой курьер её везёт и в каком он состоянии. Процессы: скан на сортировке, назначение маршрута, смена статуса курьера, вручение посылки, списание посылки как утерянной. Главные объекты: посылки с трек-номером и курьеры со статусом смены.

## Что умеет для пользователя
| Возможность | Для кого |
|---|---|
| Посмотреть посылку по трек-номеру: статус, последний пункт, курьер | не определено: роли в коде нет |
| Посмотреть список курьеров | не определено: роли в коде нет |
| Посмотреть курьера по номеру — на смене, на перерыве или вне смены | не определено: роли в коде нет |
| Отметить посылку врученной — недоступно, если посылка списана как утерянная | Курьер |
| Списать посылку как утерянную, указав причину; по умолчанию причина «нет сканов» | Оператор |
| Завести посылку первым сканом на сортировке; врученная посылка от скана не меняется | Система сортировки |
| Поставить посылке курьера при назначении маршрута; у врученной посылки курьер не меняется | Система маршрутов |
| Обновить статус курьера по сообщению о смене | Система учёта курьеров |

## Бизнес-правила

### `Courier` — курьер со статусом смены
- на смене (`ON_SHIFT`) — приходит сообщением о смене статуса курьера; последнее пришедшее значение заменяет прежнее
- перерыв (`BREAK`) — приходит тем же сообщением; последнее пришедшее заменяет прежнее
- вне смены (`OFF`) — приходит тем же сообщением; значение по умолчанию у заведённого курьера, курьер заводится при первом сообщении; допустимость значения при приёме не проверяется

### `Parcel` — посылка с трек-номером
- не определено: перехода в коде нет (`CREATED`)
- в пути (`IN_TRANSIT`) — скан на сортировке, первый скан заводит посылку; врученная посылка остаётся врученной, списанная как утерянная возвращается в путь следующим сканом
- вручена (`DELIVERED`) — курьер отмечает вручение, если посылка не списана как утерянная; после этого сканы и назначение маршрута статус не меняют; оператор по-прежнему может списать посылку
- утеряна (`LOST`) — оператор списывает вручную, причина берётся из запроса; срок «7 дней без сканов» упомянут в комментарии, но не проверяется; вручить такую посылку нельзя — отказ «посылка списана как утерянная»

### сообщение «посылка вручена»
- при отметке вручения; получают соседние сервисы через шину; не отправляется, если посылка списана как утерянная; при повторной отметке отправляется снова

### сообщение «посылка списана как утерянная»
- при списании; получают соседние сервисы через шину вместе с причиной; проверок перед отправкой нет, кроме существования посылки

## Публичный контракт

### `GET /couriers`
Список курьеров.
сущности: → `Courier` целиком
доступ: без проверки
- отдаёт всех курьеров, без фильтра и постраничности

### `GET /couriers/:id`
Курьер по номеру.
сущности: ← `id` · → `Courier` целиком
доступ: без проверки
- ошибки: `404` без тела — курьера нет
- только чтение: статус приходит из топика `couriers.status`

### `GET /health`
Проверка живости.

### `GET /parcels/:track`
Посылка по трек-номеру.
сущности: ← `track` · → `Parcel` целиком
доступ: без проверки
- ошибки: `404` без тела — посылки нет
- `lastPoint` и `courierId` бывают пустыми: нет ни одного скана / маршрут не назначен

### `POST /parcels/:track/delivered`
Курьер отмечает вручение.
сущности: ← `track` · → не сущность, ответ `204` без тела; меняет `Parcel`
доступ: без проверки
меняет: `Parcel.status` `CREATED` \| `IN_TRANSIT` \| `DELIVERED` → `DELIVERED` — кроме списанной как утерянная
шлёт: `parcels.delivered`
- ошибки: `409` с текстом «посылка списана как утерянная» — посылка в статусе `LOST`
- успех: `204` без тела
- повторный вызов на уже врученной посылке снова публикует событие о вручении
- посылки с таким треком нет: обработчика ошибки в коде нет, ответ не определён
- статус сохраняется, затем отдельным вызовом уходит событие; сбой публикации оставляет статус `DELIVERED`

### `POST /parcels/:track/lost`
Списание посылки как утерянной.
сущности: ← `track`, `reason` (тело запроса, необязательно) · → не сущность, ответ `204` без тела; меняет `Parcel`
доступ: без проверки
меняет: `Parcel.status` любой → `LOST` — без условий
шлёт: `parcels.lost` — причина из тела запроса
- `reason` по умолчанию «нет сканов»
- комментарий в коде требует «без сканов дольше 7 дней, вручную оператором», но срок и роль не проверяются
- врученную посылку тоже можно списать
- посылки с таким треком нет: обработчика ошибки в коде нет, ответ не определён

## События

### потребляет `couriers.status`
Статус курьера: на смене, перерыв, вне смены.
меняет: `Courier.status` `ON_SHIFT` \| `BREAK` \| `OFF` → значение из события — последнее пришедшее выигрывает
- читает: `courierId`, `status`; курьер заводится при первом событии
- группа: `parcel-hub`
- подтверждение: как у транспорта `startConsumers`
- повтор: безопасен — запись по `courierId`
- ошибка: как у транспорта `startConsumers`; значение `status` в рантайме не проверяется

### потребляет `parcels.scanned`
Скан посылки на сортировке.
меняет: `Parcel.status` `CREATED` \| `IN_TRANSIT` \| `LOST` → `IN_TRANSIT` — любой скан, кроме уже врученной посылки
- читает: `track`, `point` (пишется в `lastPoint`); остальные поля игнорируются
- первый скан заводит посылку
- у врученной посылки статус не меняется, `lastPoint` обновляется
- группа: `parcel-hub`
- подтверждение: как у транспорта `startConsumers`
- повтор: безопасен — `lastPoint` перезаписывается, порядок сканов не гарантируется
- ошибка: как у транспорта `startConsumers`

### потребляет `routes.assigned`
Назначение маршрута: посылке ставится курьер.
меняет: нет
- читает: `track`, `courierId` (пишется в посылку)
- посылки нет или она вручена — событие молча пропускается, посылка не создаётся
- группа: `parcel-hub`
- подтверждение: как у транспорта `startConsumers`
- повтор: безопасен — присваивание `courierId`
- ошибка: как у транспорта `startConsumers`

### публикует `parcels.delivered`
Посылка вручена.
- тело: `track: string`, `at: iso8601` — время отметки вручения
- ключ: `track` — порядок гарантирован по посылке
- когда: `POST /parcels/:track/delivered`
- гарантия: как у транспорта `producer`; событие уходит после сохранения статуса, повторная отметка даёт дубль
- не шлётся: посылка списана как утерянная (`409`)

### публикует `parcels.lost`
Посылка списана как утерянная.
- тело: `track: string`, `reason: string` — из тела запроса, по умолчанию «нет сканов»
- ключ: `track` — порядок гарантирован по посылке
- когда: `POST /parcels/:track/lost`
- гарантия: как у транспорта `producer`; событие уходит после сохранения статуса, повторное списание даёт дубль
- не шлётся: посылки с таким треком нет

### транспорт `producer`
Общая обвязка отправки.
- гарантия: идемпотентный продюсер kafkajs, подключается при первой отправке; без outbox и без транзакции с БД — при сбое публикации статус в БД уже сохранён

### транспорт `startConsumers`
Общая обвязка слушателей.
- подтверждение: одна группа на три входящих топика; сообщение подтверждается после обработки
- ошибка: при сбое обработчика — повтор до 5 попыток kafkajs; очереди недоставленных сообщений в коде нет

## Владеет данными

### `Courier`
Курьеры и их статус смены.
- `id`: `number`
- `status`: `ON_SHIFT` \| `BREAK` \| `OFF` — по умолчанию `OFF`
— значение ставит только сообщение из топика `couriers.status`; HTTP его не меняет

### `Parcel`
Посылки по трек-номеру.
- `track`: `string` — первичный ключ
- `status`: `CREATED` \| `IN_TRANSIT` \| `DELIVERED` \| `LOST` — по умолчанию `CREATED`
- `lastPoint`: `string?` — `null`, пока не было ни одного скана
- `courierId`: `number?` — `null`, пока не назначен маршрут
— код не ставит `CREATED` сам: первый скан сразу даёт `IN_TRANSIT`
— `courierId` ссылкой на `Courier` не оформлен: связи в схеме нет
