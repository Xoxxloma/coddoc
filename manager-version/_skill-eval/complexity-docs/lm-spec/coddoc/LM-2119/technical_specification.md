## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В настройках OIDC (раздел «Безопасность») появляется переключатель «создавать пользователя автоматически, если его нет» и поля выбора роли по умолчанию — роли пользователя и роли на списки. При включённом переключателе первый успешный вход через OIDC человека, чей e-mail не найден среди пользователей listmonk, создаёт для него обычного, сразу активного пользователя без пароля (вход только через OIDC) и назначает ему выбранные роли, после чего сразу пускает его внутрь.
**Тип:** доработка
**Стороны:** Fullstack — меняется страница настроек «Безопасность» (FE) и обработчики `PUT/GET /api/settings`, `GET /auth/oidc` (BE), всё в пределах одного сервиса listmonk.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| listmonk | единственный затронутый сервис (FE и BE — один бинарник) | команда listmonk | 🔵 подтверждено аналитиком (со слов) |

### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель БТ: администратор получает возможность разрешить автоматическое создание пользователей при входе через SSO, чтобы не заводить вручную каждого человека из часто меняющегося состава SSO (БТ §2.1).

## 2. Взаимодействия (ядро)

### INT-1. Настройки автосоздания при OIDC-входе — 🟢
- **Вид:** изменение существующего
- **Граница/направление:** FE (страница настроек «Безопасность») → BE (`/api/settings`)
- **Триггер:** администратор открывает или сохраняет настройки OIDC
- **Существующий стык:** `PUT /api/settings` / `GET /api/settings` — 🔵 подтверждено аналитиком (по карточке `services/listmonk.md`; путь нового блока — со слов аналитика): объединённый объект настроек уже содержит блок `security.oidc` с полями адреса провайдера и client id — их точные имена аналитик не называл и в этот документ не выносятся.
- **Изменение:**

| Поле | Где | Было | Стало |
|---|---|---|---|
| `security.oidc.auto_create_users` | `Settings` | не существовало | добавлено: `bool`, по умолчанию `false` |
| `security.oidc.default_user_role_id` | `Settings` | не существовало | добавлено: `number\|null`, ссылка на `Role.id` |
| `security.oidc.default_list_role_id` | `Settings` | не существовало | добавлено: `number\|null`, ссылка на `ListRole.id`; обязательность при включённом автосоздании — ❓ TBD (отложено аналитиком), см. «Открытые вопросы» №1 |

- **Контракт (запрос, `PUT /api/settings`):** фрагмент объекта `Settings` — три поля из таблицы выше; прочие поля `security.oidc` и всего `Settings` — без изменений.
- **Контракт (ответ, `GET`/`PUT /api/settings`):** те же три поля зеркально в ответе; прочие поля `Settings` — без изменений. `default_user_role_id`/`default_list_role_id` = `null`, если роль не выбрана.
- **Пример запроса (фрагмент):**
  ```json
  {
    "security": {
      "oidc": {
        "auto_create_users": true,
        "default_user_role_id": 3,
        "default_list_role_id": null
      }
    }
  }
  ```
  *(фрагмент: прочие поля `security.oidc` и `Settings` — без изменений)*
- **Пример ответа (успех, фрагмент):**
  ```json
  {
    "security": {
      "oidc": {
        "auto_create_users": true,
        "default_user_role_id": 3,
        "default_list_role_id": null
      }
    }
  }
  ```
  *(фрагмент: прочие поля — без изменений)*
- **Ошибки:** см. «Каталог ошибок» ниже
- **Состояния UI по ответу:** значение → переключатель и выбранные роли отражают сохранённые значения; загрузка → спиннер на форме настроек; ошибка → см. «Каталог ошибок»
- **Авторизация:** право на «настройки» из общего каталога прав — 🔵 подтверждено аналитиком (по карточке `services/listmonk.md`: доступ к `/api/settings` требует права на настройки; не меняется)
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-1, FR-2

### INT-2. Автосоздание пользователя при входе через OIDC — 🟢
- **Вид:** изменение существующего
- **Граница/направление:** внешний OIDC-провайдер → BE (`GET /auth/oidc`, обратный вызов)
- **Триггер:** человек успешно проходит аутентификацию во внешнем SSO и возвращается в listmonk
- **Существующий стык:** `GET /auth/oidc` — 🔵 подтверждено аналитиком (по карточке `services/listmonk.md`): сейчас, если e-mail из токена не найден среди пользователей listmonk, вход отклоняется; OIDC не создаёт пользователей сам.
- **Изменение:**

| Поведение | Где | Было | Стало |
|---|---|---|---|
| ветвление при ненайденном e-mail | `GET /auth/oidc` | отказ во входе | если `security.oidc.auto_create_users = true` — создать пользователя и пустить в систему; если `false` — отказ, как было (FR-5) |

- **Контракт (запрос):** без изменений — тот же обратный вызов провайдера; тело отсутствует.
- **Контракт (ответ):** без изменений в форме ответа (редирект на целевую страницу либо страница ошибки); меняется только то, какая ветка срабатывает.
- **Создание пользователя (внутри обработки, не отдельный сетевой контракт):** `User.type = "user"`, `User.status = "enabled"`, `User.username = <email>`, `User.email = <email>`, `User.password = null`, `User.password_login = false`, `User.user_role_id = security.oidc.default_user_role_id`, `User.list_role_id = security.oidc.default_list_role_id` — 🟢 правило назначения; поля самой сущности `User` — 🔵 подтверждено аналитиком (по карточке `services/listmonk.md`).
- **Пример запроса:** тело отсутствует (без изменений)
- **Пример ответа (успех):** без изменений формы — редирект на целевую страницу, как при обычном входе
- **Ошибки:** см. «Каталог ошибок» ниже
- **Состояния UI по ответу:** значение → пользователь внутри приложения, как после обычного входа; ошибка → страница ошибки (как сейчас)
- **Авторизация:** без авторизации по определению — это сам процесс входа; не меняется — 🔵 подтверждено аналитиком
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-3, FR-4, FR-5

## 3. Backend — ответственность
### 3.1. По сервисам
listmonk: 🟢 добавляет чтение и валидацию трёх новых полей `security.oidc.*` в обработчике `PUT /api/settings`; 🟢 добавляет ветвление создания пользователя в обработчике `GET /auth/oidc` при ненайденном e-mail и включённом автосоздании; 🔵 переиспользует существующие правила создания `User` (имя пользователя от 3 символов, разрешённые символы — по карточке; e-mail как логин соответствует этому набору символов).

### 3.2. Данные и хранение
- 🟢 `Settings` — три новых поля в существующем объединённом объекте (не новая таблица): `security.oidc.auto_create_users: bool`, `security.oidc.default_user_role_id: number|null`, `security.oidc.default_list_role_id: number|null`.
- 🔵 `User` — новых полей не добавляется; используются существующие поля (по карточке): `username`, `email`, `password`, `password_login`, `type`, `status`, `user_role_id`, `list_role_id`.
- 🔵 `Role`, `ListRole` — только читаются (проверка существования выбранной роли при сохранении настроек); новых полей нет.
- Новых сущностей нет. Миграции не требуются: `Settings` хранится построчно по ключу настройки, но принимается/отдаётся объединённым объектом (по карточке) — три новых поля — это новые ключи настроек, а не новая колонка или таблица.
- В уже лежащих строках `Settings` ничего не пересчитывается: до первого явного сохранения новых полей их отсутствие трактуется как `auto_create_users = false` — поведение входа не меняется, пока администратор не сохранит настройку явно.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Страница настроек «Безопасность» (раздел OIDC): добавляется переключатель «создавать пользователя автоматически, если его нет» и два поля выбора роли (роль пользователя, роль на списки). Вызывает INT-1 при сохранении.

### 4.2. Пользовательские сценарии
Основной поток: администратор выбирает роль пользователя (и опционально роль на списки) → включает переключатель → сохраняет (FR-1). Ветвление: переключатель остаётся недоступным для включения, пока роль пользователя не выбрана (FR-2).

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `settings_loaded` | `GET /api/settings` вернул текущие значения `security.oidc.*` | переключатель и поля ролей отражают сохранённое состояние |
| `toggle_blocked` | роль пользователя не выбрана | переключатель недоступен для включения (FR-2) |
| `save_error` | `PUT /api/settings` вернул 400 | сообщение об ошибке сохранения на форме |
| `save_success` | `PUT /api/settings` вернул успех | подтверждение сохранения |

### 4.3.1. Loading и таймауты
Не применимо: сохранение настроек — обычный синхронный запрос-ответ без polling и без различия cold/warm path; новых таймаутов не вводится.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Не применимо: новых механизмов синхронности, кэша или опроса нет. Создание пользователя происходит синхронно внутри уже существующего обратного вызова `GET /auth/oidc` — та же модель, что и у обычного входа.

## 6. Релиз и интеграция
### 6.1. Порядок выката
Единый релиз: FE и BE поставляются в одном бинарнике listmonk (по карточке, раздел «Стек»). Отдельного порядка выката сторон нет — обновляется один артефакт.

### 6.2. Обратная совместимость
При обновлении у всех существующих инсталляций `security.oidc.auto_create_users = false` и роли по умолчанию не заданы (`null`) — поведение входа не меняется, пока администратор явно не включит переключатель и не выберет роль (подтверждено аналитиком). Три новых поля — аддитивное изменение ответа `/api/settings`; существующие потребители API, не знающие о них, продолжают работать как прежде.

### 6.3. Фиче-флаги
Отдельных фиче-флагов сверх самого переключателя `security.oidc.auto_create_users` не требуется — он сам выполняет эту роль (подтверждено аналитиком).

### 6.4. План отката
- **Откат BE/FE:** не применимо раздельно — FE и BE поставляются одним бинарником (§6.1); откат всего бинарника на прежнюю версию убирает переключатель и поля ролей из UI и API. Уже созданные автопользователи остаются обычными активными записями `User` в БД и продолжают работать как обычные пользователи listmonk (не теряются).
- **Откат DDL:** не применимо — миграций нет (§3.2).

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано: администратор открыл настройки OIDC. Когда: смотрит на раздел. Тогда: виден переключатель (выключен по умолчанию) и поля выбора роли. |
| FR-2 | INT-1 | Дано: роль пользователя не выбрана. Когда: администратор пытается включить переключатель и сохранить. Тогда: сохранение отклоняется (400), переключатель недоступен без роли. |
| FR-3 | INT-2 | Дано: переключатель включён, роль выбрана. Когда: человек впервые успешно входит через OIDC, e-mail не найден. Тогда: создаётся активный пользователь без пароля с выбранными ролями, вход происходит. |
| FR-4 | INT-2 | Дано: переключатель включён, пользователь с таким e-mail уже есть. Когда: вход через OIDC. Тогда: новый пользователь не создаётся, вход под существующей записью. |
| FR-5 | INT-2 | Дано: переключатель выключен. Когда: не заведённый вручную человек входит через OIDC. Тогда: вход отклоняется, пользователь не создаётся. |

## 8. Допущения и открытые вопросы
- **🔵 Подтверждено аналитиком:** единственный затронутый сервис — listmonk (со слов); путь новых полей настроек — `security.oidc.*` (со слов); роль по умолчанию выбирается из существующих пользовательских ролей, без отдельной специальной роли (со слов); валидация «нельзя сохранить без роли пользователя» обязательна на бэке (со слов); авторизация `/api/settings` и отсутствие авторизации на `/auth/oidc` не меняются (со слов). Валидировать при интеграции.
- **🟡 К валидации:** нет.
- **❓ Открытые решения:**
  1. обязательна ли роль на списки по умолчанию при включённом автосоздании (см. «Открытые вопросы» в шапке №1);
  2. поведение при удалении роли, назначенной умолчанием для OIDC-автосоздания (см. «Открытые вопросы» в шапке №2).
- **⚠️ Требует уточнения:** нет.
- **Технические риски:** одновременный первый вход одного и того же e-mail дважды (повторный запрос) может попытаться создать двух пользователей с одним логином → мера: защита уникальностью на вставке `User` (§5.2).
