## 1. Обзор изменения

### 1.1. Что делаем и тип изменения
**Суть:** В `booking-service` появляется фоновая задача: раз в 5 минут она находит записи, до которых осталось 24 часа или 2 часа, и отправляет пациенту SMS через существующий метод `POST /v1/sms/messages` шлюза `notify-gateway`, повторяя отправку до трёх раз при перегрузке или сбое; каждое напоминание хранится строкой `appointment_reminder` со статусом. В профиле пациента появляется признак `smsRemindersEnabled` и переключатель в личном кабинете, а в ответе карточки записи для администратора клиники — массив `reminders` с состоянием обоих напоминаний.
**Тип:** доработка
**Стороны:** Fullstack — бэк и веб `booking-service` (личный кабинет пациента, кабинет администратора) плюс исходящий вызов в `notify-gateway`.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `booking-service` | изменение: фоновая задача, новая таблица и поле профиля, новая ручка, новые поля в двух ответах, экраны ЛК и карточки записи | команда «Запись» (наша) | 🔵 подтв. аналитиком (со слов) |
| `notify-gateway` | потребитель: существующий метод отправки SMS, без изменений | команда «Коммуникации» | 🔵 подтв. аналитиком (по карточке services/notify-gateway.md) |

### 1.3. Связь с бизнес-требованиями
Реализует цель БТ — снизить долю неявок напоминаниями пациенту за 24 и за 2 часа до приёма и дать администратору клиники видеть, кому напоминание не ушло, чтобы звонить только им.

### INT-2. Включение и отключение SMS-напоминаний — 🟢
- **Вид:** новое
- **Граница/направление:** FE (личный кабинет `booking-service`) → BE `booking-service`

- **Пример запроса:**
  ```json

  ```
- **Пример ответа (успех):**
  ```json
  {
    "smsRemindersEnabled": false,
    "updatedAt": "2026-11-13T07:00:00Z"
  }
  ```
- **Ошибки:** 400 `VALIDATION_ERROR`; 401; 403 `FORBIDDEN` — см. «Каталог ошибок».

- **Авторизация:** только роль `PATIENT`, только свой профиль (пациент берётся из сессии, идентификатора в пути нет); другая роль → 403.

- **Трассировка:** FR-5

### INT-4. Отправка SMS через шлюз — 🔵
- **Вид:** потребление существующего
- **Граница/направление:** `booking-service` (фоновая задача) → `notify-gateway`
- **Триггер:** фоновая задача напоминаний нашла напоминание к отправке или к повтору (§3.1)
- **Контракт (запрос):** `POST /v1/sms/messages` — 🔵 подтверждено аналитиком (по карточке services/notify-gateway.md; валидировать при интеграции)
  - `phone` — `string`, E.164, обязательное;
  - `text` — `string`, обязательное;
  - `clientMessageId` — `string`, обязательное; повтор с тем же значением в течение 24 ч SMS заново не отправляет и возвращает прежний `messageId`.
- **Контракт (ответ):** `202 Accepted`: `messageId` — `string`; `status` — `ACCEPTED`. Ошибки: 400 `INVALID_PHONE`; 429 — шлюз перегружен; 5xx — сбой шлюза.
- **Пример запроса:** `clientMessageId` = `id` строки `appointment_reminder`
  ```json
  {
    "phone": "+79161234567",
    "text": "Напоминаем о приёме 14.11 в 15:00: врач Орлов А. П., ул. Лесная, 7. Отключить SMS — в личном кабинете.",
    "clientMessageId": "6b1d0c2e-8f3a-4f61-9a0b-2e5c7d4a1f90"
  }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "messageId": "sms-20261113-0048812",
    "status": "ACCEPTED"
  }
  ```
- **Ошибки:** 400 `INVALID_PHONE` → напоминание `FAILED` без повторов; 429, 5xx, таймаут 10 с → повтор (§3.1); после четвёртой неудачной попытки → `FAILED`.
- **Состояния UI по ответу (если есть фронт):** фронта нет; результат виден администратору через INT-3.
- **Авторизация:** 🔵 сервисный токен `booking-service`, который уже используется для SMS с кодом входа (со слов; валидировать при интеграции).
- **Происхождение:** 🔵 подтверждено аналитиком (по карточке services/notify-gateway.md)
- **Трассировка:** FR-1, FR-2, FR-4

## 3. Backend — ответственность

### 3.1. По сервисам
`booking-service`:
- 🟢 INT-1: отдать `smsRemindersEnabled` из профиля.
- 🟢 INT-2: записать `sms_reminders_enabled` и `sms_reminders_updated_at` (время меняется, только если значение изменилось).
- 🟢 INT-3: собрать `reminders` по правилам ниже.
- 🟢 Фоновая задача `appointment-reminders`:
  - запуск каждые 5 минут (:00, :05, …) на каждом экземпляре сервиса; 🔵 экземпляров 3 (со слов; валидировать при интеграции); работает, только если включён флаг `reminders-sms-job` (§6.3);
  - моменты: `plannedAt(H24)` = `startAt` − 24 ч, `plannedAt(H2)` = `startAt` − 2 ч; конец окна: для `H24` — `startAt` − 2 ч, для `H2` — `startAt`;
  - «когда записались на это время» = `coalesce(rescheduledAt, createdAt)` записи;
  - **шаг 1, новые:** записи в статусе `BOOKED`, у которых `plannedAt ≤ now < конец окна`, «когда записались» ≤ `plannedAt` и нет строки `appointment_reminder` с тем же (`appointment_id`, `kind`, `appointment_start_at`). По каждой — вставка строки `ON CONFLICT DO NOTHING`: `SKIPPED_OPTED_OUT`, если у пациента напоминания отключены, иначе `SENDING` с `locked_until` = now + 2 мин. Вставил — этот экземпляр отправляет; конфликт — строку взял другой экземпляр;
  - **шаг 2, повторы:** атомарный захват `UPDATE … SET status = 'SENDING', locked_until = now + 2 мин` по строкам `RETRYING` с `next_attempt_at ≤ now` и по зависшим `SENDING` с `locked_until < now` (выборка `FOR UPDATE SKIP LOCKED`, до 200 строк за запуск);
  - **перед каждой попыткой:** запись всё ещё `BOOKED` и её `startAt` = `appointment_start_at` строки — иначе `CANCELLED`; у пациента напоминания включены — иначе `SKIPPED_OPTED_OUT`; `now` < конца окна — иначе `FAILED`, `last_error` = `WINDOW_PASSED`;
  - **отправка:** INT-4, `clientMessageId` = `id` строки; текст: «Напоминаем о приёме {ДД.ММ} в {ЧЧ:ММ}: врач {Фамилия И. О.}, {адрес филиала}. Отключить SMS — в личном кабинете.» — дата и время в часовом поясе филиала; `attempts` + 1;
  - **итог попытки:** 202 → `SENT`, `sent_at`, `gateway_message_id`; 400 `INVALID_PHONE` → `FAILED`; 429 / 5xx / таймаут 10 с → при `attempts` < 4 — `RETRYING`, `next_attempt_at` = now + 5 мин (повтор на следующем запуске), при `attempts` = 4 — `FAILED`. Итого первая попытка и до трёх повторов (FR-4);
  - до 10 одновременных отправок на экземпляр.
- 🟢 Правила `reminders` в INT-3 (по текущему `startAt`):

  | Строка `appointment_reminder` | Условие | `status` / `reason` |
  |-------------------------------|---------|---------------------|
  | `SENDING` или `RETRYING` | — | `IN_PROGRESS` / `null` |
  | `SENT` | — | `SENT` / `null` |
  | `FAILED` | `last_error` = `INVALID_PHONE` | `FAILED` / `INVALID_PHONE` |
  | `FAILED` | иначе | `FAILED` / `GATEWAY_UNAVAILABLE` |
  | `SKIPPED_OPTED_OUT` | — | `SKIPPED` / `OPTED_OUT` |
  | `CANCELLED` | — | `SKIPPED` / `APPOINTMENT_CANCELLED` |
  | нет строки | запись `CANCELLED` | `SKIPPED` / `APPOINTMENT_CANCELLED` |
  | нет строки | «когда записались» > `plannedAt` | `SKIPPED` / `BOOKED_LATE` |
  | нет строки | `now` ≥ конца окна | `SKIPPED` / `WINDOW_PASSED` |
  | нет строки | у пациента напоминания отключены | `SKIPPED` / `OPTED_OUT` |
  | нет строки | иначе | `SCHEDULED` / `null` |

  Строки таблицы проверяются сверху вниз, берётся первая подходящая.
- 🔵 Отмена и перенос записи — существующая логика без изменений: перенос меняет `startAt` и проставляет `rescheduledAt` (по коду booking-service, ветка develop; валидировать при интеграции).

### 3.2. Данные и хранение
- 🟢 `appointment_reminder` — новая таблица:
  - `id` (uuid, PK; он же `clientMessageId` для шлюза);
  - `appointment_id` (FK на запись);
  - `kind` (enum `H24` | `H2`);
  - `appointment_start_at` (timestamptz — время приёма, к которому относится напоминание);
  - `status` (enum `SENDING` | `RETRYING` | `SENT` | `FAILED` | `SKIPPED_OPTED_OUT` | `CANCELLED`);
  - `attempts` (smallint, 0–4);
  - `next_attempt_at` (timestamptz | null);
  - `locked_until` (timestamptz | null);
  - `sent_at` (timestamptz | null — момент, когда шлюз принял SMS);
  - `gateway_message_id` (string | null);
  - `last_error` (enum `INVALID_PHONE` | `GATEWAY_429` | `GATEWAY_5XX` | `GATEWAY_TIMEOUT` | `WINDOW_PASSED` | null);
  - `created_at`, `updated_at` (timestamptz).
  - Уникальный индекс (`appointment_id`, `kind`, `appointment_start_at`) — одно напоминание каждого вида на время приёма, защита от дублей при трёх экземплярах.
  - Индекс (`status`, `next_attempt_at`) по строкам `RETRYING` и `SENDING` — для шага 2.
  - Индекс (`appointment_id`) — для INT-3.
  - Хранится без срока, вместе с записью; около 8 000 строк в сутки.
- 🟢 `patient` — изменение существующей таблицы:
  - `sms_reminders_enabled` (boolean, not null, default `true`) — в уже лежащих строках `true` по умолчанию;
  - `sms_reminders_updated_at` (timestamptz | null) — в уже лежащих строках пусто.
- 🔵 `appointment` — `id`, `patient_id`, `doctor_id`, `branch_id`, `start_at` (UTC), `status` (`BOOKED` | `CANCELLED` | `COMPLETED` | `NO_SHOW`), `created_at`, `rescheduled_at` (null, если не переносилась) — подтверждено аналитиком (по коду booking-service, ветка develop; валидировать при интеграции). Не меняется.
- 🔵 `doctor.full_name`, `branch.address`, `branch.timezone` — подтверждено аналитиком (по карточке services/booking-service.md; валидировать при интеграции). Не меняются.
- 🔵 `patient.phone` — E.164, обязателен при регистрации (со слов; валидировать при интеграции).
- 🔵 Индекс по `appointment.start_at` уже есть (со слов; валидировать при интеграции) — выборка шага 1 идёт по нему.
- Миграции: да — создать `appointment_reminder` с индексами; добавить два столбца в `patient`. Пересчёт старых записей не нужен. Точный DDL финализирует `booking-service`.

### 3.3. Авторизация/доступ на бэке
- 🟢 INT-2: только роль `PATIENT`, профиль берётся из сессии; другая роль → 403 `FORBIDDEN`.
- 🔵 INT-1: пациент видит только свой профиль (по коду booking-service, ветка develop; валидировать при интеграции).
- 🔵 INT-3: `CLINIC_ADMIN` видит записи только своей клиники, чужая запись → существующий 403 (по карточке services/booking-service.md; валидировать при интеграции). Новое поле `reminders` отдаётся под той же проверкой.
- INT-4: вызов от имени сервиса, сервисным токеном (§2, INT-4).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
- 🔵 Личный кабинет пациента, раздел «Профиль» (со слов; валидировать при интеграции):
  - 🟢 переключатель «SMS-напоминания о приёме» с подписью «за 24 часа и за 2 часа до приёма»; значение — из INT-1, изменение — INT-2.
- 🔵 Кабинет администратора, экран «Карточка записи» (по карточке services/booking-service.md; валидировать при интеграции):
  - 🟢 блок «Напоминания» — две строки: «За 24 часа» и «За 2 часа»; данные — `reminders` из INT-3; время — в часовом поясе филиала, как прочее время в карточке.

### 4.2. Пользовательские сценарии
- Пациент отключает напоминания (FR-5): переключает → `reminders_saving` → 200 → `reminders_off`; ошибка → переключатель возвращается, сообщение «Не удалось сохранить, повторите».
- Пациент включает напоминания снова (FR-5): то же, итог `reminders_on`.
- Администратор открывает карточку записи (FR-6): видит обе строки блока «Напоминания» с текстами из §4.3; кому «Не отправлено» или «Не отправлялось» — звонит сам.
- Отправка и повторы (FR-1–FR-4) идут без участия пользователя; результат виден администратору по FR-6.

### 4.3. Состояния (именованные — обязательно, если есть FE)
Личный кабинет, переключатель:

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `reminders_loading` | профиль загружается (INT-1) | переключатель неактивен, скелетон |
| `reminders_on` | `smsRemindersEnabled = true` | переключатель включён |
| `reminders_off` | `smsRemindersEnabled = false` | переключатель выключен |
| `reminders_saving` | INT-2 выполняется | переключатель неактивен, спиннер |
| `reminders_error_save` | INT-2: 400 / 403 / 5xx / таймаут / сеть | переключатель в прежнем положении; «Не удалось сохранить, повторите» |

Карточка записи, строка напоминания (по элементу `reminders`):

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `reminder_scheduled` | `status = SCHEDULED` | «Запланировано на 14.11 13:00» (`plannedAt`) |
| `reminder_in_progress` | `status = IN_PROGRESS` | «Отправляется» + «попытка N из 4» при `attempts` ≥ 1 |
| `reminder_sent` | `status = SENT` | «Отправлено 13.11 15:02» (`sentAt`) |
| `reminder_failed` | `status = FAILED` | `INVALID_PHONE` → «Не отправлено: неверный номер телефона»; `GATEWAY_UNAVAILABLE` → «Не отправлено: SMS-шлюз недоступен» |
| `reminder_skipped` | `status = SKIPPED` | `OPTED_OUT` → «Не отправлялось: пациент отключил напоминания»; `BOOKED_LATE` → «Не отправлялось: запись сделана позже»; `APPOINTMENT_CANCELLED` → «Не отправлялось: запись отменена»; `WINDOW_PASSED` → «Не отправлялось: время напоминания прошло» |

`zero` и `empty` не применимы: в `reminders` всегда два элемента, `null` не бывает; `error_source` и загрузка блока — существующие состояния карточки записи.

### 4.3.1. Loading и таймауты (обязательно, если есть FE)
- **Таймаут cold-path:** 10 с — первое сохранение переключателя после открытия «Профиля» (INT-2).
- **Таймаут warm-path:** 5 с — повторные сохранения.
- Загрузка профиля (INT-1) и карточки записи (INT-3) — прежние таймауты экранов.
- **Polling:** нет — состояние напоминаний обновляется при открытии или обновлении карточки.
- Таймаут, 5xx, сеть на INT-2 → `reminders_error_save`.

### 4.4. Доступ по ролям в UI
- `PATIENT` — переключатель в своём «Профиле».
- `CLINIC_ADMIN` — блок «Напоминания» в карточке записи своей клиники.
- Другим ролям новые элементы не показываются.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- INT-1, INT-2, INT-3 — синхронно; кэша нет.
- Отправка — асинхронно, фоновой задачей раз в 5 минут; повторы — на следующих запусках, итого задержка при повторах — до 15 минут.
- Таймаут вызова шлюза — 10 с; до 10 одновременных отправок на экземпляр, до 30 на три экземпляра.
- 🔵 Шлюз принимает до 50 запросов в секунду (по карточке services/notify-gateway.md; валидировать при интеграции).
- Нагрузка: около 4 000 записей в сутки → до 8 000 SMS в сутки; в пиковый запуск утром — до 300 SMS.
- INT-3 добавляет один запрос по индексу `appointment_id`.

### 5.2. Надёжность/деградация
- Шлюз перегружен или недоступен → строка `RETRYING`, повторы на следующих запусках; после четвёртой неудачной попытки → `FAILED`, администратор видит «Не отправлено: SMS-шлюз недоступен» и звонит сам.
- При сбое вызова шлюза у нас остаётся записанным: строка напоминания со статусом `RETRYING` или `FAILED`, число попыток и `last_error`.
- Экземпляр упал посреди отправки → строка `SENDING` с истёкшим `locked_until` подхватывается шагом 2; дубля SMS нет — шлюз не отправляет повтор с тем же `clientMessageId`.
- БД недоступна → запуск задачи пропускается; следующий запуск догоняет напоминания, чьё окно ещё не закрылось.
- Флаг выключен дольше окна → напоминание не отправляется, в INT-3 — `SKIPPED` / `WINDOW_PASSED`; запоздалых SMS после включения нет.

### 5.3. Безопасность/доступ (сводно)
| Кто | INT-1 профиль | INT-2 переключатель | INT-3 карточка записи | INT-4 шлюз |
|-----|---------------|---------------------|-----------------------|------------|
| `PATIENT` | свой | свой | — | — |
| `CLINIC_ADMIN` | — | 403 | записи своей клиники | — |
| фоновая задача `booking-service` | — | — | — | сервисный токен |

## 6. Релиз и интеграция

### 6.1. Порядок выката
1. DDL-миграция БД `booking-service`: таблица `appointment_reminder`, столбцы в `patient`.
2. Деплой `booking-service` (бэк и веб одним артефактом) с выключенным флагом `reminders-sms-job`.
3. Проверка на staging с включённым флагом, затем включение флага в prod.

Миграция идёт раньше сервиса: новая версия читает новые таблицу и столбцы.

### 6.2. Обратная совместимость
- Миграция совместима с прежней версией сервиса: новая таблица ей не известна, новые столбцы `patient` имеют значение по умолчанию.
- INT-1, INT-3: поля только добавляются — прочие потребители ответов их игнорируют.
- INT-2: новая ручка.
- `notify-gateway`: используется существующий метод без изменений, его потребители не затронуты.
- Существующие SMS с кодом входа не меняются.

### 6.3. Фиче-флаги
- `reminders-sms-job` — `boolean`, по умолчанию выключен.
- Проверяется в начале каждого запуска фоновой задачи: выключен — запуск не выполняется; строки `RETRYING` ждут включения и после него отрабатывают, пока окно не закрылось.
- Переключатель в ЛК и блок в карточке записи флагом не скрываются: при выключенном флаге администратор видит фактическое состояние (`SCHEDULED` / `WINDOW_PASSED`).
- 🔵 Флаги `booking-service` переключаются в сервисе конфигурации без перезапуска (со слов; валидировать при интеграции); переключает команда «Запись» по согласованию с заказчиком.

### 6.4. План отката (обязательно, если задача деплоится — иначе «не применимо: причина»)
Основной откат — выключить флаг `reminders-sms-job`: отправка останавливается, данные и экраны остаются. Полный откат — предыдущая версия `booking-service`: переключатель и блок «Напоминания» пропадают вместе, таблица и столбцы остаются и прежней версией не читаются.
- ~~**Откат только BE** (FE на старой версии): не применимо — бэк и веб выкатываются и откатываются одним артефактом `booking-service`.~~
- ~~**Откат только FE**: не применимо — бэк и веб выкатываются и откатываются одним артефактом `booking-service`.~~
- **Откат DDL** (down-миграция): не планируется — таблица и столбцы остаются, прежняя версия их не читает; удаление потеряло бы историю напоминаний и выбор пациентов.
