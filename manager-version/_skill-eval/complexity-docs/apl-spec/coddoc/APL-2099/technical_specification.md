## 1. Обзор изменения

### 1.1. Что делаем и тип изменения
**Суть:** Клиенты, запрашивающие у `apollo-configservice` конфигурацию приватных namespace, теперь обязаны подтверждать подлинность подписанным ключом доступа (секретом); ключи заводит и включает/выключает/удаляет администратор приложения (роль Master) на новом экране в `apollo-portal`. Пока у приложения в окружении не включён ни один ключ, поведение не меняется; публичные namespace проверке не подлежат.
**Тип:** доработка (из шапки БТ §1.0)
**Стороны:** Fullstack — `apollo-configservice` (проверка ключа), `apollo-adminservice` (хранение ключей + новый API), `apollo-portal` (UI управления ключами). Клиентская SDK Apollo, которая должна отправлять подпись, — вне этой спеки (🟢 подтверждено В3): спека описывает только контракт, который SDK обязана соблюдать.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `apollo-configservice` | изменение существующих ручек раздачи (добавлена проверка ключа) | — | 🔵 подтверждено аналитиком (по карточке `services/apollo-configservice.md`) |
| `apollo-adminservice` | новый вызов: хранение ключей + новый CRUD API | — | 🔵 подтверждено аналитиком (по карточке `services/apollo-portal.md`, строка «Зависит от») |
| `apollo-portal` | изменение: новый экран управления ключами, вызывает `apollo-adminservice` | — | 🔵 подтверждено аналитиком (по карточке `services/apollo-portal.md`) |

### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель §2.1 БТ: ограничить получение конфигурации приватных namespace только клиентами с верным ключом, снижая риск утечки чувствительных настроек между приложениями и командами.

## 2. Взаимодействия (ядро)

### INT-1. Проверка ключа при раздаче конфигурации — 🟢 (изменение существующего)
- **Вид:** изменение существующего
- **Граница/направление:** Клиент Apollo (SDK, вне этой спеки) → `apollo-configservice`
- **Триггер:** запрос конфигурации приватного namespace любым из пяти способов (все пять — 🔵 подтверждено аналитиком, по карточке `services/apollo-configservice.md`, раздел «Публичный контракт»; правило применяется к ним одинаково):
  - `GET /configs/{appId}/{clusterName}/{namespace}`
  - `GET /configfiles/{appId}/{clusterName}/{namespace}`
  - `GET /configfiles/json/{appId}/{clusterName}/{namespace}`
  - `GET /notifications`
  - `GET /notifications/v2`
- **Существующий стык:** 🔵 — пять ручек выше (источник: `services/apollo-configservice.md`).
- **Изменение:**

| поле | где | было | стало |
|------|-----|------|-------|
| `Timestamp` | заголовок запроса | не было | добавлен: unix-время запроса в мс; обязателен, если у приложения в этом окружении включён хотя бы один ключ |
| `Authorization` | заголовок запроса | не было | добавлен: `Apollo <appId>:<подпись>`, обязателен при тех же условиях |
| HTTP-код ответа | ответ | 200 / 304 / 404 (как было) | добавлен `401` — неверная/отсутствующая подпись либо `Timestamp` старше 60 секунд от момента на сервере |

- **Контракт (запрос):** без изменения схемы тела — только два новых заголовка выше. Если у appId/окружения нет ни одного включённого ключа, заголовки не обязательны (FR-1).
- **Контракт (ответ):** без изменения схемы тела при успехе. При отказе — тело `{ "message": string }`, без указания, какой из нескольких включённых ключей не совпал.
- **Пример запроса:**
  ```
  GET /configs/100004458/default/application HTTP/1.1
  Timestamp: 1762598400000
  Authorization: Apollo 100004458:3k9Qd1m2h8vXyZl0pQe7rT4uI6oP9sA2bC5dE8fG1hJ=
  ```
- **Пример ответа (успех):** фрагмент — без изменений, прежняя схема (см. карточку `apollo-configservice.md`, `/configs`).
- **Пример ответа (отказ):**
  ```json
  { "message": "Invalid or missing access key signature" }
  ```
- **Ошибки:** см. «Каталог ошибок» в конце §2.
- ~~**Состояния UI по ответу:** не применимо — вызывающий клиент (SDK) вне этой спеки, состояний FE здесь не проектируем.~~
- **Авторизация:** право вызова не меняется (как и сейчас — знание appId достаточно для запроса); проверяется подлинность предъявленного секрета, а не роль. Негативный случай — неверный/просроченный/отсутствующий ключ → `401`.
- **Происхождение:** 🟢 изменение существующего (подтверждено В4, В5).
- **Трассировка:** FR-1, FR-3.

### INT-2. Управление ключами доступа приложения — 🟢 (новое)
- **Вид:** новое
- **Граница/направление:** `apollo-portal` (UI, роль Master) → `apollo-adminservice` (новый API)
- **Триггер:** действия администратора приложения (Master) на экране управления ключами в портале.
- **Контракт (запрос/ответ):**
  1. `POST /apps/{appId}/accesskeys` — создать ключ; тело запроса отсутствует; ответ — объект ключа.
  2. `GET /apps/{appId}/accesskeys` — список ключей приложения; ответ — массив объектов ключа.
  3. `PUT /apps/{appId}/accesskeys/{id}/enable` — включить; тело отсутствует; ответ — обновлённый объект ключа.
  4. `PUT /apps/{appId}/accesskeys/{id}/disable` — выключить; тело отсутствует; ответ — обновлённый объект ключа.
  5. `DELETE /apps/{appId}/accesskeys/{id}` — удалить (добавлено по В7); тело отсутствует; ответ — без тела, `204`.

  Поля объекта ключа: `id` (long), `appId` (string), `secret` (string, генерируется сервером случайно при создании, далее не меняется), `enabled` (bool), `dataChangeCreatedBy`/`dataChangeCreatedTime`, `dataChangeLastModifiedBy`/`dataChangeLastModifiedTime`.
- **Пример запроса (создание):**
  ```
  POST /apps/100004458/accesskeys
  ```
  (тело отсутствует)
- **Пример ответа (создание):**
  ```json
  {
    "id": 1,
    "appId": "100004458",
    "secret": "3f2504e0-4f89-11ee-be56-0242ac120002",
    "enabled": true,
    "dataChangeCreatedBy": "someuser",
    "dataChangeCreatedTime": "2026-11-08T10:00:00Z",
    "dataChangeLastModifiedBy": "someuser",
    "dataChangeLastModifiedTime": "2026-11-08T10:00:00Z"
  }
  ```
- **Ошибки:** см. «Каталог ошибок».
- **Состояния UI по ответу:** значение → список ключей с переключателем включён/выключен и кнопкой удаления; загрузка → спиннер списка; пусто/«—» → «У приложения пока нет ключей доступа» + кнопка «Создать»; ошибка → сообщение об ошибке + повтор.
- **Авторизация:** доступ — только Master приложения (подтверждено В2); проверка выполняется в `apollo-portal` перед вызовом `apollo-adminservice`, тем же способом, каким портал уже проверяет права на прочие операции уровня приложения перед их проксированием (🔵 подтверждено аналитиком, по карточке `services/apollo-adminservice.md`: «проверка прав выполняется до вызова, в apollo-portal»). Негативный случай — не-Master → `403`.
- **Происхождение:** 🟢 новое (подтверждено В1, В6, В7).
- **Трассировка:** FR-2.

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 401 | `{ "message": "Invalid or missing access key signature" }` | INT-1: неверная/отсутствующая подпись или `Timestamp` старше 60с | обрабатывается клиентом (SDK), вне этой спеки |
| 403 | `{ "message": "Forbidden" }` | INT-2: вызывающий не Master приложения | `error_forbidden` |
| 404 | `{ "message": "AccessKey not found" }` | INT-2: несуществующий `id` ключа в enable/disable/delete | `error_source` |

## 3. Backend — ответственность

### 3.1. По сервисам
- **`apollo-configservice`:** на каждый из пяти запросов конфигурации приватного namespace — проверяет наличие заголовков `Timestamp`/`Authorization`, пересчитывает подпись по каждому включённому ключу appId из локального кэша (§5.1), сравнивает, проверяет свежесть `Timestamp`. Публичные namespace не проверяются (без изменений). 🟢.
- **`apollo-adminservice`:** хранит сущность `AccessKey` (§3.2), отдаёт новый CRUD API (INT-2) без собственной проверки прав — доверяет вызывающему (`apollo-portal`), как и для прочих своих операций (🔵 по карточке `apollo-adminservice.md`, строка «без входа»). 🟢.
- **`apollo-portal`:** новый экран управления ключами; перед вызовом `apollo-adminservice` проверяет, что текущий пользователь — Master приложения. 🟢.

### 3.2. Данные и хранение
- [🟢] `AccessKey` — `id` (long), `appId` (string), `secret` (string), `enabled` (bool), `dataChangeCreatedBy` (string), `dataChangeCreatedTime` (timestamp), `dataChangeLastModifiedBy` (string), `dataChangeLastModifiedTime` (timestamp). Хранится в `apollo-adminservice`, в той же БД окружения, где уже хранятся app/cluster/namespace этого окружения (🔵 подтверждено аналитиком, по карточке `services/apollo-portal.md` — «проксируются ... по каждому активному окружению»); отдельного поля «окружение» не заводим — разделение по окружениям обеспечивается отдельным деплоем adminservice/БД на каждое окружение.
- Миграция: новая таблица, нужна. Точный DDL и синтаксис миграции финализирует `apollo-adminservice` (владеющий сервис).
- Старых строк нет — таблица новая, пересчитывать и дозаполнять нечего.
- Других новых/изменённых сущностей нет.

### 3.3. Авторизация/доступ на бэке
`apollo-adminservice` сам не проверяет права — доверяет вызову (см. §3.1, 🔵). `apollo-portal` проверяет Master перед каждым вызовом INT-2 (🟢). `apollo-configservice` проверяет подлинность ключа, а не роль, перед выдачей приватного namespace (🟢).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
`apollo-portal` — новый экран «Ключи доступа» в настройках приложения (рядом с существующими экранами управления namespace/консьюмерами), доступен только Master; вызывает INT-2.

### 4.2. Пользовательские сценарии
Master открывает экран → видит список ключей или пустое состояние → создаёт новый ключ (сервер генерирует `secret`, он показывается в ответе на создание — UI должен показать его сразу, повторно открытым текстом он не восстанавливается) → включает/выключает/удаляет любой из ключей. (FR-2)

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос списка ключей | спиннер |
| `value` | список ключей не пуст | список с переключателями включён/выключен и кнопкой удаления |
| `empty` | список ключей пуст | «У приложения пока нет ключей доступа» + кнопка «Создать» |
| `error_source` | 5xx/сеть при любой операции | сообщение об ошибке + повтор |
| `error_forbidden` | 403 (вызывающий не Master) | экран недоступен / «нет доступа» |

### 4.3.1. Loading и таймауты
Операции над ключами (создание/список/включение/выключение/удаление) — разовые CRUD-вызовы без долгого опроса; cold-path и warm-path таймауты не отличаются от прочих операций портала и этой задачей не меняются.

### 4.4. Доступ по ролям в UI
Экран «Ключи доступа» виден только Master приложения; остальным пользователям пункт меню не отображается (и защищён на API, §3.3).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- INT-1: синхронная проверка на каждый запрос. `apollo-configservice` держит в памяти кэш «включённые ключи по appId», обновляемый фоновым опросом БД с интервалом по умолчанию 1 секунда (по аналогии с `scanNewAppNamespaces`, карточка `apollo-configservice.md`); отдельная точечная инвалидация не требуется — опроса достаточно, задержка применения нового/выключенного/удалённого ключа — секунды. (подтверждено В8)
- INT-2: синхронный CRUD, без кэша на стороне `apollo-adminservice`/`apollo-portal`.

### 5.2. Надёжность/деградация
Если `apollo-configservice` не может прочитать/обновить кэш ключей (сбой БД, старт сервиса) — для appId, у которого в последнем известном состоянии кэша был хотя бы один включённый ключ, сервис отказывает (`401`), а не пропускает запрос молча: нельзя «открыть» приватный namespace по сбою кэша. Риск непрогретого кэша при старте — см. §8 «Технические риски».

### 5.3. Безопасность/доступ (сводно)
| Кто | Что может |
|---|---|
| Клиент с верным ключом и свежей `Timestamp` | получает приватный namespace как раньше |
| Клиент без ключа / с неверным ключом / с просроченной `Timestamp` | `401`, если у appId есть включённый ключ |
| Любой клиент | публичный namespace — без изменений |
| Master приложения | создаёт/включает/выключает/удаляет ключи своего приложения |
| Прочие пользователи портала | экран управления ключами не видят и не могут вызвать (`403`) |

## 6. Релиз и интеграция

### 6.1. Порядок выката
`apollo-adminservice` (миграция + новый API) → `apollo-configservice` (проверка) → `apollo-portal` (UI). Обратную совместимость для старых клиентов обеспечивает сам FR-1 (нет включённых ключей = нет изменений); строгий порядок между adminservice и configservice продиктован зависимостью API portal→adminservice. (подтверждено В9)

### 6.2. Обратная совместимость
Приложения без единого включённого ключа продолжают работать без изменений (FR-1, явно в БТ) — ломающих изменений для текущих потребителей нет.

### 6.4. План отката
- **Откат только BE** (`apollo-configservice` на старой версии, `apollo-adminservice`/`apollo-portal` — новые): ключи можно создавать и включать через портал, но `apollo-configservice` их не проверяет — приватные namespace временно раздаются без проверки (функциональный откат к состоянию «до задачи»); доступ клиентов не нарушается.
- **Откат только FE** (`apollo-portal` на старой версии, `apollo-configservice` — новый): экран управления ключами пропадает, но уже созданные/включённые ключи продолжают проверяться `apollo-configservice` как есть — временно управлять ими через UI нельзя.
- **Откат DDL** (down-миграция): удаление таблицы `AccessKey` эквивалентно выключению всех ключей — раздача не блокируется (FR-1 pass-through), но ранее включённые ключи перестанут приниматься. Down-миграцию выполнять после отключения/отката проверки в `apollo-configservice`, чтобы не получить переходных `401` у клиентов, уже настроивших секрет.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано приложение с включённым ключом, когда клиент запрашивает приватный namespace с верным ключом и `Timestamp` не старше 60с, тогда конфигурация отдаётся как сейчас (200); когда ключ неверный/отсутствует или `Timestamp` старше 60с, тогда 401 |
| FR-1 | INT-1 | Дано приложение без единого включённого ключа, когда клиент запрашивает конфигурацию, тогда она отдаётся без проверки (200, как раньше) |
| FR-1 | INT-1 | Дано запрос публичного namespace, когда клиент его запрашивает с любым ключом или без, тогда конфигурация отдаётся без проверки ключа |
| FR-2 | INT-2 | Дано приложение и Master, когда Master создаёт и включает новый ключ в портале, тогда ключ становится действителен для проверки в INT-1 наравне с уже включёнными |
| FR-2 | INT-2 | Дано включённый ключ, когда Master его выключает или удаляет, тогда он перестаёт приниматься при проверке (в течение интервала опроса кэша) |
| FR-3 | INT-1 | Дано секрет указан у клиента несколькими способами одновременно, когда клиент обращается за конфигурацией, тогда используется значение в порядке приоритета — параметр запуска, переменная окружения, файл свойств (реализует клиентская SDK, вне этой спеки; INT-1 требует только валидную подпись независимо от источника секрета на клиенте) |

  1. Карта сервисов и хранение ключей в `apollo-adminservice`; окружение — через отдельный деплой, без поля `env` (В1, по карточке `services/apollo-portal.md`).
  2. Роль управления ключами — Master приложения (В2).
  3. Клиентская SDK — вне спеки, только контракт (В3).
  4. Транспорт — HMAC-подпись в заголовках `Timestamp`/`Authorization` (В4).
  5. Код отказа INT-1 — `401` (В5).
  6. Секрет генерируется сервером при создании (В6).
  7. CRUD включает удаление ключа (В7).
  8. Кэш ключей в `apollo-configservice` с фоновым опросом БД (В8).
  9. Порядок выката без отдельного фиче-флага (В9).
  10. `apollo-adminservice` не проверяет права сам, доверяет вызову от `apollo-portal` (по карточке `services/apollo-adminservice.md`).
- **🟡 К валидации:** нет.
- **❓ Открытые решения:** нет.
- **⚠️ Требует уточнения:** нет.
- **Технические риски:**
  1. Расхождение часов клиента и сервера шире 60-секундного окна → легитимные запросы получат `401` → мера: задокументировать в контракте SDK требование синхронизации времени (NTP) на клиентских хостах.
  2. Непрогретый/недоступный кэш ключей в `apollo-configservice` при старте или сбое БД → риск временно пропустить проверку → мера: при недоступном кэше для appId с ранее известным включённым ключом — отказывать (`401`), не пропускать молча (§5.2).
