## 1. Введение и контекст
### 1.0. Тип изменения
Доработка существующего функционала: вход в listmonk через внешний OIDC-провайдер (SSO) уже настроен и работает; доработка — в настройках этого входа.

### 1.1. Описание проблемы
Войти в listmonk может только тот, кого администратор заранее завёл в системе вручную. Пользователей в SSO много, а их состав часто меняется (люди приходят и уходят), поэтому администратор регулярно тратит время на ручное создание учётных записей для каждого нового человека.

### 1.2. Конечные потребители
- Администратор listmonk — перестаёт тратить время на ручное создание пользователей.
- Люди из SSO (пример — команда около десяти человек с часто меняющимся составом) — получают доступ в listmonk сразу при первом входе, без обращения к администратору.

### 1.4. Как сейчас
Вход через SSO (OIDC) в listmonk настроен, но войти может только пользователь, которого администратор заранее завёл в listmonk руками. Если человека нет в списке пользователей listmonk, попытка входа через OIDC для него отклоняется, даже если он успешно прошёл аутентификацию в SSO.

## 2. Бизнес-требования (цели и ценность)
### 2.1. Бизнес-цель
Я как администратор listmonk должен иметь возможность разрешить автоматическое создание пользователей при входе через SSO, чтобы не заводить вручную каждого человека из SSO, состав которого часто меняется.

### 2.2. Ценность для бизнеса
Снижение ручной нагрузки администратора на создание пользователей и более быстрый доступ новых людей из SSO к listmonk. Пример масштаба — команда около десяти человек с частой сменой состава.

## 4. Функциональные требования
### 4.1. Описание функционала / бизнес-процесса
В настройках OIDC (раздел «Безопасность») администратор включает опцию «создавать пользователя автоматически, если его нет» и выбирает для неё роль по умолчанию. Без выбранной роли опцию включить нельзя. По умолчанию опция выключена — поведение входа не меняется, пока администратор не включит её явно.

Когда опция включена: человек успешно проходит аутентификацию во внешнем SSO и возвращается в listmonk через OIDC. Listmonk ищет пользователя с таким же e-mail.
- Если пользователь с таким e-mail уже есть — он просто входит под своей существующей учётной записью, ничего не создаётся повторно.
- Если пользователя с таким e-mail нет — listmonk создаёт для него учётную запись: обычный пользователь (не API-пользователь), сразу активный, логин — его e-mail, пароль не задаётся — входить он может только через OIDC. Этому пользователю назначается выбранная в настройках роль по умолчанию.

Когда опция выключена: поведение остаётся как сейчас — войти может только пользователь, заранее заведённый в listmonk вручную; для остальных вход отклоняется.

Требования:
- **FR-1.** В настройках OIDC появляется переключатель «создавать пользователя автоматически, если его нет», выключенный по умолчанию, и поле выбора роли по умолчанию.
- **FR-2.** Включить переключатель нельзя, если роль по умолчанию не выбрана.
- **FR-3.** При включённом переключателе и первом успешном входе через OIDC человека, чей e-mail не найден среди пользователей listmonk, система создаёт для него обычного, сразу активного пользователя без пароля (вход только через OIDC, логин — e-mail) и назначает ему роль по умолчанию.
- **FR-4.** Если пользователь с таким e-mail уже существует, повторное создание не происходит — он входит под существующей учётной записью.
- **FR-5.** При выключенном переключателе вход для не заведённых вручную пользователей отклоняется, как и сейчас.

### 4.5. Разбиение на части
Не применимо: все FR реализуют один неделимый механизм — переключатель без логики автосоздания ничего не делает, а роль по умолчанию без самого создания пользователя смысла не имеет. Выпустить что-то из этого по отдельности и получить от этого пользу бизнесу нельзя.
