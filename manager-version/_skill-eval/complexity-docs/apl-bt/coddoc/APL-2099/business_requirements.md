## 1. Введение и контекст

### 1.0. Тип изменения
Доработка существующего функционала раздачи конфигурации: добавление проверки подлинности клиента по ключу (секрету) при обращении к приватным namespace приложения, плюс управление этими ключами в портале.

### 1.1. Описание проблемы
Сейчас для получения конфигурации клиенту достаточно знать адрес сервиса и appId — различить настоящего (легитимного) клиента от поддельного нечем: любой, кто знает адрес сервиса и appId, может получить конфигурацию приложения, включая приватные namespace.

### 1.2. Конечные потребители
Приложения-клиенты, которые запрашивают свою конфигурацию по appId.

### 1.4. Как сейчас
Конфигурация раздаётся по appId, окружению и namespace без проверки личности вызывающего — любой, кто знает адрес сервиса и appId, получает полную конфигурацию, включая приватные namespace.

## 2. Бизнес-требования (цели и ценность)

### 2.1. Бизнес-цель
Я как администратор приложения должен иметь возможность ограничить получение конфигурации приватных namespace только клиентами с верным ключом, чтобы защитить чувствительные настройки приложения от доступа поддельных клиентов и посторонних команд.

### 2.2. Ценность для бизнеса
Снижение риска утечки чувствительных настроек между разными приложениями и командами, живущими в одном конфигурационном центре. Для компаний с требованиями безопасности отсутствие такой проверки может быть блокером при выборе конфигурационного центра. Дополнительно снижается риск там, где тестовые стенды открыты в интернет, и там, где при гибридном облаке связывание сетей дорого.

## 3. Объём проекта

### 3.1. Входит в проект
- Проверка ключа (секрета) при обращении к приватным namespace приложения — для всех способов получения конфигурации (обычный запрос, файл `.properties`, файл JSON, подписка на изменения).
- Управление ключами (создание, включение, выключение) администратором приложения в портале — отдельный набор ключей на каждое окружение приложения.
- Возможность иметь несколько одновременно включённых ключей на одно окружение приложения (чтобы заменить ключ без простоя — подходит любой из включённых).
- Настройка секрета на стороне клиентского приложения тем же способом, что и appId сейчас: параметром запуска, переменной окружения или файлом свойств.
- Отказ в выдаче конфигурации при неверном/отсутствующем ключе или просроченной временной метке запроса.

### 3.2. Не входит в проект
- Проверка доступа к публичным namespace — они продолжают отдаваться без проверки ключа.
- Автоматический срок действия ключа — управление только вручную (включение/выключение).
- Как именно ключ генерируется и хранится на сервере — это тех-спека.

### 3.3. Архитектурные изменения и интеграции
Затрагиваются сервис, который раздаёт конфигурацию (сама проверка при выдаче), и портал управления (администратор приложения заводит и включает ключи). Других интеграций не называлось.

## 4. Функциональные требования

### 4.1. Описание функционала / бизнес-процесса
**FR-1.** При запросе конфигурации приватного namespace сервер проверяет ключ (секрет), присланный клиентом, на совпадение с одним из включённых ключей, заведённых для этого приложения в этом окружении.
- Если у приложения в этом окружении нет ни одного включённого ключа — проверка не выполняется, конфигурация отдаётся как раньше (старые клиенты продолжают работать без изменений).
- Если ключ совпал с одним из включённых и временная метка запроса не старше минуты — конфигурация отдаётся как сейчас.
- Если ключ неверный или не указан, либо временная метка запроса старше минуты, — конфигурация не передаётся.
- Публичные namespace проверке не подлежат — отдаются как сейчас, без проверки ключа.
- Правило действует для всех способов получения конфигурации: обычный запрос, файл `.properties`, файл JSON, подписка на изменения (долгий опрос).

**FR-2.** Администратор приложения заводит и включает ключи для приложения в портале — отдельный набор ключей на каждое окружение приложения. У приложения в одном окружении может одновременно быть несколько включённых ключей (для замены без простоя). Ключи включаются и выключаются вручную, автоматического срока действия нет.

**FR-3.** Разработчик приложения указывает секрет на стороне клиента тем же способом, что и appId сейчас: параметром запуска (`-Dapollo.accesskey.secret`), либо переменной окружения (`APOLLO_ACCESSKEY_SECRET`), либо значением `apollo.accesskey.secret` в файле `/META-INF/app.properties` — в этом порядке приоритета.

### 4.2. Критерии приёмки
- **[FR-1]** Дано приложение в окружении с хотя бы одним включённым ключом; когда клиент запрашивает конфигурацию приватного namespace с верным ключом и временной меткой не старше минуты, тогда конфигурация отдаётся как сейчас. Дано то же приложение и окружение; когда клиент запрашивает конфигурацию приватного namespace с неверным/отсутствующим ключом или с временной меткой старше минуты, тогда конфигурация не передаётся. Дано приложение в окружении без единого включённого ключа; когда клиент запрашивает конфигурацию, тогда конфигурация отдаётся без проверки, как раньше. Дано запрос публичного namespace с любым ключом или без него; когда клиент его запрашивает, тогда конфигурация отдаётся без проверки ключа.
- **[FR-2]** Дано приложение и его окружение; когда администратор приложения заводит и включает в портале новый ключ, тогда этот ключ становится действителен для проверки в FR-1 наравне с уже включёнными. Дано включённый ключ; когда администратор его выключает, тогда он перестаёт приниматься при проверке.
- **[FR-3]** Дано секрет указан у клиента несколькими из трёх способов одновременно; когда клиент обращается за конфигурацией, тогда используется значение в порядке приоритета: параметр запуска, затем переменная окружения, затем файл свойств. Дано секрет не указан ни одним из трёх способов; когда клиент обращается за конфигурацией приватного namespace, тогда это равносильно неверному/отсутствующему ключу (FR-1).

### 4.3. Бизнес-данные

Доработка:

| № | Объект | Что это | Что меняется |
|---|--------|---------|--------------|
| 1 | Ключ доступа приложения | секрет, подтверждающий подлинность клиента при запросе конфигурации приватных namespace | новый объект: привязан к приложению и его окружению; может быть несколько одновременно включённых на одно окружение; включается/выключается администратором приложения вручную, без автоматического срока действия |
| 2 | Конфигурация приложения (namespace) | уже существующий набор настроек приложения, который раздаётся клиентам | для приватных namespace — теперь выдаётся только после проверки ключа (если хоть один ключ включён для этого приложения и окружения); публичные namespace — без изменений |

### 4.5. Разбиение на части
Не применимо: FR-1 (проверка на сервере), FR-2 (управление ключами в портале) и FR-3 (настройка секрета на клиенте) — звенья одного потока. Ни одно из них не даёт бизнесу защиты само по себе: без FR-2 ключ негде завести, поэтому проверка в FR-1 всегда остаётся отключённой; без FR-3 у легитимного клиента нет способа предъявить секрет, и включённый ключ просто блокирует всех. Выпустить можно только все три вместе.
