## 1. Обзор изменения

### 1.1. Что делаем и тип изменения
**Суть:** В карточке мероприятия веб-части `events-app` появляется кнопка «Выгрузить участников (CSV)», которую видит только организатор этого мероприятия: ответ карточки получает признак `canExportParticipants`. По нажатию бэк `events-app` синхронно отдаёт CSV-файл (ФИО, e-mail, тип билета, статус оплаты, дата покупки) через новую ручку `GET /api/v1/events/{eventId}/participants/export`; чужое мероприятие — 403, несуществующее — 404.
**Тип:** доработка
**Стороны:** Fullstack — бэк и веб в одном сервисе `events-app`: новое поле в ответе карточки мероприятия, новая ручка выгрузки и кнопка в карточке.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `events-app` | изменение: поле в ответе карточки мероприятия, новая ручка выгрузки, кнопка в веб-карточке | команда «Организаторы» (наша) | 🔵 подтв. аналитиком (по карточке services/events-app.md) |

### 1.3. Связь с бизнес-требованиями
Реализует цель БТ: организатор сам получает актуальный список участников своего мероприятия без обращения в поддержку, при этом ФИО и e-mail участников не уходят посторонним.

- **Граница/направление:** FE (веб `events-app`) → BE `events-app`
- **Триггер:** открытие карточки мероприятия
- **Существующий стык:** `GET /api/v1/events/{eventId}` → поля `id`, `title`, `startsAt`, `organizerId` — 🔵 подтверждено аналитиком (по коду events-app, ветка main; валидировать при интеграции)

  | `canExportParticipants` | ответ `GET /api/v1/events/{eventId}` | — (поля нет) | добавлено: `boolean`, обязательное, `null` не бывает; `true` — текущий пользователь вправе выгрузить участников этого мероприятия |

- **Контракт (запрос):** без изменений.
- **Контракт (ответ):** прежние поля без изменений + `canExportParticipants: boolean`.
- **Пример запроса:** тело отсутствует; `GET /api/v1/events/3f6c2a9e-1b4d-4c1e-9a77-0d2b5e8f4c10`

- **Ошибки:** без изменений (существующие 401 и 404 карточки).
- **Состояния UI по ответу (если есть фронт):** `true` → `export_idle`; `false` → `export_hidden`; остальные состояния карточки — без изменений.
- **Авторизация:** значение вычисляет бэк: `true` только если у пользователя роль `ORGANIZER` и `organizerId` мероприятия совпадает с его идентификатором; иначе `false`. Фронт сам права не вычисляет.

- **Трассировка:** FR-1

### INT-2. Выгрузка списка участников в CSV — 🟢
- **Вид:** новое
- **Граница/направление:** FE (веб `events-app`) → BE `events-app`
- **Триггер:** нажатие кнопки «Выгрузить участников (CSV)» в карточке мероприятия
- **Контракт (запрос):** `GET /api/v1/events/{eventId}/participants/export`
  - `eventId` — путь, `string` (UUID), обязательный;
  - заголовок `Accept: text/csv`; тела нет.
- **Контракт (ответ):**
  - `200 OK`, `Content-Type: text/csv; charset=utf-8`;
  - `Content-Disposition: attachment; filename="participants-<eventId>-<YYYY-MM-DD>.csv"` — дата выгрузки по часовому поясу мероприятия;
  - `X-Rows-Count: <int>` — число строк участников без строки заголовков; `0` — участников нет (валидный ноль);
  - тело: UTF-8 с BOM, разделитель `;`, перевод строки CRLF, экранирование по RFC 4180 (значение с `;`, `"` или переводом строки — в кавычках, `"` удваивается);
  - значения, начинающиеся с `=`, `+`, `-`, `@`, предваряются `'` — защита от исполнения формул при открытии файла;
  - первая строка — заголовки, порядок колонок фиксирован:

    | № | Заголовок | Источник значения | Формат |
    |---|-----------|-------------------|--------|
    | 1 | `ФИО` | владелец билета — ФИО | строка как введена при покупке |
    | 2 | `E-mail` | владелец билета — e-mail | строка |
    | 3 | `Тип билета` | название типа билета | строка |
    | 4 | `Статус оплаты` | статус заказа | `PAID` → «Оплачен», `PENDING` → «Ожидает оплаты», `REFUNDED` → «Возврат» |
    | 5 | `Дата покупки` | дата оформления заказа | `ДД.ММ.ГГГГ ЧЧ:ММ` в часовом поясе мероприятия |

  - одна строка на билет (участника); в выгрузку входят билеты с любым статусом заказа из перечисленных;
  - сортировка: по дате покупки по возрастанию, при равенстве — по ФИО;
  - пустых значений нет: ФИО и e-mail обязательны при покупке, тип билета и статус заказа есть у каждого билета.
- **Пример запроса:** тело отсутствует; `GET /api/v1/events/3f6c2a9e-1b4d-4c1e-9a77-0d2b5e8f4c10/participants/export`, `Accept: text/csv`
- **Пример ответа (успех):** `200`, `X-Rows-Count: 3`, `Content-Disposition: attachment; filename="participants-3f6c2a9e-1b4d-4c1e-9a77-0d2b5e8f4c10-2026-11-12.csv"`
  ```csv
  ФИО;E-mail;Тип билета;Статус оплаты;Дата покупки
  Иванова Анна Сергеевна;anna.ivanova@example.com;Стандарт;Оплачен;02.11.2026 14:05
  Петров Олег Игоревич;o.petrov@example.com;VIP;Ожидает оплаты;05.11.2026 09:41
  Смирнов Кирилл Андреевич;k.smirnov@example.com;Стандарт;Возврат;06.11.2026 18:20
  ```
- **Пример ответа (участников нет):** `200`, `X-Rows-Count: 0`
  ```csv
  ФИО;E-mail;Тип билета;Статус оплаты;Дата покупки
  ```
- **Ошибки:** тело ошибки — JSON, `Content-Type: application/json`:
  ```json
  {
    "error": {
      "code": "EXPORT_FORBIDDEN",
      "message": "Выгрузка доступна только организатору мероприятия"
    }
  }
  ```
  401 — нет сессии; 403 `EXPORT_FORBIDDEN`; 404 `EVENT_NOT_FOUND`; 500 `INTERNAL_ERROR` — см. «Каталог ошибок».
- **Состояния UI по ответу (если есть фронт):** значение → `export_done`; `X-Rows-Count: 0` → `export_zero`; загрузка → `export_loading`; 403 → `error_forbidden`; 404 → `error_not_found`; 5xx / таймаут / сеть → `error_source`.
- **Авторизация:** нужна сессия пользователя (иначе 401); мероприятия нет или оно удалено → 404 (проверяется первым); роль `ORGANIZER` и совпадение `organizerId` с текущим пользователем → иначе 403. Проверка — на бэке, в обработчике ручки; скрытая кнопка защитой не считается.
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-2, FR-3, FR-4

### Каталог ошибок (сводно) — последний подраздел §2, после всех INT-карточек
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 401 | существующий ответ `events-app` без сессии | пользователь не вошёл | существующий переход на вход |
| 403 | `EXPORT_FORBIDDEN` — «Выгрузка доступна только организатору мероприятия» | нет роли `ORGANIZER` или пользователь не организатор этого мероприятия | `error_forbidden` |
| 404 | `EVENT_NOT_FOUND` — «Мероприятие не найдено» | мероприятия нет или оно удалено | `error_not_found` |
| 500 | `INTERNAL_ERROR` — «Не удалось сформировать файл, повторите позже» | ошибка чтения из БД или формирования файла | `error_source` |

## 3. Backend — ответственность

### 3.1. По сервисам
`events-app` (бэк):
- 🟢 INT-1: в ответ `GET /api/v1/events/{eventId}` добавить `canExportParticipants` по правилу из INT-1.
- 🟢 INT-2: новая ручка выгрузки:
  1. найти мероприятие по `eventId`; нет или удалено → 404 `EVENT_NOT_FOUND`;
  2. проверить роль `ORGANIZER` и `organizerId` → иначе 403 `EXPORT_FORBIDDEN`;
  3. одним запросом прочитать билеты мероприятия с типом билета и заказом, отсортировать по дате покупки и ФИО;
  4. собрать CSV целиком в памяти (до 5 000 строк — порядка 1 МБ) и только после этого начать ответ: при ошибке на шагах 3–4 клиент получает 500, а не обрезанный файл;
  5. проставить `Content-Disposition` и `X-Rows-Count`.
- Правило «кто организатор» общее для INT-1 и INT-2 — одна функция проверки, чтобы кнопка и ручка не разошлись.
- 🔵 Мероприятие удалено — признак `deletedAt` не пустой (по коду events-app, ветка main; валидировать при интеграции).

### 3.2. Данные и хранение
Новых сущностей нет; новых полей и миграций нет; старые записи не меняются, пересчёт не нужен. Ручка только читает:
- 🔵 `Event` — `id` (uuid), `organizerId` (string), `timezone` (string, IANA), `deletedAt` (timestamp|null) — подтверждено аналитиком (по коду events-app, ветка main; валидировать при интеграции)
- 🔵 `Ticket` — `id` (uuid), `eventId` (uuid), `ticketTypeId` (uuid), `orderId` (uuid), `holderFullName` (string, обязательное), `holderEmail` (string, обязательное) — подтверждено аналитиком (по коду events-app, ветка main; валидировать при интеграции)
- 🔵 `TicketType` — `id` (uuid), `name` (string) — подтверждено аналитиком (по карточке services/events-app.md; валидировать при интеграции)
- 🔵 `Order` — `id` (uuid), `status` (`PAID` | `PENDING` | `REFUNDED`), `createdAt` (timestamp, дата оформления заказа) — подтверждено аналитиком (по коду events-app, ветка main; валидировать при интеграции)
- 🔵 Индекс по `Ticket.eventId` уже есть — подтверждено аналитиком (со слов; валидировать при интеграции). Новых индексов не требуется.

### 3.3. Авторизация/доступ на бэке
- 🔵 Аутентификация — существующая сессия `events-app`; без сессии ручки отвечают 401 (со слов; валидировать при интеграции).
- 🔵 Роль `ORGANIZER` уже есть и выдаётся пользователям-организаторам (по карточке services/events-app.md; валидировать при интеграции).
- 🟢 Новая проверка в INT-2: роль `ORGANIZER` И `Event.organizerId` = идентификатор текущего пользователя.
- Негативные случаи: организатор другого мероприятия → 403; пользователь без роли → 403; удалённое мероприятие → 404 и для организатора этого мероприятия.
- 404 отдаётся раньше 403: существование мероприятия не секрет — страницы продаж публичны.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
- 🔵 Экран «Карточка мероприятия» веб-части `events-app`, блок «Продажи» с числом проданных билетов по типам (со слов; валидировать при интеграции).
- 🟢 В блок «Продажи» добавляется кнопка «Выгрузить участников (CSV)»; показывается при `canExportParticipants = true` (INT-1).
- 🟢 Нажатие вызывает INT-2; ответ 200 сохраняется браузером как файл с именем из `Content-Disposition`.

### 4.2. Пользовательские сценарии
- Основной (FR-1, FR-2): организатор открывает карточку своего мероприятия → видит кнопку → нажимает → файл скачивается, тост об успехе.
- Участников нет (FR-2): файл только с заголовками, тост «Участников пока нет — в файле только заголовки».
- Нет прав (FR-3): права отозвали, пока карточка была открыта, → 403 → сообщение, кнопка скрывается.
- Мероприятие не найдено (FR-4): мероприятие удалили, пока карточка была открыта, → 404 → сообщение.
- Сбой: 5xx / таймаут → сообщение и кнопка «Повторить».

### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `export_hidden` | `canExportParticipants = false` | кнопки нет |
| `export_idle` | `canExportParticipants = true`, выгрузка не запущена | активная кнопка «Выгрузить участников (CSV)» |
| `export_loading` | запрос INT-2 выполняется | кнопка неактивна, спиннер, «Формируем файл…» |
| `export_done` | 200, `X-Rows-Count` > 0 | файл скачан; тост «Список участников скачан» |
| `export_zero` | 200, `X-Rows-Count` = 0 | файл скачан; тост «Участников пока нет — в файле только заголовки» |
| `error_forbidden` | 403 `EXPORT_FORBIDDEN` | «Выгрузка доступна только организатору мероприятия»; кнопка скрывается |
| `error_not_found` | 404 `EVENT_NOT_FOUND` | «Мероприятие не найдено» |
| `error_source` | 5xx / таймаут / сеть | «Не удалось сформировать файл» + кнопка «Повторить» |

`empty` не применимо: пустой список — валидный ноль участников (`export_zero`); `null` в ответе не бывает.

### 4.3.1. Loading и таймауты (обязательно, если есть FE)
- **Таймаут cold-path:** 30 с — первая выгрузка после открытия карточки.
- **Таймаут warm-path:** 20 с — повторная выгрузка из той же карточки.
- **Polling:** нет — выгрузка разовая по нажатию.
- Таймаут, 5xx, сетевая ошибка → `error_source`; повторное нажатие во время `export_loading` невозможно — кнопка неактивна.

### 4.4. Доступ по ролям в UI
- Организатор (`ORGANIZER`) своего мероприятия — кнопка видна.
- Организатор чужого мероприятия, пользователь без роли `ORGANIZER` — кнопки нет (`canExportParticipants = false`).
- Решение о показе — только по полю из INT-1; роли на фронте не сравниваются.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- Синхронно: файл формируется в ответе на запрос, без очереди и фоновых задач.
- Кэша нет — каждый раз актуальные данные.
- Объём: до 5 000 строк; время ответа p95 ≤ 3 с на 5 000 строк.
- Нагрузка: до 200 выгрузок в сутки, в пике — единицы в минуту.
- Таймауты фронта — §4.3.1.

### 5.2. Надёжность/деградация
- БД недоступна или запрос упал → 500 `INTERNAL_ERROR`, пользователь видит `error_source` и повторяет.
- Обрезанного файла не бывает: CSV собирается целиком до начала ответа (§3.1).
- Операция только читает данные: при сбое ничего не остаётся записанным.

### 5.3. Безопасность/доступ (сводно)
| Кто | Кнопка в карточке (INT-1) | Выгрузка (INT-2) |
|-----|---------------------------|------------------|
| `ORGANIZER`, организатор этого мероприятия | видна | 200 |
| `ORGANIZER`, организатор другого мероприятия | нет | 403 |
| пользователь без роли `ORGANIZER` | нет | 403 |
| без сессии | — | 401 |

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано пользователь с ролью `ORGANIZER`, `organizerId` мероприятия А = его id, когда открывается карточка А, тогда `canExportParticipants = true` и кнопка видна; дано тот же пользователь открывает карточку мероприятия Б другого организатора — `false`, кнопки нет; дано пользователь без роли `ORGANIZER` — `false`, кнопки нет |
| FR-2 | INT-2 | Дано у мероприятия А 3 билета (статусы заказов `PAID`, `PENDING`, `REFUNDED`), когда организатор А вызывает выгрузку, тогда 200, `X-Rows-Count: 3`, CSV с заголовками и 3 строками в порядке даты покупки, статусы «Оплачен», «Ожидает оплаты», «Возврат»; дано 5 000 билетов — 5 000 строк, ответ ≤ 3 с; дано билетов нет — 200, `X-Rows-Count: 0`, только строка заголовков |
| FR-3 | INT-2 | Дано пользователь не организатор мероприятия А, когда он вызывает `GET /api/v1/events/{A}/participants/export`, тогда 403 `EXPORT_FORBIDDEN`, CSV не отдаётся |
| FR-4 | INT-2 | Дано `eventId` несуществующего мероприятия или мероприятия с заполненным `deletedAt`, когда организатор вызывает выгрузку, тогда 404 `EVENT_NOT_FOUND` |
