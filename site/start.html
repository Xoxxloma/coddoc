Установка и первая задача

Что поставить, где взять контекст системы и как провести первую задачу до спеки.

Что нужно

  • Репозиторий AI-SDD. В нём живут документы задач (coddoc/) и контекст системы (services/, context/). Если у команды он уже есть — склонируйте его. Если нет — заведите пустой git-репозиторий и рядом склонируйте репозитории сервисов системы: их будет читать service-map. Работа над задачей идёт в папке AI-SDD, кодовая база не нужна.
  • git и bash (macOS, Linux) или PowerShell (Windows) — для обновления скиллов, to-html и services-graph.
  • Python — только для плагинов peek, work-plan, retro и coddoc-settings. Основному процессу он не нужен.

Установка и обновление

  1. Поставить

    Скопируйте все папки скиллов в .gigacode/skills/ — в папке AI-SDD или в глобальной. В GigaCode Desktop: Навыки → Загрузить навык → SKILL.md.

  2. Обновлять

    Из чата:

    /analyst-skills-update

    Скилл analyst-skills-update запускает скрипт из своей папки reference/ (skills.sh, на Windows — skills.ps1), подтягивает свежие версии в .gigacode/skills/ и показывает список установленных. Нужен доступ к репозиторию со скиллами, как для git clone; если по https не пускает, скрипт пробует ssh-ключ.

Контекст системы

Карточки сервисов в services/ снимаются по коду, документы вне кода лежат в context/. Их читают скиллы процесса, чтобы спрашивать про вашу систему, а не вообще.

В services/ уже есть карточкиПропустите этот шаг: их сняли коллеги. Обновляют их после релиза соседнего сервиса или когда появился новый — это делает archive-spec или /service-map по имени сервиса.
Карточек нет — снять с нуля
  1. Рядом с AI-SDD склонируйте репозитории сервисов системы.
  2. В AI-SDD на ризонинг-модели: /service-map. До шести сервисов идут параллельно; если их больше десяти — по именам: /skills service-map auth geo. Плохая карточка — перечитайте сервис по имени, карточка перезапишется целиком.
  3. В services/manifest.yaml — состав сервисов и notes: договорённости вне кода, они переносятся в карточку дословно.
  4. Документы вне кода: /context-doc путь/к/файлу (txt, docx, pdf, xlsx, папка или текст из чата). Строка description обязательна — без неё файл не найдут.
  5. Запушьте AI-SDD.

Без контекста скиллы работают, но вопросы будут общие, не про вашу систему, и варианты ответов агент придумает сам.

Первая задача

Перед каждым шагом — /clear: переписка прошлого шага портит ответы следующего.

  1. 1Ветка под задачу

    git checkout -b feature/DORM-101

  2. 2Запустить процесс

    /analyst-workspace

    На старте четыре варианта: «Бизнес: Переводим Идею в БТ, баг — в баг-репорт, правку — в запрос», «Аналитика: Создаем Спецификацию на основе готового документа», «Продолжить начатое», «Доработка готова — обновить описание сервисов». Для новой задачи — «Бизнес»; дальше скилл спросит, идея это, дефект или правка.

  3. 3Ответить на вопросы

    Скилл ведёт интервью и пишет документ-источник в coddoc/<КЛЮЧ>/: business_requirements.md, bug_report.md или change_request.md. Чего вы не знаете — попадает в открытые вопросы.

  4. 4Приёмка документа

    Запускается сама. Прочитайте документ и замечания, решите, что дальше, — варианты ниже.

  5. 5Спека

    «Идти дальше» после приёмки ведёт к спеке. Если спеку пишет другой человек, он берёт ветку и запускает /analyst-workspace → «Аналитика» с путём к документу. Скилл technical-spec-doc пишет technical_specification.md рядом с документом-источником.

  6. 6Приёмка спеки и «Что дальше?»

    После приёмки — четыре варианта: «Проверить спеку», «Доработать спеку», «Разбить на этапы», «Начать другую задачу».

  7. 7Проверить спеку

    Исполнитель, архитектор сервиса и безопасник читают спеку параллельно; в чат приходит один список критичных вопросов, на которые она не отвечает. Ответьте на них и выберите «Доработать спеку». Между проверкой и доработкой /clear не делайте: список живёт только в переписке.

  8. 8Передать исполнителю

    Запушьте ветку и передайте её разработчику — и номер этапа, если нарезали этапы.

    git push origin feature/DORM-101

    Разработчик в AI-SDD делает git pull && git checkout feature/DORM-101 и работает по technical_specification.md или своему stages/stage-NN.md. Не хватает чего-то в документе — возвращается к аналитику, сам не дописывает.

  9. 9Когда фича вышла в прод

    Подтяните свежий код затронутых сервисов и запустите /analyst-workspace → «Доработка готова — обновить описание сервисов» (или /archive-spec <КЛЮЧ>). archive-spec перечитает затронутые сервисы, допишет историю карточек и пометит спеку архивной. Так следующая задача прочитает уже обновлённые карточки.

Если приёмка вернула замечания

Приёмка — второй агент с чистым контекстом: он не видел интервью и черновиков. Он сверяет документ с правилами, записанными в шаблоне, и к каждому замечанию даёт цитату и номер строки. Хорошо ли решение, он не оценивает — это ваша работа.

После БТ, баг-репорта или запроса на правку analyst-workspace всегда задаёт один вопрос — это гейт. Решение за вами:

  • «Поправить документ сейчас» — есть, только если остались замечания или открытые вопросы. Возврат в интервью того же скилла; новую редакцию приёмка проверит снова.
  • «Идти дальше» — явное принятие. Открытые вопросы перейдут в раздел 8 спеки и её статус не заблокируют; замечания останутся в документе.
  • «Пока остановиться» — документ лежит на диске, вернуться можно через «Продолжить начатое».

После спеки отдельного гейта нет: приёмка пишет «нарушений нет» или список, дальше — «Что дальше?», где есть «Доработать спеку».

Три правила

  • Перед каждым шагом — /clear: перед БТ, перед спекой, перед архивацией и при переключении между задачами.
  • Список замечаний приёмки передавайте как есть, с цитатами и номерами строк. Замечаний много — выберите «Поправить документ сейчас», а не правьте руками.
  • /analyst-workspace --no-review выключает приёмку на всю сессию. Гейт с вопросом остаётся и считается по открытым вопросам.
