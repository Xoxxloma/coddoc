# Фреймворк coDDoc: туториал по сценариям

Аналитический фреймворк — набор скиллов, которые ведут задачу от идеи, дефекта или мелкой правки до `technical_specification.md`. Спека — конечный продукт: по ней пишет код разработчик или агент. Всё живёт в репозитории **AI-SDD**: карточки сервисов в `services/`, ваши документы в `context/`, задачи в `coddoc/<КЛЮЧ>/`.

## Как выглядит настроенный репозиторий

Три папки: `context/` — контекст, `services/` — отсканированные сервисы, `coddoc/` — задачи. Репозитории сервисов лежат рядом с AI-SDD, на одном уровне.

```
рабочая папка/
├── AI-SDD/
│   ├── context/                          # контекст: то, чего нет в коде
│   │   ├── api-guidelines.md             #   один файл — одна тема, у каждого description
│   │   ├── glossary.md
│   │   └── roles.md
│   ├── services/                         # отсканированные сервисы
│   │   ├── manifest.yaml                 #   список сервисов и notes
│   │   ├── auth.md                       #   карточка: один сервис — один файл
│   │   └── geo.md
│   └── coddoc/                           # задачи: одна задача — одна папка с ключом
│       ├── SMSEC-12345/                  # новый функционал/новая фича
│       │   ├── business_requirements.md
│       │   ├── technical_specification.md
│       │   ├── stages/                   #   необязательно: этапы для нескольких исполнителей
│       │   │   ├── index.md
│       │   │   ├── stage-01.md
│       │   │   └── stage-02.md
│       │   └── .archived                 #   метка: уехало в прод, карточки обновлены
│       ├── SMSEC-12400/                  # дефект
│       │   ├── bug_report.md
│       │   └── technical_specification.md
│       ├── SMSEC-12410/                  # мелкая правка
│       │   ├── change_request.md
│       │   └── technical_specification.md
│       └── SMSEC-12500/                  # эпик
│           ├── business_requirements.md  #   БТ эпика, спека по нему не пишется
│           ├── decomposition.md          #   кто из детей каким требованием владеет
│           ├── _foundation/              #   фундамент #0, если есть: только спека
│           │   └── technical_specification.md
│           ├── SMSEC-12501/              #   ребёнок: свой БТ и своя спека
│           │   ├── business_requirements.md
│           │   └── technical_specification.md
│           └── SMSEC-12502/
│               ├── business_requirements.md
│               └── technical_specification.md
├── auth/                                 # репозитории сервисов: нужны для service-map и архивации
└── geo/
```

## Общие правила

- **Одна задача — одна ветка, в имени ветки обязателен ключ задачи.** Префикс — как принято у вас по процессу. В примерах ниже — `feature/`. Ветка ходит между владельцем продукта, аналитиком и разработчиком.
- **Каждый этап — с чистого контекста**: новая сессия, либо `/clear` в текущей. Перед БТ, перед спекой, перед архивацией, при переключении задач. Переписка прошлого этапа портит следующий.
- **Точка входа — `/analyst-workspace`.** Скилл сам спрашивает, что у вас на руках, и сам зовёт нужный под-скилл. Имена под-скиллов знать не нужно.
- **Приёмка автоматическая.** После каждого записанного документа его читает агент с чистым контекстом и возвращает список нарушений. Много нарушений — выбирайте «Доработать», не правьте руками: на новую редакцию запустится новая приёмка.
- **`/analyst-workspace --no-review`** выключает приёмку на всю сессию. Отключается только проверка структуры готового документа. Проверка каждого пункта по ходу интервью и гейт по статусу остаются.
- **Прерванная работа** — `/analyst-workspace` → «Продолжить начатое».
- **Коммит и пуш делаете вы.** Скиллы ничего в git не меняют, `deep-search` только читает историю.
- Модель DeepSeek-V4-Flash, effort `high` и выше. Кодовая база рядом нужна для `service-map`, архивации и `deep-search` — ответа «как сейчас работает» по коду и «откуда это взялось» по истории git. Для истории клон нужен полный: в обрезанном `deep-search` её не читает и подскажет `git fetch --unshallow`.

## Сценарий 1. Собрать карточки сервисов: `service-map`

Делается один раз при старте и точечно после релизов.

1. Склонируйте репозитории сервисов рядом с AI-SDD, на одном уровне.
2. В AI-SDD: `/service-map`. Скилл найдёт соседние репозитории, спросит, какие читать, и напишет `services/manifest.yaml` и по карточке `services/<имя>.md`.
3. Прочитайте каждую карточку и сверьте с тем, что знаете о сервисе: назначение, что он умеет для пользователя, бизнес-правила, контракты, события, зависимости. Если карточка неполная или с ошибками, перечитайте сервис по имени: `/service-map auth geo`. Повторный скан перезаписывает карточку целиком, но опирается на прежнюю: там, где факты не изменились, он сохраняет старые формулировки. Поэтому если после повторного скана карточка вышла хуже или её части исказились, удалите файл карточки и отсканируйте сервис с нуля, как в первый раз.
4. В `manifest.yaml` заполните `notes`: договорённости, которых нет в коде. Они переносятся в карточку дословно.
5. Закоммитьте `services/`.

Ограничения:

- До пяти сервисов за один запуск. Больше — по именам, партиями: `/service-map auth geo billing`. Партии можно гнать параллельно в нескольких окнах, каждая пишет свои карточки.
- `--refresh` перечитывает все сервисы из манифеста. Без аргументов — только те, у кого карточки ещё нет.
- Карточка пишется только по коду. То, что из кода не выводится (например, роли проставляет шлюз, расписание задано вне репозитория), скилл не достраивает по аналогии, а помечает строкой `не определено` и пишет, где это искать. Знаете ответ сами — впишите его в `notes` манифеста.
- Если новый скан потерял заметную часть старой карточки (в одном разделе пропало три и больше пунктов и это больше трети), скилл не пишет поверх, а кладёт кандидата в `services/_pending/`. В отчёте об этом строка `ГАРД` с числами и именами пропавшего. Проверьте по коду: это действительно удалили — переместите файл из `_pending/` в `services/` поверх старой карточки; скан не дочитал — удалите кандидата и пересканируйте сервис.

### Переезд со старого бизнес-контекста

Новая версия `service-map` пишет бизнес-описание сервиса прямо в его карточку. Отдельная папка `business_context/` больше не нужна. Если ваш бизнес-контекст устарел и требует обновления — сразу переходите на новый вид.

1. Пересканируйте сервисы новой версией скилла. Бизнес-описание появится внутри каждой карточки.
2. Прочитайте карточки. Если описание сервиса стало хуже прежнего, удалите файл карточки и отсканируйте сервис с нуля.
3. Когда все карточки переведены на новый вид, удалите папку `business_context/`.
4. Уберите из `GIGACODE.md` инструкции, связанные с бизнес-контекстом.

Шаги 3 и 4 — только после полного перехода на новый вид.

## Сценарий 2. Положить свои заметки: `context-doc`

В `context/` лежит то, чего нет в коде: регламенты, глоссарий, договорённости с внешними командами, правила оформления API. Эту папку читают скиллы БТ и спеки.

1. `/context-doc путь/к/файлу`. Форматы: txt, md, csv, json, html, pdf, docx, xlsx, папка или текст прямо в чате. Если настроен MCP-сервер Confluence, так же читаются и его страницы: `/context-doc <ссылка на страницу>`.
2. Скилл переносит содержимое дословно и предлагает строку `description`. Утвердите или поправьте её.
3. Один документ — одна тема. Сборный регламент режется на несколько файлов, каждый со своим описанием.
4. Положили файл руками — запустите `/context-doc` без аргументов. Он найдёт файлы без `description` и допишет её.

Почему `description` обязательна: скиллы ищут контекст одним грепом по этой строке. Файл без неё и не-`.md` файл для фреймворка не существуют.

**Правила оформления в `context/` улучшают спеку.** Когда в спеке проектируются новые контракты и сервисы, скилл сверяет их с правилами из `context/`: форма пути, коды ошибок, формат дат, именование полей, семантика `null`. Если нет такого файла, каждый аналитик получает свой стиль. Положите туда стандарты API, архитектурные соглашения, правила именования. Правило применяется ровно к тому решению, которое оно называет: правило про таймаут не задаёт интервал опроса. Пишите правила конкретно.

Правила из `context/` применяются молча и с кодом не сверяются. Держите папку актуальной.

## Сценарий 3. Новый функционал/новая фича: ветка БТ

Самый длинный маршрут. Обязательных шагов два: сначала пишется БТ, потом по нему спека. Ещё три шага нужны не всегда, каждый разобран ниже:

- большой БТ режется на несколько детских, и спека пишется на каждого ребёнка;
- если детям нужна общая основа, сначала на неё пишется отдельная спека — фундамент #0;
- готовая спека делится на этапы, когда работу раздают нескольким исполнителям.

### Написать БТ

**Роль:** владелец продукта или бизнес-аналитик. Может быть и разработчик.

1. `git checkout -b feature/SMSEC-12345`.
2. `/analyst-workspace` → «Бизнес» → «идея / новая возможность».
3. Первым вопросом скилл спросит ключ задачи. Без ключа файл не пишется.
4. Отвечайте на вопросы. Скилл спрашивает гипотезой: предлагает вариант, вы подтверждаете или поправляете. То, что вы уже сказали, он не переспрашивает.
5. Получаете `coddoc/SMSEC-12345/business_requirements.md` и отчёт приёмки. Прочитайте документ.
6. `git push`, ветку передаёте аналитику.

### Написать спеку по БТ

**Роль:** системный аналитик. Может быть и разработчик.

1. `git pull && git checkout feature/SMSEC-12345`.
2. Новая сессия или `/clear`, затем `/analyst-workspace` → «Аналитика», путь к БТ.
3. Скилл прочитает в БТ раздел о разбиении и решит, резать ли на детей (см. ниже).
4. **Пишется `technical_specification.md`. Это главная часть всей работы:** спека — конечный продукт, по ней пишут код. Скилл спрашивает о технических решениях гипотезой: предлагает вариант, вы подтверждаете или поправляете. От точности ваших ответов зависит качество спеки, не торопитесь. Когда файл записан, внимательно прочитайте спеку целиком и отчёт приёмки.
5. Скилл спросит «Что дальше?»: проверить спеку, доработать, разбить на этапы, начать другую задачу. Порядок вариантов всегда один, после каждого из первых трёх вопрос вернётся.
6. «Проверить спеку» (Сценарий 6) → ответьте на вопросы проверки → «Доработать спеку». Между ними `/clear` не делайте: вопросы живут только в переписке.
7. Делите работу между исполнителями — «Разбить на этапы» (см. ниже).
8. Закоммитьте и запушьте изменения.

### Когда БТ бьётся на детей

Большой БТ можно разрезать на несколько детских: каждый ребёнок выпускается отдельно и сам по себе приносит бизнес-ценность. Разрез агент только предлагает. Последнее слово за вами: скажете «разбей» или «не надо», так и будет.

**Когда агент предложит разрез.** БТ считается эпиком в одном из двух случаев:

- в БТ описаны две и более самостоятельные фичи, каждую из которых можно зарелизить отдельно;
- в БТ четыре и более требования, и они про разные куски функциональности, каждый со своей ценностью.

Если ни одно условие не выполнено, БТ считается одной фичей и идёт в спеку целиком.

**Когда разрез не делается.** Единственная настоящая причина: результат один, ни одну часть нельзя выпустить отдельно и получить от неё ценность. Отдельно есть технический минимум: в БТ меньше двух требований. Тогда декомпозиция откажет и отправит писать спеку напрямую.

Что не является доводом против разреза:

- Общая бизнес-цель. Это определение эпика, а не возражение.
- Общий источник данных, общий сервис, общий UI-модуль. Это признак фундамента #0, а не повод слепить всё в одну фичу.

Ключи детей спрашиваются уже после того, как вы согласились с разрезом и увидели состав каждого ребёнка. В этот момент заведите подзадачи в трекере, по одной на ребёнка, и назовите их ключи. Плейсхолдеры не принимаются: ребёнок без ключа не записывается.

Каждый ребёнок — самостоятельный БТ в `coddoc/<ЭПИК>/<РЕБЁНОК>/`, с требованиями, скопированными из родителя дословно. Если одно требование нужно сразу двум детям, оно записывается только в одного из них. Второй ребёнок помечается как зависящий от первого и делается после него. Сквозное требование в обоих детях — только по вашему явному решению, и это риск: две спеки спроектируют для него два контракта.

### Фундамент #0

После разреза скилл читает детей и ищет общий источник: ≥2 ребёнка опираются на одну сущность, сервис или справочник. Если такой источник есть, скилл предложит узел #0: отдельную спеку, в которой общая часть описана один раз. Дети берут её контракт готовым и не меняют.

- У #0 своего БТ нет. Это слой реализации, интервью по бизнес-требованиям на него не будет.
- Спека #0 пишется первой, потом дети.
- Если общего источника у детей нет, фундамент не нужен: скилл его не предложит, и на каждого ребёнка сразу пишется спека.

### Когда спеку можно разбить на этапы

Этапы `stages/stage-NN.md` — необязательный шаг: вариант «Разбить на этапы» в вопросе «Что дальше?» после готовой спеки. Единственная причина его выбрать: **работу делят между несколькими исполнителями**, людьми или агентами, и каждому нужен свой файл задачи.

Разрез считается механически, по контрактам, которые строит спека: API и события с меткой 🟢 — новые и изменённые — и новые сущности. Отсюда следствия:

- **Ни одного нового или изменённого контракта** (чисто фронтовая доработка, правка без изменения API) — «не применимо». Штатный исход, не ошибка.
- **Один контракт — один этап.** Например, мелкая правка, которая добавила поле в ответ. Файл будет, но раздавать нечего.
- **Независимые контракты — разные этапы**, даже если их отдаёт один сервис из одной таблицы.
- **По границе фронт/бэк не режется никогда.** У фронтовой стороны контракта нет своего выхода.
- **Потребление существующего (🔵/🟡) и контракт #0** — вход извне: эта работа их не меняет. Своего этапа под них нет.
- Открытые пункты в спеке разрезу не мешают, но могут его потом изменить.
- «Один этап на всё» допустимо, но ничего не даёт: получите «не применимо».

Не режьте «на всякий случай»: каждый этап — копия куска спеки. Правка спеки после нарезки означает правку всех этапов. Поэтому «Проверить спеку» выбирайте **до** нарезки.

## Сценарий 4. Дефект прода: ветка баг

Маршрут короткий: баг-репорт → спека с флагом багфикса → (этапы?). Разреза и фундамента нет.

1. `git checkout -b feature/SMSEC-12345`, `/analyst-workspace` → «Бизнес» → «дефект».
2. Скилл фиксирует шаги воспроизведения, факт, ожидание, критичность. Причину и код он не ищет: это работа спеки и разработчика.
3. Получаете `bug_report.md`. `git push`, передаёте аналитику.
4. Аналитик: новая сессия или `/clear`, затем `/analyst-workspace` → «Аналитика», путь к репорту. Тип определится по имени файла.
5. Спека, «Проверить спеку», пуш.

Если в описании дефекта на самом деле новый функционал/новая фича, скилл остановит и отправит в БТ.

## Сценарий 5. Мелкая правка

Решение уже принято: поменять текст, поднять версию, добавить поле, сменить лимит. БТ не заводится.

1. `/analyst-workspace` → «Бизнес» → «правка». Ключ задачи обязателен.
2. Скилл выяснит, что именно меняется: контракт, данные, интерфейс, зависимость или конфигурация. Для каждого изменения нужна пара «как сейчас → как должно стать» конкретной фразой. Если в «как должно стать» есть порог (лимит, срок, сумма), скилл попросит пример на границе: само значение и ближайшее по ту сторону.
3. Если правка окажется крупной, скилл скажет «выше порога» и спросит, идти правкой или разворачиваться в БТ. Решаете вы. Крупной считается правка, которая меняет сразу многое из перечисленного или добавляет то, чего в системе ещё нет: новую роль, нового потребителя, новую интеграцию. Пример «выше порога»: «поле хранить, отдавать в ответе и показывать в карточке» — меняются и данные, и контракт, и интерфейс.
4. Получаете `change_request.md`. Дальше как с дефектом: аналитик пишет спеку с флагом правки.

Скилл не пересматривает решение и не достраивает его. Соседнее поле, которое «логично добавить заодно», в документ не идёт.

## Сценарий 6. Проверить любую спеку: `spec-readiness`

Приёмка отвечает за форму: разделы заполнены, пометки расставлены. `spec-readiness` отвечает на другой вопрос: можно ли по этой спеке писать код. Три агента с чистым контекстом читают спеку как бэкенд, фронтенд и интеграция между ними, четвёртый вычёркивает вопросы, на которые спека уже отвечает. Результат — список потенциальных противоречий и дыр в спецификации.

В маршруте `analyst-workspace` — вариант «Проверить спеку» в вопросе «Что дальше?» (у эпика проверяются все спеки, #0 первой). Отдельно, на любой спеке:

```
/spec-readiness coddoc/SMSEC-12345/technical_specification.md
```

- Работает на любой спеке: одиночной, детской, #0, багфикса, правки.
- Не работает на БТ и на `stages/stage-NN.md`.
- Ничего не пишет на диск. Ответы дописываете в спеку вы: ответьте на вопросы и выберите «Доработать спеку» в `analyst-workspace` — или руками.
- Если проверка ничего не нашла, список будет пустым, и это нормальный результат. Он означает, что исполнителю хватит данных, чтобы писать код. Насколько хороши сами решения в спеке, проверка не оценивает.
- Карточка существующего сервиса (🔵/🟡) дырой не считается. Требовать контракт у чужого сервиса значит просить аналитика его выдумать.
- У карточки «изменение существующего» проверяется само изменение и то, как оно встраивается в прежнее. Прежнее поведение ручки, которого правка не касается, вопросов не порождает.

Запускайте перед передачей разработчику и до нарезки на этапы. После правок спеки можно запустить ещё раз.

## Сценарий 7. Архивация после релиза

Фича уехала в прод — код изменился, карточки затронутых сервисов устарели. Архивация перечитывает эти сервисы через `service-map` и кладёт метку `.archived` в папку задачи.

1. Обновите локальные клоны затронутых сервисов. Карточка честна настолько, насколько свежа рабочая копия.
2. Новая сессия или `/clear`, затем `/analyst-workspace` → «Доработка готова». Или напрямую: `/archive-spec SMSEC-12345`.
3. Скилл перечислит, что архивирует, и остановится. Подтвердите список. Для эпика это важно: дети, которые ещё в разработке, из списка убираются.
4. Скилл запустит перечитывание сервисов и отчитается: что перечитано, что не нашлось в коде, что пропущено.
5. Закоммитьте карточки и `.archived` одним коммитом. Метка без карточек в истории приведёт к повторному перечитыванию.

**Архивируйте пачкой, сразу за релиз.** Каждая архивация перезаписывает карточки `services/*.md` целиком. Две фичи одного релиза, заархивированные в разных ветках, дадут конфликт на одних и тех же карточках, и разрешать его придётся руками. Правильно: после релиза в одной ветке архивировать все уехавшие задачи подряд, потом один коммит с карточками и метками. Эпик архивируется по ключу эпика разом.

Что ещё делать по отчёту:

- В отчёте может быть строка о том, что пункт спеки не найден в коде. Причин может быть три: изменение ещё не уехало в прод, локальный клон сервиса не обновлён или в коде оно названо иначе, чем в спеке. Проверьте по коду, какая из них ваша.
- Эндпоинты и поля, которые спека помечает устаревшими, — если их уже нет в коде, впишите в `notes` манифеста. Иначе этот факт скан не сохранит.
- Незавершённые спеки не архивируйте: метка помешает перечитать сервисы, когда фича действительно уедет.

## Сценарий 8. Обновить скиллы

```
/analyst-skills-update
```

Скилл запускает скрипт из своей папки, подтягивает свежие версии в `.gigacode/skills/` и печатает список «скилл — версия». Нужны `git` и `bash` (на Windows вместо bash — PowerShell из коробки) и доступ к репозиторию со скиллами.

Обновляйте перед новой задачей, не посреди неё: под-скиллы меняют шаблоны документов, и спека, начатая одной версией, может не пройти приёмку другой.

### Если нет доступа к репозиторию

Скрипт пробует https, потом ssh и падает с «не удалось получить скиллы ни по одному адресу», а логина и пароля для git у вас нет. Тогда ходите по SSH-ключу. Ключ делается один раз.

1. Сгенерируйте ключ. Команду можно выполнить самому в терминале (на Windows — в Git Bash) или попросить агента в чате:

   ```
   ssh-keygen -t ed25519 -C "ваша почта"
   ```

   На все вопросы жмите Enter. Появятся два файла: `~/.ssh/id_ed25519` (приватный, никому не показывать) и `~/.ssh/id_ed25519.pub` (публичный).

2. Скопируйте содержимое публичного ключа:

   ```
   cat ~/.ssh/id_ed25519.pub
   ```

3. Добавьте его в Bitbucket: аватар → Manage account → SSH keys → Add key, вставьте строку целиком.

4. Снова `/analyst-skills-update`: по https не пустит — скрипт сам перейдёт на ssh.

Если и после этого `Permission denied` — ключ добавлен, но доступа к репозиторию у учётки нет. Его выдаёт команда скиллов.

## Бест практисы

**Контекст**

- Без `services/` и `context/` скиллы работают, но вопросы общие, а варианты ответов агент выдумывает сам. Соберите контекст до первой задачи.
- Правила оформления API, архитектурные соглашения, общие сведения о системе (роли, домены) — в `context/` с `description`. Они напрямую влияют на качество новых контрактов в спеке и помогают формировать релиз с нуля, когда готовых сервисов и карточек ещё нет.
- После релиза соседнего сервиса — `/service-map <имя>`. Не ждите, пока карточка соврёт в спеке.

**Интервью**

- Отвечайте на вопросы фактами, не описаниями процесса. Атомарные вещи (ключи, версии, имена) скилл не угадывает — их нужно назвать.
- Ключ задачи — первый вопрос и жёсткий блокер. Заведите задачу в трекере до запуска.
- Согласились разрезать эпик — заведите подзадачи в трекере, когда агент спросит их ключи. Без ключа ребёнок не запишется.
- **Нет информации — скажите это прямо: «не знаю», «TBD», «пропускаем».** Пункт ляжет в документ как `TBD` и попадёт в открытые вопросы. «Уточню позже» так не работает: это обещание ответить, скилл будет ждать значение и файл не запишет. Ключ задачи отложить нельзя.
- **Материал, который относится только к части вопросов, прикладывайте в ответе на эти вопросы**, а не пачкой в начале: вопрос, материал и ваш ответ окажутся рядом. То, что пригодится и в других задачах (регламенты, стандарты), кладите в `context/` (Сценарий 2).
- **Сложную спеку с глубокими описаниями делайте в два прохода.** Первый проход поверхностный: на глубоких развилках отвечайте «не знаю», получите спеку со статусом «Требуются уточнения (N)». Второй — «Доработать», по одному открытому пункту за раз, лучше с `/clear` между ними: контекст не забивается, агент занят одной веткой спеки. После `/clear` вопрос «Что дальше?» вернёт `/analyst-workspace` → «Продолжить начатое». «Проверить спеку» и «Разбить на этапы» выбирайте после того, как пункты закрыты.

**Приёмка и проверки**

- Когда отдаёте документ на доработку, передавайте агенту список нарушений приёмки целиком, как она его выдала: с цитатами и номерами строк. В пересказе своими словами теряется точное место нарушения.
- Если нарушений много, выбирайте «Доработать», а не правьте документ руками: на новую редакцию приёмка запустится заново.
- Флаг `--no-review` отключает приёмку. Он подходит для быстрых итераций, когда документ вы будете вычитывать сами. Проверка статуса документа при этом остаётся: если в нём есть открытые пункты, скилл остановится и спросит, дорабатывать документ или принять как есть.
- «Проверить спеку» (`spec-readiness`) — перед передачей и до нарезки на этапы. `--no-review` её не выключает.
- Открытые пункты закрывайте до передачи разработчику. Разработчик спеку не дописывает: если в документе чего-то не хватает, он возвращает его аналитику.

**Метки в спеке**

- 🟢 — спроектировано здесь: новое или изменение существующего. Строить как написано.
- 🔵 — существующее, вы подтвердили. Источник указан в метке: «по карточке services/<сервис>.md», «по коду <сервис>, ветка …» (после глубокого поиска), «со слов», «по документу сверху» (в багфиксе и правке). Путь и поля под 🔵 — из этого источника. Сверить при интеграции: карточка и копия кода могли отстать.
- 🟡 — существующее, не подтверждено. Только словами, без пути и полей. Пункт открыт.
- Путь и поля существующего агент берёт из карточки `services/`, из кода или с ваших слов — и только после вашего «да». Не знаете — отвечайте «не знаю», будет 🟡. Не просите дописать контракт под 🟡: агент его выдумает. Подтвердите у владельца сервиса или запустите глубокий поиск.
- **Глубокий поиск в спеке.** Код чужого сервиса лежит рядом с репозиторием спек — в вопросе о нём будет вариант «Глубокий поиск». Разведчик `deep-search` читает код, спека показывает найденное со ссылками `файл:строка` и спрашивает «беру?». После «беру» в спеку идут метод, путь или имя события и поля — под 🔵 «по коду …»; файлы, строки и имена классов — нет. В багфиксе варианта нет.

**Git**

- Одна задача — одна ветка. Пушьте после каждого этапа, ветка ходит между ролями.
- Архивация — пачкой за релиз, в одной ветке, одним коммитом с карточками.
- Скиллы ничего не коммитят. Дифф читаете вы.

## Из чего состоят документы

Все разделы обязательны. Пустой раздел не выдумывается: там стоит `TBD` или «не применимо: причина». Статус документа считается механически по числу открытых пунктов: ноль — «Готово», один и больше — «Требуются уточнения (N)».

### Бизнес-требования

Шапка: ключ задачи, статус готовности, список открытых вопросов.

1. **Введение и контекст** — тип изменения (новое или доработка), описание проблемы (не решения), конечные потребители, заказчик и стейкхолдеры, как процесс идёт сейчас (или «сейчас никак»).
2. **Бизнес-требования** — бизнес-цель в форме «я как роль хочу …, чтобы …», ценность для бизнеса с метрикой, риски и меры по снижению.
3. **Объём** — что входит, что явно не входит, затронутые системы на уровне требования, без проектирования; внешние зависимости — что и от какой команды ждём, или «нет».
4. **Функциональные требования** — процесс шагами с нумерованными требованиями, критерии приёмки «дано / когда / тогда» на каждое (у критерия с порогом — пример на границе: само значение и ближайшее по ту сторону), бизнес-данные — объекты, с которыми работает функция (у доработки — что в них меняется), разбиение на части или «не применимо». Поля объектов скилл не спрашивает: в БТ попадают только сведения, которые вы назвали сами или дали файлом, остальное — тех-спека.
5. **Ограничения** — приоритет с обоснованием, сроки, ролевая модель с точными именами ролей из системы.
6. **Приложения** — необязательно: UX-пожелания, схемы, файлы от заказчика.

Система в БТ называется словами пользователя, не кодовыми именами сервисов. Единственное исключение — имена ролей.

### Техническая спецификация

Шапка: ключ задачи, документ-источник, статус готовности, легенда пометок 🟢🔵🟡, список открытых вопросов.

1. **Обзор изменения** — суть в два-три предложения с конкретными именами, тип, стороны (фронт, бэк, оба), таблица затронутых сервисов с владельцами и происхождением, связь с бизнес-целью.
2. **Взаимодействия** — ядро спеки. Карточка на каждый новый или изменённый контракт: граница, триггер, запрос и ответ с типами полей, примеры JSON, ошибки, состояния UI по ответу, авторизация, происхождение, ссылка на требование. Первая строка карточки — вид: новое (🟢); изменение существующего (🟢) — строка «Существующий стык» со своей меткой и таблица «поле | где | было | стало», «было» только у поля, подтверждённого источником, на 🟡-стыке пример JSON подписан как фрагмент; потребление существующего (🔵/🟡) — путь и поля из источника метки, у 🟡 словами. В конце сводный каталог ошибок. Чисто фронтовая задача — явная строка «новых взаимодействий нет».
3. **Бэкенд** — что делает каждый сервис по контрактам из раздела 2; сущности и хранение с пометкой происхождения, индексы, нужны ли миграции; где проверяется доступ.
4. **Фронтенд** — где и что меняется в UI, пользовательские сценарии, именованные состояния экрана (`loading`, `value`, `zero`, `empty`, `error_*`), таймауты и опрос, доступ по ролям.
5. **Нефункциональные требования** — синхронность, кэш, нагрузка; поведение при недоступности зависимостей; сводная матрица доступа.
6. **Релиз и интеграция** — порядок выката сторон, обратная совместимость, фиче-флаги или «релизим атомарно», план отката по сторонам, чек-лист преднастройки: роли, миграции, конфиги, сервисные аккаунты, алерты.
7. **Трассировка приёмки** — таблица «требование из БТ → взаимодействие → тест-кейс».
8. **Допущения и открытые вопросы** — сгруппированы по пометкам: подтверждено аналитиком, к валидации, открытые решения, расплывчатое, унаследованное из БТ.
