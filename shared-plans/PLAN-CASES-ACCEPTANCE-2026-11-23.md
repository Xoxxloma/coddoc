# План: случаи через тронутое место — приёмка на каждый случай — 2026-11-23

Источник: дефект из прода, прошедший через `change-request-doc` 1.4.0 (GigaCode); самоанализ агента из прода;
разбор 23.11 в разговоре; два независимых предложения субагентов по одной постановке, сведённые ниже.
**В скиллах ничего не внесено.** Решения человека отмечены в «Решено».

## Инцидент

Аналитик оформил через `change-request-doc` правку поля события в сервисе с процессом (этапы, типы проверок;
карточка `services/vector-b3.md`). В его словах было два случая: «в событиях RUNNING, даже если перешли в
руки» и «последний раз актуальное значение публикуем в ACTIVITY_RESULT». Агент свернул их в одно требование и
одну приёмку («одна сделка + ручка»). Дефект сидел в другой ветке процесса, приёмка его не покрыла; спека по
запросу унаследовала ту же одну приёмку. В карточке строка поля — одна фраза «на что ссылается событие»,
перечень этапов и типов проверок — на 290–370 строк выше.

Текст скилла в проме = 1.4.0 в репозитории: номера строк из самоанализа совпали.

## Корень

**Единица требования во всех трёх скиллах — тронутое место, а не случай, в котором видно его поведение.** На
требование — одна приёмка; «соседнее» спрашивается только как «кто читает». Вопроса «через какие случаи
проходит это место и где поведение меняется» нет ни в запросе на правку, ни в БТ, ни в спеке. Спека строит §7
строкой на требование и наследует одну приёмку сверху. Дефект тихий: приёмка зелёная, всплывает в проде.

**Случай** — условие, при котором тронутое место ведёт себя по-своему: состояние или этап, вид сообщения или
запроса, роль, экран, новые или старые записи.

## Масштаб

Данных по проду нет. По устройству: дыра бьёт там, где тронутое значение производится в нескольких случаях —
сервисы с процессом (этапы, статусы, типы), правка поля события или ответа, кнопка в нескольких состояниях,
лимит для нескольких ролей. В простом сервисе с одним путём не проявляется. Для своего класса — систематическая,
не единичная. Цена промаха высокая: приёмка зелёная, дефект в проде.

## Самоанализ из прода — что берём

- Берём: гейта на случаи нет; приёмка разрешена одна; два случая во входе свернулись в один.
- Не берём: «приёмок не меньше, чем веток» — абстракция для слабых моделей, тот же счёт даёт «FR на случай»
  через уже существующую «строку §7 на FR»; обязательная проверка на неизменённые ветки — хватит строки в «рядом
  остаётся прежним» (и §6.2 спеки), иначе работа аналитика удваивается на каждой правке.

## Решено

- **Карточки `service-map` не трогаем вообще** (человек, 23.11).
- **БТ входит в скоуп** (человек, 23.11): тот же пример легко идёт веткой БТ; «ждать данных с прода» — не довод.
- **Граница — не «только контракт».** Случаи — ось поперёк всех пяти строк правки. Таблица вопросов по пяти
  строкам (:230–236) не меняется; правило живёт в гейтах 3–4 (требование и приёмка).
- **Одно определение случая**, разная точка приземления по документу:
  - запрос на правку — случай с изменённым поведением = свой `FR-*` и своя строка приёмки; без изменения —
    строка в «Что рядом остаётся прежним»;
  - БТ — требование остаётся «правилом с развилками» (:577), критерий — на каждую развилку с разным поведением;
    порог — по-прежнему одной строкой с примером на границе. Дробить FR в БТ не стали: «одно правило с
    развилками» — намеренное правило, дробление меняет число FR в десятках проверок БТ;
  - спека, основной режим — §7 строкой на каждый критерий FR.
- **Названные случаи — обязательны; неназванные (видны по карточке) — неблокирующей гипотезой**, без нового ❓.
- **Режим правки в спеке — только по замеру** (С1б).
- Две стороны порога — не два случая. Перечислить случаи той же правки — границы правки, не достройка объёма.

## Не делаем

- Новый гейт или ❓ в реестре — меняется счёт, ломаются грейдеры, блокирует запись на простых правках.
- Вопрос про случаи на каждой правке — на кнопке и версии это шум; срабатывает, только когда больше одного
  случая назвал аналитик или видно по карточке.
- Переписывать вопросы пяти строк, трогать сторожа и «одну фразу» в «Что тронуто».
- Строки §7 без требования и составной ключ «требование + случай» — ломают связку по номерам.
- Разрешать спеке дописывать требования — это пересмотр решения; нашла случай без FR — вопрос аналитику.
- Обратные ссылки «поле → этапы» в карточках, правки формата карточек.
- Режим багфикса.
- Слова инцидента (RUNNING, ACTIVITY_RESULT, «сделка», «ручка») и предметную область проб — в скиллы.

## Срезы

Каждый срез — коммит по «да», по одному рычагу с замером между ними. Номер CHANGELOG — от `origin/main` в момент
коммита (сейчас 5.135). Замер — Sonnet; новая проба ×3, регресс по ×2. Пробы и грейдеры пишут субагенты.

### С0 — пробы до правок

Предметная область — не из примеров скиллов и не из инцидента. У каждого грейдера — самотест.

- **`cr-case-w`** (имя условное): CR-SMALL; «как должно стать» одной фразой с двумя случаями, приёмка дана на оба,
  рядом неизменённый случай; все гейты отвечены. Зелёный: два `FR-*`, якоря случаев в разных строках FR, у каждого
  FR строка в «Как проверят», неизменённый — в «рядом остаётся прежним», вердикт «правка». Красный: оба якоря в
  одной строке FR.
- **`cr-case-q`**: CR-SMALL + одна карточка — объект с 3–4 состояниями и сообщение с поводом «при каждом переходе»;
  аналитик называет один случай. Зелёный (на С3): вопрос называет подписью другое состояние — меняется или
  остаётся. Пока не С3 — только база.
- **`br-case`**: доработка в сервисе с этапами, пользователь называет два случая с разным поведением, все гейты
  отвечены. Зелёный: два критерия с разными «Дано» (не один на оба). Плюс плечо спеки по замороженному выходу:
  в §7 две строки.
- **База на текущем тексте ×2 — должна быть красной.** Если на Sonnet база зелёная, проба ничего не различает —
  остановиться и решить (мерить на модели слабее, как в проме, или менять пробу).
